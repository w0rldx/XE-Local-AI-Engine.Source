## Executive summary

**v1 is sound.** All eleven of its load-bearing code claims verified as stated; two are *worse* than described (port TOCTOU produces a permanently misleading "model too large" error; MTP misclassification is enforced at four separate layers). Three v1 statements need correction (§2).

**The highest-impact new findings are not llama.cpp flags.** They are:

1. A **user-visible hard failure** v1 missed entirely: the 3-process cap equals the number of model roles, the cap *rejects* instead of evicting, and in-window processes are never evicted — so "run a knowledge search, then switch chat model" throws for up to 15 minutes (§3.1).
2. Two **O(n²) amplifiers on the streaming path**: every 100 ms persistence flush re-decrypts/re-encrypts/rewrites the *entire* accumulated message, and every SignalR delta event carries the *full* accumulated content and reasoning (§3.3, §3.4).
3. A **silently inherited 8 GiB host-RAM prompt-cache budget** (`--cache-ram` default 8192 MiB in the pinned build, confirmed against the binary) with an open upstream Linux bug where the limit is ineffective and the OOM killer SIGKILLs llama-server (§3.2).
4. **No CPU thread policy on partial-offload GPU launches** — precisely the normal ≤16 GB VRAM case — reintroducing the oversubscription AUD4-17 fixed for CPU-only builds (§3.6).

**Pin verdict:** `b10201` is 7 days old; the b10201→master delta (117 commits) contains essentially no consumer-inference perf work. The one commit that argues for a bump is the grammar fix [#26613](https://github.com/ggml-org/llama.cpp/pull/26613) (merged 2026-08-05), which degrades `maxLength > 2000` to unbounded instead of rejecting — this repo's own known GBNF tool-schema trap. Hold the pin unless that trap still costs workarounds.

## 2. Corrections to v1

1. **"The default whole-invocation ceiling is therefore finite—300 seconds" understates the real ceiling.** `SetInvocationDeadline` re-points the same CTS on *every* human round-trip: a park on approval/ask_user re-arms to `MaxPendingToolCallAge` (10 min default) + a fresh 300 s, and the tool loop can park up to `MaximumToolIterationsPerRequest` times. A **disconnected** invocation parked on an approval nobody will answer holds the llama-server lease and the whole transcript for ~15 minutes *per park*, not 300 s total. This materially raises the priority of v1's P0 subscriber-aware disconnect policy: the grace deadline must also apply to parked human waits when no subscriber exists.
2. **"CPU thread tuning: configured by policy" is true only for pure-CPU builds.** `ResolveCpuThreads` returns `(null, null)` for every GPU variant, so partial-offload launches — the normal case at ≤16 GB VRAM with 12B–27B models — run CPU-resident layers at llama.cpp's auto thread count (§3.6).
3. **"DFlash/DSpark … not in the compiled allowlist" conflated app and runtime.** The pinned b10201 binary's `--spec-type` accepts `draft-dflash`/`draft-dspark` (binary probe); only the *application's* allowlist omits them. Also resolved from v1's open questions: `--cache-ram` **is** supported by the pinned build, default **8192 MiB** (§3.2), and `--parallel` defaults to `-1` (auto) upstream — the app's explicit `--parallel 1` is load-bearing, since auto resolves to ~4 slots with unified KV.

## 3. New findings (prioritized)

### P0

#### 3.1 Model-switch hard failure: cap = 3 = number of roles, reject-not-evict, in-window never evicted

`AdmitAndAllocatePortAsync` throws a non-retryable `CapReached` ("The maximum number of local models are already loaded…") when `_allocatedPorts.Count >= MaxLoadedProcesses` and `TryEvictIdleLeastRecentlyUsed` finds no victim; the victim scan **skips any process used within `IdleTimeToLive`** (15 min). `ModelRole` has exactly three members — Chat, Embedding, Reranker — and all three count against the one cap of 3. With knowledge base + reranker enabled, a node routinely holds exactly 3 processes, and background indexing/search keeps refreshing the pooled processes' `LastUsedUtc`. Any fourth key — most commonly **the user picking a different chat model** — finds zero evictable victims and the send errors, for up to 15 minutes. Two independent passes converged on this as the most likely user-visible llama.cpp failure on target hardware, and it is not memory-driven at all.

The eviction score is also byte- and cost-blind (pure `LastUsedUtc` LRU): it would never prefer sacrificing a ~100 MB embedding process (~1 s reload) to keep a 20 GB chat model warm, or vice versa.

**Fix direction (composable with v1's P1 residency ledger):** a foreground chat spawn must be able to preempt an idle-*enough* pooled process — e.g. roles below Chat priority are evictable outside their own active leases regardless of TTL window; score victims by `reclaimable bytes / reload penalty`; and raise or role-partition the cap (chat slots vs pooled slots) so the pooled pair cannot starve chat. Acceptance test: index a document continuously, run a search, switch chat model — the switch must succeed without waiting out the TTL.

#### 3.2 Silent 8 GiB host-RAM prompt-cache budget, with an open Linux OOM-kill bug

Binary probe of the pinned build: `-cram, --cache-ram N` — "set the maximum cache size in MiB (**default: 8192**, -1 no limit, 0 disable)" ([PR #16391](https://github.com/ggml-org/llama.cpp/pull/16391)). The app never passes it, so every chat process inherits an 8 GiB host-RAM claim for saved prompt states on top of weights, active KV, the OS and the app — on a 16 GB machine that is half of physical RAM. Worse, [#22629](https://github.com/ggml-org/llama.cpp/issues/22629) (open): on Linux the limit is *ineffective* — eviction triggers only on `std::bad_alloc`, which never fires under default `vm.overcommit_memory=0`; pages fault in on write and the **OOM killer SIGKILLs llama-server**, bypassing eviction entirely. That failure then presents through the supervisor as a process exit, i.e. the misleading "incompatible or too large" error of §1.

**Fix:** size `--cache-ram` from detected RAM (order of 1024–2048 MiB at 16 GB; scale up with headroom), charge it to the host-RAM side of v1's residency ledger, and emit it on every chat launch (explore *and* replay). This upgrades v1's P2 "probe needed" item to a P0 config change — the probe is done.

#### 3.3 Quadratic persistence cost per streamed turn

`NodeChatMessageCommands.UpdateCorrelatedMessageAsync`, reached from `FlushAssistantPartialAsync` on a 100 ms debounce, per flush: `ReadMessageAsync` (SELECT + decrypt content + decrypt/deserialize metadata), re-serialize the whole metadata (accumulated `parts[]` + full reasoning), AEAD-re-encrypt the **entire** accumulated content and metadata, UPDATE both blobs. Work per flush is O(everything generated so far) → total work per turn is **quadratic in output length**. A 100 KB response streaming for 100 s ≈ 1000 flushes × ~50 KB average = tens of MB each of decrypt, JSON, encrypt, and SQLite write for 100 KB of output. The debounce bounds the *rate*, not the per-event cost. This is the largest CPU/IO amplifier on the streaming path and is absent from v1.

**Fix direction:** debounce interval that scales with accumulated size, or an append-only partial-content journal so a flush writes only the delta (compact to the final blob at terminalization). Either preserves crash-resume semantics.

#### 3.4 Every SignalR delta carries the full accumulated content and reasoning

`ChatStreamEventMapper.MessageEvent` embeds `message.Content` and `message.Reasoning` — the complete accumulated strings — in every `AssistantDelta` event: O(n²) wire bytes and JSON serialization per turn at ~10 frames/s. This is load-bearing today: `NodeChatStreamState.ts` *prefers* the snapshot over the delta (`event.content ?? existing + delta`), so the fix is a coordinated protocol change — delta-only live events, keeping the snapshot for resume replay (which already has its own snapshot event in `InvocationResumeRegistry`). Do this together with §3.3 and v1's P0 channel bounding: they are the same "stream budget" work item, and bounded channels without delta-only events would fill their budget with n× redundant snapshots.

### P1

#### 3.5 Process-wide mutation gate held across health probes on every inference request

`EnsureRunningAsync` takes the single `_runtimeMutationGate` `SemaphoreSlim` on **every** ensure — chat, embedding, and rerank — and holds it through external-endpoint resolution, the source-build check, and `TryReuseAsync`'s liveness probe, which can block up to 2 s (`ReuseLivenessProbeTimeout`). With background KB indexing alongside chat (the normal agent workload), one stalled probe on any role head-of-line blocks every other role's ensure. The per-key `_ensureGates` already provide single-flight per process; the global gate exists for rare operator runtime mutations and should be an `AsyncReaderWriterLock`-style shared/exclusive split, or should scope down to the mutation paths only. Related: `_admissionGate` is held across a *synchronous* `TreeKill` + `Dispose` of the evicted process, so tearing down a multi-GB model serializes every unrelated model's port allocation and release behind it.

#### 3.6 No CPU thread policy on partial-offload GPU launches

`ResolveCpuThreads` returns `(null, null)` for every non-CPU variant, so `-t`/`-tb` are emitted only on pure-CPU builds — while the supervisor itself logs the case that matters ("placed {Offloaded}/{Total} … the remainder runs from system RAM"). On ≤16 GB VRAM with 12B–27B models partial offload is the *normal* path, and CPU-resident layers then run at llama.cpp's auto thread selection. Upstream nuance (research-verified): unset `-t` routes to `common_cpu_get_num_math()`, which skips Intel E-cores and SMT siblings **on x86_64 Linux only**; native Windows cannot distinguish P from E cores, so the same machine behaves differently under WSL vs native Windows — and native Windows is the shipped target. Extend the physical-core-aware policy (AUD4-17) to any launch where offload < total layers, and pass an explicit P-core count on hybrid Intel under Windows. (Unsloth ships the inverse special case: omit `-t` generally, pin `--threads 2` on Windows *full*-offload.)

#### 3.7 Frozen-profile replays have no OOM adaptation and no metrics

Two candidates (safe-KV retry) are built only when `UseKvCacheQuantization` is true, which `ResolveAsync` sets false for every replay; and `TryDownTierAfterOutOfMemory` returns false when the allocation source is `FrozenProfile`. Net: an explore spawn gets a safe-config retry plus two context down-tiers, a frozen profile gets **zero adaptation** and fails with the non-retryable "exited while loading" — yet frozen profiles are the steady state on a tuned machine, and free VRAM on a consumer box changes between runs (browser, game, second app). Additionally `--metrics` is emitted only alongside `--fit on` in explore mode (`ensureMetrics: false` on replay), so v1's Phase-0 observability plan (cache-reused tokens, slots, KV bytes from `/metrics`) is unavailable on exactly the machines that have frozen a profile. **Fix:** allow at least one context down-tier + safe-KV retry for `FrozenProfile` allocations (invalidating the profile on success), and emit `--metrics` unconditionally.

#### 3.8 KV-quantization guardrails: a 25× cliff, an asymmetry trap, and architecture gating

The blanket `-ctk q8_0 -ctv q8_0` is the right default *direction* (K is more sensitive than V — [PR #7412](https://github.com/ggml-org/llama.cpp/pull/7412), [#23470](https://github.com/ggml-org/llama.cpp/discussions/23470); q8/q8 is quality-free) but carries three unhandled hazards:

- **`GGML_CUDA_FA_ALL_QUANTS` is OFF in official CUDA release builds**; unsupported K/V combos silently fall to an unfused path — measured 96 vs 2361 tok/s (~25×) on Gemma-class ([#24485](https://github.com/ggml-org/llama.cpp/issues/24485)). There is **no runtime signal**. The app's managed-build pipeline and BYO `XE_LLAMACPP_SERVER_PATH` binaries must both be verified; add a one-time micro-probe (tiny model, q8 KV, compare decode rate against f16 KV) or a build-flag check to the device audit.
- **Never emit an asymmetric K/V pair**: it forces the cache off-GPU on CUDA (30.6 vs 883 tok/s pp, [#20866](https://github.com/ggml-org/llama.cpp/issues/20866), open). The current code always emits symmetric pairs — freeze that as an invariant (test), since the safe-KV fallback path is exactly where an asymmetric "optimization" would creep in.
- **Gate by architecture**: quantized-KV support lands *after* new attention schemes do (DeepSeek MLA gibberish [#25382](https://github.com/ggml-org/llama.cpp/issues/25382), fixed; MiniMax-M3 assert, fixed in b10201; **GLM-4.7-Flash + quantized KV still crashes past ~65k tokens — [#19036](https://github.com/ggml-org/llama.cpp/issues/19036) open**). The safe-KV *retry* exists for launch failures; a runtime *crash* at long context does not trigger it. Maintain a small denylist per model family, refreshed on pin bumps.

Related SWA interaction (affects the named gemma target): with SWA active and no `--swa-full`, out-of-window KV is discarded — no prefix cache, no reuse; `--swa-full` costs ~5× KV VRAM. `--cache-reuse 256` is emitted unconditionally for chat with no SWA gate. Decide per family: on SWA models at ≤16 GB, accept no-reuse rather than 5× KV.

#### 3.9 Launch-line hygiene against the actual pinned defaults

Binary-probe + upstream-verified against b10201: `--jinja` is now default-on (**redundant**), `--fit on` is the default (**redundant**, though harmless), `-fa on` is redundant (default `auto`) but defensible as an explicit assertion, and `--mmap`/`--mlock` spellings are **deprecated** in favor of `-lm/--load-mode` (mixing spellings is last-wins — migrate before removal; keep `mmap` default at 16 GB, since mlock is what *causes* swap-death there). `--no-warmup`'s stated justification is stale — the readiness budget it protected against is now size-aware (120 s + 20 s/GiB, cap 600 s) — and its real effect is deferring graph/kernel/cuBLAS init onto the user's first message (v1's own capture: cold TTFT 1723 ms vs warm 141 ms on a 0.5B model; proportionally worse at 9–27B partial offload). No measured evidence exists in either direction upstream: measure once on this stack (warmup on vs off × cold TTFT), then keep or drop deliberately. `--fit` note: explicit `-c` protects only *context* from fitting; since the app passes no `-ngl`/`-ts`/`-ot` on explore, `--fit` still performs layer/tensor fitting — the current line reads like auto-fit but is manual for context, deliberate-choice territory (either own the context math, or drop `-c` and set `--fit-ctx <floor>`). Also freeze `--port` emission with a test: upstream announced a default-port change (8080 → 9931, [#26508](https://github.com/ggml-org/llama.cpp/pull/26508)).

The single highest-leverage structural copy from Unsloth Studio: **`probe_server_capabilities()`** — parse `llama-server --help` once, cache on `(path, mtime)`. It converts the pin from a contract into a floor, survives BYO binaries and flag renames, and is the mechanism v1's "runtime capability probe" recommendation should take. (Their fit arithmetic is also worth stealing verbatim: budget = free − 3% of *total*, binary-search context, floor 4096, round down to ×256, `--fit-target 512`.)

#### 3.10 Foreground/background contention on the pooled roles

- The search-time query embed targets the same single-slot (`--parallel 1`) embedding process as ingestion's 64-chunk (~32K-token) batches; a KB search issued mid-indexing waits for the whole in-flight batch — multi-second retrieval stalls on CPU boxes. No priority lane, pause, or backpressure exists. Smallest fix: cap the ingest batch (or split it) so a foreground request's queue delay is bounded, and pause ingestion submission while a chat/search embed is pending.
- `LlamaServerRerankerClient` has a fixed 5 s request timeout against a pool of `max(20, 4×limit)` ~500-token documents scored sequentially on a single slot: CPU-only boxes exceed it routinely, so **reranking silently degrades to fusion order** with only a log line — the configured reranker effectively never runs, and no metric distinguishes timeout-degrade from unavailability. Scale the timeout with pool size/hardware, and meter degrade cause.
- The count-bounded no-coalescing embedding cache is **triplicated**: `EmbeddingPlaybookRetrievalRanker` (512, FIFO), `MemorySemanticDeduplicator` (512, same shape), `KnowledgeQueryEmbeddingCache` (128, TTL but no coalescing). v1's P2 byte-accounted-LRU + in-flight-dedup fix should be one shared component applied at all three sites.

#### 3.11 Per-round constant-work in the agent/tool path

The tool loop multiplies these by up to 40 provider rounds per turn:

- `ProviderMessageTokenEstimator.EstimateTools` calls `JsonSchema.GetRawText()` (full-schema string) + char-scan **per tool per round**; messages are memoized via `ConditionalWeakTable`, tools — strictly immutable per invocation — are not. Same-shape fix as the existing memo.
- `BuildToolBudgetDefinitions` + `ConversationContextBudgeter.EstimateFixedOverhead` wrap the system prompt and every tool definition in **new** `ChatMessage` instances per call, guaranteeing a miss in the instance-keyed memo — the full system prompt (tens of KB with skills) is re-scanned on every `ApplyContextBudgetAsync` (once per approval-resume round). Compute once into `TurnPolicy`.
- `LlamaGrammarToolSchemaCompatibility.RequiresSanitizing` routes struct JSON enumerators through LINQ `Any`, boxing per schema node — despite its "allocation-free pre-check" doc comment — per tool per round. A `foreach` rewrite is behavior-identical.
- `InvocationRunner` retains **every** streamed `AgentResponseUpdate` of a segment whenever *any* tool is offered (`approvalPossible = AllowedTools.Count > 0`), purely to fold history if an approval surfaces. `ToolApprovalRequestContent` can only originate from `ApprovalRequiredAIFunction`, so the correct predicate is `AllowedTools.Any(t => t.RequiresApproval)` — dropping the retention for the common all-auto-approved agent turn.

#### 3.12 Streaming-path memory retention and per-token overhead

- `StreamingText` fixed the O(n²) *CPU* problem but not memory: each node holds `_previous` and caches its materialized full string, and flush/replay/cursor reads materialize on different nodes — tens of MB of dead strings retained per long turn until invocation state drops. Collapse the chain when a node materializes.
- `StreamIdleWatchdog.PullNextAsync` allocates ~7–8 objects + a timer schedule/cancel **per token** (`AsTask` + linked CTS + `Task.Delay` + `WhenAny`); `moveTask.WaitAsync(idleTimeout, ct)` is semantically identical at a fraction of the cost.
- `InvocationResumeRegistry` allocates a capturing closure per state publish (per token) in `GetOrAdd`; `TryGetValue`-first removes it.
- Per token, the producing thread already pays two locks, an `InvocationState` allocation, a `StreamingText` node, and a synchronous multicast dispatch before any of the above — keep this path's budget in view when adding handlers.

### P2

- **History materialization:** the full conversation is loaded, decrypted, and projected **three times** per turn (`NodeChatReadModel` → `ConversationMessageDto` → `ChatMessage`) with no load cap — compaction shapes what is *sent*, not what is *loaded*. Per-turn pre-first-token cost grows with conversation length; add a load-side cap keyed to the compaction boundary.
- **Ingestion transients:** ~4–5 concurrent copies of a document's text exist at the embed step (blob bytes, `MemoryStream`, extracted doc, section builders, chunk contents, contextual texts, vector blobs); bounded by 1-doc concurrency, ~0.5 GB transient for a 100 MB extract. Stream per-section extract→chunk→embed→write. Also: `KnowledgeIndexWriter` re-creates two `DbCommand`s per chunk (no prepared-statement reuse) and copies each vector a second time.
- **Startup capture:** the `-lv 4` log sink stays wired for the process's lifetime — every serving-time line pays a lock + string copy into a 16 KB buffer never read after readiness. Detach the sink at ready.
- **Dev-only reranker resilience:** under Aspire the reranker client carries the standard resilience handler (health probe opted out per AUD4-15; reranker didn't) — retries re-run full cross-encoder passes and the breaker can refuse a healthy respawn; dev-measured rerank latency is unrepresentative. Desktop builds unaffected.
- **Latent embedding-endpoint staleness:** `DeferredLlamaServerEmbeddingGenerator` caches its endpoint forever with no `IsServerGone` self-heal (safe today only because all four callers scope per-operation — which itself pays a fresh `OpenAIClient`+adapter per document/search).
- **Duplicate tool-call `Requested` events** are absorbed downstream but each pays serialize + dispatch + wire.
- **Sequential health probes** in `CheckHealthAsync` (≤3 s worst case; diagnostics only).

## 4. External-research updates to v1's technique table

- **Speculation:** v1's per-class contract split stands, with sharper numbers. EAGLE-3 acceptance is *higher* on quantized targets (Q4_K_M → 2.26×, 92.5% acceptance, [#18039](https://github.com/ggml-org/llama.cpp/pull/18039)) — but acceptance ≠ speedup: multi-token verification disables CUDA graphs (GPT-OSS-120B: 86% acceptance yet *slower* than plain decode), and MoE targets regress. `draft-mtp` is large-model-only in practice (Qwen3.6-27B+ class), costs ~2.5 GiB extra and pins the server to one concurrent request. **N-gram modes are the only zero-VRAM speculative option** and the sane first candidate at ≤16 GB, especially for code/edit loops.
- **Quants:** `Q4_K_M` may be Pareto-dominated — Q4_K_S smaller *and* better, Q5_0 highest aggregate on a 13-scheme/5-benchmark study ([arXiv 2601.14277](https://arxiv.org/html/2601.14277v1); k-quants only — don't over-generalize, but stop defaulting reflexively). Gemma-4 specifically: naive Q4_0 conversion corrupts Google's QAT checkpoint; prefer Unsloth's QAT-corrected artifact (99.96% vs 24.77% byte-exactness). **No major publisher ships NVFP4 GGUFs** (Unsloth's NVFP4 releases are safetensors for vLLM/SGLang) — the sm_120 NVFP4-GGUF capability on this box is real but has no artifact ecosystem; don't build a UI tier for it.
- **Alternative runtimes — verdict unchanged, evidence sharper:** ik_llama.cpp wins prefill 3.8× but *loses decode 4.4×* on exactly the hybrid-offload path this app ships (closed wontfix); TensorRT-LLM still has no consumer path (RTX 50 = WSL-only); ExLlamaV3 1.x is Python/CUDA-shaped; Vulkan-vs-CUDA gap narrowed (~10% decode) — Vulkan is the credible universal fallback, CUDA stays default on NVIDIA. New entrant worth one evaluation: **Microsoft Foundry Local** (GA, first-class C# SDK, Windows ML driver-matched execution providers) as a *Windows-only secondary provider* — it is the only 2026 stack solving "which backend binary do I ship to this Windows box" for .NET. llama-server's own **router mode** (`--models-dir`, `--models-max`, load/unload endpoints, LRU scheduler) now overlaps the app's per-role supervision — not a reason to switch (the app's supervisor is richer), but watch it before building more supervisor features upstream already ships.
- **Market constraint:** DDR5 prices roughly 4×'d into 2026 and are structural — the 16–32 GB floor is sticky. Do not design assuming users add RAM.

## 5. Consolidated action list

Ordered by (user-visible impact ÷ risk); items 1–4 are shippable without new evidence, items 5+ follow v1's experiment gates.

1. **Fix the model-switch hard failure** (§3.1): role-priority preemption + byte-aware victim scoring; acceptance test = switch chat model during active indexing.
