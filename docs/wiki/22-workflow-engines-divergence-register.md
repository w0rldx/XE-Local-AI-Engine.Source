# Workflow Engines Divergence Register

> Reviewed: 2026-09-15 · Code-grounded.

Two workflow engines live in this codebase: [Dev Workflows](../../XE-Local-AI-Engine.Client.Application/Services/DevWorkflows)
(`Services/DevWorkflows/`, Dev Mode's graph runtime) and [Graph Workflows](21-graph-workflows.md)
(`Services/GraphWorkflows/`, the general-purpose operator-authored DAG feature). Graph Workflows was
**copy-adapted** from Dev Workflows by explicit ruling — operator rulings D2 and D4 of the Graph Workflows
assessment, 2026-09-03: copy-adapt the Dev Workflow graph core into the new module, extracting a shared core
only later; no shared library; never edit `DevWorkflow*` files. The two stacks do not interoperate today: no
shared assembly, no shared entity, no code path that reads one engine's rows from the other. This page exists
because that follow-up extraction never landed and both engines now ship, so every future fix to one engine's
behavior is a **decision to make about the other**, not an automatic consequence. The 2026-09-06 MAF
best-practice review's finding F11 names the risk directly: "Every future graph-engine fix must be made twice
or consciously not, with no record of which divergences are intentional." **Convergence itself is explicitly
deferred** — operator ruling D10, 2026-09-09: write this register, do not design a merge.

Sections 1–4 compare **only** those two engines. §6 is an addendum outside that comparison: one adjacent, still-undecided duplication in a third module, recorded here because it is the same shape and has no other register.

Where a plan document and the code disagreed, the code (read on this baseline) wins, and the note says so.

## 1. Comparison table

| Axis | Dev Workflows | Graph Workflows |
|---|---|---|
| Run status vocabulary | `Pending, Running, Pausing, Paused, WaitingForApproval, Cancelling, Completed, Failed, Cancelled` (`DevWorkflowRunStatus`, `XE-Local-AI-Engine.Client.Persistence/Entities/DevWorkflowEnums.cs`) | `Pending, Running, WaitingForApproval, Cancelling, Completed, Failed, Cancelled` (`GraphWorkflowRunStatus`, `XE-Local-AI-Engine.Client.Persistence/Entities/GraphWorkflowEnums.cs`) — **no `Pausing`/`Paused`: a run cannot be paused at all**, only cancelled |
| Node-run status vocabulary | adds `Blocked` (retries-exhausted intervention state) to the Graph Workflows set (`DevWorkflowNodeRunStatus`) | no `Blocked`; a node run that exhausts retries fails outright (`GraphWorkflowNodeRunStatus`) |
| Node kind vocabulary | 7 kinds, Start/End implicit (zero in/out degree): `Agent, Tool, DevTask, HumanGate, Gate, Parallel, Join` (`DevWorkflowNodeType`) | 8 kinds, Start/End explicit nodes: `Start, Agent, Tool, Condition, Parallel, Join, Pause, End` (`GraphWorkflowNodeKind`) — no `DevTask` equivalent (no hash-locked apply-gate integration node) |
| Decision vocabulary | one enum for both a gate decision and a retry-budget intervention: `Approve, Reject, RequestChanges, Retry, Skip, Abandon` (`DevWorkflowDecisionKind`) | `Approve, Reject` only (`GraphWorkflowDecisionKind`) — no `RequestChanges`, no `Retry`/`Skip`/`Abandon` human intervention, because there is no `Blocked` state to intervene on |
| Approval model | in-RAM parked node run; durable `WaitingForApproval` row answered by `IDevWorkflowRunService.DecideAsync`, keyed by client `operationId`, three distinct 409 exception types (`DevWorkflowInvalidTransitionException`, `DevWorkflowRunInFlightException`, `DevWorkflowGateAlreadyDecidedException`) | durable `WaitingForApproval` row answered by `IGraphWorkflowRunService.DecideAsync`, keyed by client `operationId`; one merged `GraphWorkflowRunConflictException` (stale version at start **or** cancel-after-terminal) plus a separate `GraphWorkflowGateAlreadyDecidedException` — fewer conflict discriminators |
| Restart / reconciler behavior | `DevWorkflowStartupReconciler`: a `Running` **Agent** node run resumes — its work session survives on its own checkpoint, so recovery costs **no retry attempt** — driven by a run-wide re-attempt budget (`MaxTotalAttempts`) spent across every interrupted sandbox row in a fixed order, with rows past budget going to `Blocked` for a human | `GraphWorkflowStartupReconciler`: a `Running` **Agent or Tool** node run is unconditionally **failed** as `Interrupted` — "an `IInvocationRunner` turn is an in-process task with no durable handle" (in-code doc on `GraphWorkflowAgentExecutor`) — and re-attempted only on the dispatcher's ordinary retry stage, if the node/run budgets still allow it |
| Cross-node fix loop | `retryTarget`: a node may name a strict ancestor to re-run on failure, validated at save time (`DevWorkflowGraph.cs`), bounded by `MaxTotalAttempts` | **absent by design** — `GraphWorkflowStateMachine.cs` and `GraphWorkflowDispatcher.cs` both carry an explicit comment: "There is no cross-node fix loop in v1" / "No cross-node routing, ever" |
| Dynamic materialization (O5 decomposition) | present: a template subtree clones once per task, up to ~20× (`DevWorkflowGraph` template keys, `MaxNodesPerDefinition` sized for it at 500) | **absent** — no `Materializ*` type anywhere under `Services/GraphWorkflows/`; the node/run caps are correspondingly smaller (`MaxNodesPerDefinition` 200) |
| Agent execution stack | Agent Work Sessions: `IWorkflowOwnedWorkSessionLifecycle` / `WorkSessionExecutionSupervisor`, stepwise, resumable, has its own transcript; zero `IInvocationRunner` hits under `Services/DevWorkflows/` | headless `IInvocationRunner` via `RuntimePackage`, one turn per node run, `IsUnattended = true`, optional `ResponseJsonSchema` for structured output (`GraphWorkflowAgentExecutor`) |
| Tool node execution | sandboxed repo validation/apply shell commands over a synthesized Dev Mode workspace snapshot (`DevelopmentWorkspaceProvider`, `DevelopmentCommandProfileCatalog`) | named-tool invocation via a promoted `IToolInvocationService` (from `HeadlessToolExecutor`), v1 restricted to `ToolCategory.ReadLocal` **and** no-approval-required tools — no repo/sandbox concept at all |
| Persistence shape | `GraphJson`/`InputJson`/`OutputJson` etc. as encrypted columns, run-pinned `GraphJson` + `GraphRevision` copied from the definition at run start (no run-edge table), append-only `DevWorkflowRunEvent` log with `(RunId, OperationId)` idempotency | same run-pinned-blob-plus-revision shape and append-only event log pattern, explicitly modelled on Dev Workflows (`GraphWorkflowStartupReconciler` doc: "modelled on the development-workflow reconciler this is modelled on") |
| Hub / event surface | `DevWorkflowRunHub`, content-free `devWorkflowChanged{...}` ping + REST replay (ruling O10) | `GraphWorkflowRunHub` (`XE-Local-AI-Engine.Client/Hubs/GraphWorkflowRunHub.cs`), content-free `graphWorkflowChanged{runId, seq, kind}` ping + REST replay, replay capped and `replayTruncated`-flagged — same discipline, independently implemented |
| MAF/MEAI boundary | zero references to `Microsoft.Agents.AI*` or `Microsoft.Extensions.AI*` under `Services/DevWorkflows/` (verified by grep) | zero *code* references either; the only hits are two doc-comments in `GraphWorkflowGraph.cs` and `GraphWorkflowDefinitionService.cs` describing `Microsoft.Extensions.AI.OpenAI`'s strict-schema JSON transform — no MAF/MEAI type is imported or held past the runner boundary in either engine |
| Feature flag posture | `DevWorkflowOptions.Enabled` — **default `false`**; the module ships gated off, matching Dev Mode's overall opt-in posture | `GraphWorkflowOptions.Enabled` — **default `true`** since S4 (ruling D9): "the editor, the run engine and the run view are verified end to end, so a node ships with them offered"; both flags gate behavior only, never DI registration, and a disabled route family 404s at the request-path gate rather than 500ing |
| Sandbox concurrency bound | `MaxParallelToolNodes` (default 2) — a dedicated semaphore-bound sandbox lane, because Tool/DevTask nodes launch real build processes | no equivalent option; the Tool lane's own in-flight bound is scoped to `IToolInvocationService`'s `ReadLocal`-only, no-approval surface, which does not launch a build |

## 2. Deliberately dropped (with authority)

| Dropped from Dev Workflows | Authority |
|---|---|
| `Pausing`/`Paused` run states (run-level pause/resume) | Never a v1 requirement: the 2026-09-03 assessment's recommended shape made `Pause` a *node* kind, parked in `WaitingForApproval` with a `PendingDecisionKind` and answered by a decide endpoint, and named no run-level pause at all; operator ruling D6(a) fixed the v1 vocabulary as `Start, Agent, Tool, Condition, Parallel, Join, Pause, End` with no `Paused` run status. `GraphWorkflowEnums.cs`'s own doc comment states it plainly: "No `Interrupted`: runs auto-resume... `Cancelling` exists because cancel is fire-and-forget". |
| `Blocked` node-run state and the `Retry`/`Skip`/`Abandon` human-intervention decisions | Same D2/D6 ruling; no retry-budget-exhaustion story exists in Graph Workflows v1 because there is no cross-node fix loop (below) to exhaust a budget against. |
| Cross-node fix loop (`retryTarget`) | Operator ruling D6(a), 2026-09-03, deferred the richer node vocabulary — "Transform and Sub-workflow v2" — and the fix loop was never proposed for v1 at all; the assessment's recommended shape gave Graph Workflows per-node `MaxAttempts` and `NodeTimeoutSeconds` plus a run-wide `MaxTotalAttempts` budget, and **no** cross-node `retryTarget`. Confirmed as a deliberate v1 boundary by the in-code comments on `GraphWorkflowStateMachine.cs` and `GraphWorkflowDispatcher.cs`. |
| Dynamic materialization / decomposition (O5) | Not part of the 2026-09-03 assessment's v1 vocabulary. The earlier Dev Workflow platform ruling O1 (2026-08-27, re-cited by that assessment) treats O5 as the axis that "alone decides" MAF Workflows cannot be the backbone: a `WorkflowBuilder` graph is build-once, so expanding it means constructing a new builder and starting a fresh run, at which point the checkpoint's `IsMatch` fails against the new topology and prior state cannot be carried over — so the Dev Workflow module built its own decomposition instead. Graph Workflows' brief scopes decomposition out of v1 entirely. O1's premise is version-pinned: `docs/agent-knowledge.md` §4 requires re-running its axes on any `Microsoft.Agents.AI.Workflows` bump. |
| `DevTask` node kind (hash-locked apply-gate integration) | The 2026-09-03 assessment found no reusable seam: `DevWorkflowNodeType.Tool` is sandboxed repo validation/apply commands (`DevWorkflowToolExecutor`), there is no "invoke tool by name" service in production, and the only precedent is Training's internal `HeadlessToolExecutor` — so Dev Mode's apply-gate machinery is Dev Mode-specific, not portable, and Graph Workflows got a new `IToolInvocationService` seam instead. Operator ruling D6(a)'s vocabulary is `Start, Agent, Tool, Condition, Parallel, Join, Pause, End`, with no `DevTask`; `GraphWorkflowNodeKind` enumerates exactly those eight. |
| Agent nodes on Work Sessions (stepwise, resumable) | Operator ruling D3, 2026-09-03, chose the headless `RuntimePackage → IInvocationRunner` stack — one turn per node run, unattended semantics already proven by the scheduler, structured output available, no session ceremony — explicitly over the rejected alternative, "Work Sessions like Dev Workflows (stepwise, resumable, transcript; no structured output; heavier; external-integrations deferred this path for the same reason)". |
| Tool node = sandboxed repo shell commands | Same ASSESSMENT §2/§10 D6: Graph Workflows' Tool node is a named-tool-by-id invocation (`IToolInvocationService`), not a repository command runner; the report calls Dev Mode's `DevelopmentValidationRunner` "welded to the Dev Mode task machine" and explicitly not reusable. |
| Shipped-off-by-default posture | Operator ruling D9, 2026-09-03: "ship gated off, flip in S4" — Graph Workflows started with the same `Enabled=false` posture Dev Workflows still has today, and only flipped to `true` once its own S4 parity slice landed; this is a *timing* difference, not an unexamined one. |

## 3. Unintentional gaps (candidates for convergence)

None of these were named as a decision in either plan set; each is a difference in fact with no recorded reason.

| Gap | Cost guess | Note |
|---|---|---|
| Restart resume fidelity: Dev Workflows resumes an interrupted Agent node run from its work session's own checkpoint at no attempt cost; Graph Workflows fails an interrupted Agent/Tool node run outright and pays a full retry attempt to recover | M | Direct consequence of the D3 execution-stack choice (headless runner has no durable handle), not itself examined as a cost. The *chat* path's version of the same asymmetry was found to be "unstated as a decision" by the 2026-09-06 MAF best-practice review (F4) and is now recorded in `docs/agent-knowledge.md` §4 — the `PendingToolCallRegistry` / `NodeChatRestartRecoveryService` entry, accepted product behaviour by operator ruling, ledger D5. The workflow-engine instance of it is the same shape and was not separately weighed. |
| Fewer conflict-exception discriminators on `IGraphWorkflowRunService` (one merged `GraphWorkflowRunConflictException` vs Dev Workflows' three distinct 409 types) | S | A caller cannot distinguish "stale definition version" from "run already terminal" without parsing the message; Dev Workflows made that a type-level distinction on purpose. No plan discusses whether Graph Workflows' merge was a simplification or an oversight. |
| No sandbox/tool-node concurrency option on `GraphWorkflowOptions` corresponding to `MaxParallelToolNodes` | S | Currently moot because v1 Tool nodes are `ReadLocal`-only and launch no processes; becomes live the moment Tool-node scope widens past `ReadLocal` (a widening the ASSESSMENT §8 D6(b) already anticipates as a future decision), and nothing today reserves the option shape for it. |
| No `RequestChanges`-equivalent decision on a Graph Workflows `Pause` node | S | Dev Workflows' `HumanGate` supports three gate outcomes; Graph Workflows' `Pause` supports two (`Approve`/`Reject`). Not discussed in either plan as a deliberate narrowing — it may simply be that no v1 template needed the third outcome yet. |
| Divergent hub-kind and event-log field naming conventions, independently implemented rather than sharing a contract | S | The 2026-09-03 assessment already anticipated this in its layer review: "the 'General Graph Concepts' layer should be a **contract** (JSON schema conventions, operator vocabulary, status names) shared by convention, not a shared assembly, until both engines are stable" — the convention exists in intent but nothing enforces it, so a future field rename in one hub has no cross-check against the other. |

## 4. Deliberately shared (with authority)

## 5. The agent-knowledge rule this register backs

`docs/agent-knowledge.md` §4, "A fix in one workflow engine is not automatically engine-local", is the durable
rule; this page is the evidence it points at. Read that entry before changing behavior in either engine.

## 6. Addendum: adjacent divergence outside this register's pair (OPEN)

Development Mode is neither of the two engines compared above, so this sits outside §1–§4. It is recorded here because it is the same shape of unexamined engine duplication the register exists to surface, and because the decision about it is still open. Same ungoverned-gap shape as §3.

| Gap | Cost guess | Note |
|---|---|---|
| `DevelopmentCoderModel.RunAsync` (`Services/Development/`) drives `IChatClient.GetStreamingResponseAsync` directly, with a hand-built `ChatOptions` tool set (its private `ToolGateway`, wrapped per tool in `AIFunctionFactory.Create`) and its own `ProviderCallBudget` scope — a second tool-invocation stack beside the shared `IInvocationRunner` that chat (`NodeChatStreamService`), Work Sessions (whose step loop drains that same chat stream service), Graph Workflows' Agent nodes (`GraphWorkflowAgentExecutor`), scheduler `run-agent` (`RunSavedAgentHandler`), External Integrations (`IntegrationExecutionCoordinator`) and Benchmarks (`BenchmarkRunExecutor` / `BenchmarkJudgeExecutor` / `BenchmarkComparisonExecutor`) all route through. | L | **Undecided — recorded, not ruled.** The duplication is real, and a migration would be a re-architecture rather than a rename: the loop's gateway carries Dev Mode-specific pieces, including a cloud-only `submit_cloud_implementation` submission and the hash-locked apply-gate machinery §2 already records as non-portable. The 2026-09 feature audit's recommendation — a recommendation, not an owner ruling — is to **leave as is**. Treat this row as a fact about the code, not as sanctioned target architecture; revisit when a change would otherwise have to be made in both stacks. |
