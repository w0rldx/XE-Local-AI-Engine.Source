# API Surface & Realtime Hubs

> Reviewed: 2026-09-15 · Code-grounded.

This page documents the **Node Web Server transport layer**: the HTTP API exposed under `/api/local/v1` (FastEndpoints), the unconditional SignalR push/stream hubs plus the conditional Development hub, the cross-cutting transport concerns (security middleware, exception handling, health checks, auth), and how the backend's OpenAPI document becomes the single source of truth for every React REST client via hey-api.

If you are adding or changing an endpoint or hub, this is the page that tells you *where the route lives, how it is secured, and what regen step you must run for the React client to see it*.

---

## Big picture

```
 Browser (React SPA, same origin)
        │  HTTP /api/local/v1/*  (FastEndpoints)
        │  SignalR hubs (all but one unconditional)
        ▼
 ┌───────────────────────────────────────────────────────────────────────┐
 │ Node Web Server  (XE-Local-AI-Engine.Client)                          │
 │  • UseExceptionHandler  → IExceptionHandler chain → RFC7807           │
 │  • UseAntiforgery / UseStaticFiles                                    │
 │  • MapHealthChecks /health/live  /health/ready                        │
 │  • LocalApiSecurityMiddleware (loopback peer + Host/Origin guard)     │
 │  • UseRouting / UseRateLimiter                                        │
 │  • UseAuthentication / UseAuthorization (JWT bearer, Operator policy) │
 │  • UseFastEndpoints (RoutePrefix = api/local/v1)                      │
 │  • MapHub × N (see Program.cs), plus DevelopmentAttemptHub when       │
 │    Development is enabled                                             │
 │  • (non-Production) OpenAPI JSON + /scalar                            │
 │  • MapFallbackToFile("index.html")  (serves the React build)         │
 └───────────────────────────────────────────────────────────────────────┘
```

**Text fallback:** there is one transport direction — **inbound, browser → node**: the local management
API and local hubs, loopback/local-only, authenticated as the node *operator*, secret-redacted. This is
everything under `/api/local/v1`. The node holds no outbound control connection; see
[Security & Privacy](12-security-and-privacy.md) for the full invariant.

The middleware/mapping order above is authoritative — see `XE-Local-AI-Engine.Client/Program.cs`, from the `app.UseExceptionHandler()` call through `app.MapFallbackToFile("index.html")`.

## 1. The inbound HTTP API (FastEndpoints)

### Conventions

- **Framework:** FastEndpoints. One endpoint = one `*Endpoint.cs` class; request/response shapes live in `*EndpointDtos.cs`, FluentValidation rules in `V1/Validators/`, and entity↔DTO mapping in `Mappers/`.
- **A request-shape check belongs in the validator, not the handler.** Required, length, range, enum-membership and format checks over the request's own fields go in a `Validator<TRequest>` under `V1/Validators/`; the handler keeps only what needs a service or the database. Moving one is not free, though: the validator runs before the handler and, by default, reports every failure at once, so a handler that returned on the first failure needs `ClassLevelCascadeMode = CascadeMode.Stop` (or `.Cascade(CascadeMode.Stop)` on the rule) to keep answering with the same single error, and a handler that used the unkeyed `AddError(message)` needs the failure reported under the general-errors field rather than the property. Running earlier also decides more: a check that used to sit behind a lookup now pre-empts the 404/409/403 that lookup answered, so only a check that was already the handler's first statement moves unchanged. The rule must judge the exact string the handler goes on to use — decode, trim and case-fold all sit between what was bound and what is used — and it must not change the OpenAPI document; see the two schema bullets below.
- **Route prefix:** every endpoint is mounted under `api/local/v1` via `config.Endpoints.RoutePrefix = LocalApiRoutes.Prefix` in `XE-Local-AI-Engine.Client/Program.cs`; the value is `LocalApiRoutes.Prefix` in `Endpoints/Common/LocalApiRoutes.cs`.
- **Routes are centralized**, not string-literal'd per endpoint. Every route and hub path is a
  `public const string` on a nested route-family class in
  `XE-Local-AI-Engine.Client/Endpoints/Common/LocalApiRoutes.cs` (for example,
  `LocalApiRoutes.Scheduler.JobById`), alongside `Prefix`. That file is the inventory — read it rather
  than a count here, which drifts every time a family lands. Change a path there and both the endpoint
  and any `Send.CreatedAtAsync<TEndpoint>()` location resolution follow.
- **operationId = camelCased class name.** The global `NameGenerator` in `Program.cs` strips the `Endpoint` suffix and lowercases the first char: `CreateScheduledJobEndpoint` → `createScheduledJob`. These operationIds are what the hey-api React SDK function names are derived from, so **the C# class name is the public contract name** — rename with care.
- **Errors → ProblemDetails.** `config.Errors.UseProblemDetails()` in `Program.cs` turns validation failures into RFC7807. Domain exceptions are handled by the `IExceptionHandler` chain (see §4). Note that not every non-2xx is ProblemDetails: several families answer a **typed domain object** instead (the source-build `409` is the notable one — see §1 design notes).
- **Desktop-only endpoints.** The `config.Endpoints.Filter` configured in `Program.cs` drops any endpoint implementing `IDesktopOnlyEndpoint` unless the host launched in desktop mode. The `app-update/*` family and Custom Tools executable probe use it, so those endpoints are absent from a headless OpenAPI regen.
- **A `{modelName}` route segment must be decoded before it is validated.** The React client's hey-api path serializer escapes the segment with `encodeURIComponent`, so a Hugging Face reference such as `hf.co/unsloth/gemma-4-12b-it-GGUF:UD-Q4_K_XL` reaches the server as `hf.co%2Funsloth%2Fgemma-4-12b-it-GGUF%3AUD-Q4_K_XL`. Kestrel's route binding decodes most percent-octets (`%3A` becomes `:`) but, by security design, leaves encoded slashes (`%2F`) and backslashes (`%5C`) **encoded**, to defeat path-segment smuggling. The endpoint therefore receives a value still containing a literal `%2F`, whose `%` fails `ModelNameValidator` and surfaces as "Invalid model identifier", while a plain tag like `llama3:8b` arrives fully decoded and passes. `Endpoints/LocalModels/V1/ModelRouteName.Decode` restores the canonical name before validation and before the service call; the validator's own path-traversal and scheme guards still run after it.
- **A validator condition is CHAINED, never blocked.** `RuleFor(x => x.Title).NotEmpty().MaximumLength(n).When(...)` sets the per-component condition FastEndpoints' schema processor reads, so the member stays optional in the OpenAPI document. The block form — `When(pred, () => { … })` — applies the same rules at runtime but leaves the components unconditional, and the processor then emits an OPTIONAL member as **required** on the wire, which the generated client encodes as a contract lie. The chained form loses nothing: a condition at the end of a chain covers every validator before it, because `ApplyConditionTo.AllValidators` is FluentValidation's default. This is why the PATCH validators in `Endpoints/DevelopmentWorkflows/V1/Validators/` spell it that way.
  - **Chaining is not always enough — a conditional rule on an OPTIONAL member belongs on the request object.** The processor lifts any *property* rule into the schema, so the block form published `CreateTranscriptionSessionRequest.languageOverride` as `required`, and switching to the chained `.When(...)` dropped the requiredness but still published `minLength: 2`. Either way the generated client refused every `languageMode: "auto"` create before the request left the browser — a break no backend test can see, because the server answers correctly throughout. `RuleFor(request => request)` has no property to attach to, so nothing about it reaches the schema; `CreateTranscriptionSessionRequestValidator` is the worked example.
  - **A check moved out of a handler must not arrive as a new schema constraint.** The same processor reads the moved rule, so a handler's `string.IsNullOrWhiteSpace` guard rewritten as `NotEmpty()` publishes `minLength: 1` and `required` on a member the wire contract never required, and the generated client then refuses the request before it leaves the browser. `Must(...)`/`Custom(...)` state the same condition and reach no schema at all, which is why `SaveTutorialStateRequestValidator` spells the required-key rule that way. Prove it per move: regenerate the spec from the built host and compare it to `openapi/v1.json` — `pnpm run openapi:check` regenerates from the COMMITTED spec and cannot see a backend-side change.

Nothing on this surface carries a host path. **Never model-reachable**: no `[McpServerTool]` and no `IClientLocalToolHandler` names `INodePatchApplyService`, which `HostPatchApplyReachArchitectureTests` pins | [Agent Mode](04-agent-mode.md), [Security & Privacy](12-security-and-privacy.md) |
| **Automation** (`automation/*`) | `automation/commands`, `automation/commands/{commandId}` | [React Client](10-react-client.md) |

Ships gated OFF: `ExternalApps:Enabled` defaults to `false` and the request-path middleware in `Program` answers 404 for the whole family — the hub's negotiate included — ahead of the security middleware, so the switch cannot be probed by status code | [External Apps](23-external-apps.md) |

> **Endpoints are orchestration-only.** They validate input, call a service in `XE-Local-AI-Engine.Client.Application/Services/*`, and map to a DTO. Business logic does not live in the endpoint. When tracing a route, jump straight to the matching service area.

### Inbound MCP scopes and registered tools

`POST mcp/server-key` accepts an optional JSON body whose `scope` is `delegate` or `agentic`; the
historical body-less form remains `delegate`. One singleton row is replaced atomically, so rotation
has no dual-valid window. Authentication emits the bounded `xe:mcp_scope` and
`xe:mcp_key_prefix` claims. SDK authorization filters apply `McpServer` to the eight shared
`NodeAgentMcpTools` and `McpAgentic` to the admin tools declared across the `NodeAdminMcpTools`
partials, so `tools/list` returns the eight shared tools for a `delegate` key and those eight plus
every admin tool for an `agentic` key. The admin set is enumerated — and drift-tested — in
[`references/mcp-tools.md`](../../skills/xe-local-ai-engine/references/mcp-tools.md); no other page
restates it. Direct calls to unauthorized admin tools are rejected too.

The admin class calls application services directly — no internal HTTP hop — for node/runtime
status, runtime acquisition, GGUF pull lifecycle, model delete/default selection, the exact 18-field
node-settings whitelist, and saved-agent CRUD. The canonical names and inputs are drift-tested
against [`references/mcp-tools.md`](../../skills/xe-local-ai-engine/references/mcp-tools.md).

### Design notes on the newer endpoint families

- **Inference optimizer profiles (`model-fit/profiles*`).** The collection `GET model-fit/profiles` lists every persisted node-local profile (machine key omitted). The four actions — `explore`, `benchmark`, `freeze`, `invalidate` — are all **POST with the target carried in the body**, never a route param, so the POST always has a body. The literal action segments follow `profiles`, so none can be parsed as a profile id. `benchmark` is the gate for `freeze` (a profile can only be frozen after a successful benchmark). See `Endpoints/ModelFit/V1/{Explore,Benchmark,Freeze,Invalidate}InferenceProfileEndpoint.cs` + `ListInferenceProfilesEndpoint.cs`; runtime side in [Local Runtime & Providers](03-local-runtime-and-providers.md).
- **Runtime acquisition (`model-fit/llamacpp/acquisition`).** `GetRuntimeAcquisitionStatusEndpoint` exposes the latest in-memory snapshot from `IRuntimeAcquisitionStatusRegistry`. `RuntimeAcquisitionHub` pushes the same sequence-numbered status during the host's automatic llama.cpp acquisition. React hydrates the query first, merges pushes by highest sequence, and invalidates after reconnect so a client that authenticates after startup or misses a terminal push still converges on the canonical status. The read exists because acquisition starts within seconds of boot, very likely before the React app has authenticated and opened its hub connection — without it the banner would never appear for precisely the slow-first-run case the channel exists to explain. No log body is exposed; the payload is phase/variant/tag, byte and step counters, and a sanitized error.
- **Custom Tools (`custom-tools/*`).** Five Operator-gated CRUD endpoints manage HTTP-fetch or host-program definitions through `ICustomToolService`; `ValidateExecutableEndpoint` is desktop-only and probes one supplied absolute path with the same `HostExecutableGuard` used at execution. Read DTOs mask secret header/environment values, and masked values round-trip without overwriting stored secrets. A tool is offered only when enabled, explicitly acknowledged, and allowed by the node-level `CustomToolsEnabled` switch; every resolved tool is unconditionally approval-wrapped. Execution controls and residual trust are documented in [Security & Privacy](12-security-and-privacy.md#custom-tools-operator-authored-execution-boundary).
- **Chat file uploads (`chat/conversations/{id}/uploads`).** `UploadConversationFileEndpoint.Configure()` calls `AllowFileUploads()` and binds an `IFormFile`, enforcing the size cap + extension allowlist and sanitizing the client name to a leaf. List is a plain GET; delete is `DELETE .../uploads/{fileId}` keyed on the server-generated file id. See [Chat](05-chat.md).
- **Locked-out login → coded `401` (`auth/login`).** A wrong password answers a body-less `401`; an account ASP.NET Identity has locked (`MaxFailedAccessAttempts = 5`, `DefaultLockoutTimeSpan = 5 min`) answers `401` with `{"message", "code": "locked-out", "retryAfterSeconds"}` plus a matching `Retry-After` header, so the operator holding the *correct* password learns that waiting is the fix instead of re-reading "incorrect password". This deliberately reveals that an email exists once five attempts have been spent — an accepted trade-off on a loopback-only node whose login is additionally bounded by the 10 requests/minute per-IP throttle (`NodeAuthRateLimits.AuthPolicy`); the throttle's own `429` is unchanged. The seconds come from `UserManager.GetLockoutEndDateAsync`, floored at one. See `NodeAuthService.LoginAsync` and `NodeAuthEndpointSupport.SendTokenResultAsync`.
- **Body-less POST (415) override.** Route-only POST actions whose id binds from the route (e.g. scheduler `trigger`/`enable`/`disable`, run `cancel`) send no body and therefore no `Content-Type`; FastEndpoints' default `Accepts` metadata answers that with **415**. Those endpoints override it with `Description(x => x.Accepts<T>())`; see `TriggerScheduledJobEndpoint.Configure()`. See [Scheduler](06-scheduler.md).
- **Run-envelope lifecycle records (`GET agents/run-envelopes`).** Read-only, **operator-gated**, metadata-only projection of the durable per-invocation run envelopes (`ListRunEnvelopesEndpoint`). Newest-first, paged (`limit` default 50 / max 200, `offset`), optionally scoped by `conversationId`. The store holds no message content — only terminal status, usage/timing counters, correlation + trace ids — so there is nothing to redact, and `FailureCategory` is a category enum name only. See the shared `agent_execution_logs` schema in [Data & Persistence](08-data-and-persistence.md). This endpoint (plus `GET agents/{agentDefinitionId}/execution-logs`) is also the durable, no-live-collector-needed path for incident diagnosis — see the [OTel export operator runbook](../runbooks/otel-export-operator-runbook.md) for how it complements (and doesn't depend on) OpenTelemetry export.
- **Source-build start → typed `409`, not ProblemDetails (`model-fit/llamacpp/source-build`).** `StartLlamaCppSourceBuildEndpoint` answers a blocked start with `Results.Conflict(new LlamaCppSourceBuildBlockedResponse { Reason, Message, RunningProcessCount })` — a **domain object**, so `ProblemDetails.detail`/`title` are absent. The machine-readable `reason` is one of `not-linux`, `already-building`, `disk`, `prerequisites`, `processes-running`, `runtime-busy`. Two consequences a maintainer must respect: (1) the endpoint must **not** re-normalize the request — the service is the single normalization point, and a second pass over an already-normalized official-source request used to be rejected by the strict "the official repository is selected by the server" rule, 409-ing every official build (`2cab52ec`); (2) the React `ApiError` resolves `detail → message → title` so this body's `message` surfaces in a toast instead of rendering an empty notification. Runtime side: [Local Runtime & Providers](03-local-runtime-and-providers.md#26-in-app-source-builds-linux).
  - **The family's shape.** `…/source-build/prerequisites` reports the itemized toolchain checklist on **any** OS — a non-Linux host answers it with "cannot build" rather than 404ing, so the UI can explain the platform instead of hiding the feature. The build action itself is gated server-side on exactly what the six `reason` values above name (Linux, prerequisites, disk, eject-first, single-flight), and `…/status`, `…/cancel` and `…/remove` drive the in-flight build and the adopted managed runtime. `SourceBuildHub` pushes the phase plus the newly appended log lines. The literal `source-build` segments follow `llamacpp`, so none of them collides with the `version` / `runtime` / `update` routes beside them.
- **Image-runtime source-build conflicts (`images/runtime/source-build`).** The image build family uses the same typed
  `409` transport shape. Admission outcomes use `not-linux`, `already-building`, `prerequisites`, or `runtime-busy`;
  unexpected lifecycle/recovery exceptions use `source-build-error`, never the misleading
  `prerequisites`. Build/remove stay blocked while an image job, spawn/readiness lease, or resident process exists;
  `POST images/runtime/eject` is the operator recovery action before retrying the mutation. See
  [Image Generation](14-image-generation.md).
- **External Apps (`external-apps/*`) — a 202 carries the ADMITTED row, never the outcome.** Install, update, start, stop, restart and reset admit *synchronously* — validate, gate, create or move the row, append the event — and hand the container work to the operation runner, so the awaited task completes in milliseconds even when the image pull behind it runs for minutes. The 202 body is `ExternalAppInstanceSummaryView`, the snapshot as admission left it, which is why its status set carries the transient `Starting`/`Stopping`/`Updating`/`Resetting` values: re-reading the instance to fill a manifest into that body would return a row a concurrent operation may already have moved. No endpoint awaits completion or polls, and the request's own token covers the admission only, so a disconnecting browser cancels nothing — `ExternalAppInstanceHub` (§2) carries the rest. `POST …/cancel` is the exception that answers **202 with no body at all**: the cancellation is a request to the running operation, which settles through its own `finally`, so a row read there would be neither the outcome nor the admission, and the hub ping carries the settled state.
  - **`expectedVersion` is the whole concurrency mechanism.** The four lifecycle verbs send it in the body, uninstall's rides the **query** (a DELETE body is awkward on every layer that touches it and intermediaries may drop it), and cancel is the one command that takes none — it names no target state, and requiring the operator's tab to be current before it can stop a runaway pull would defeat the point. It is `long?` plus a `NotNull` rule rather than `required long`, because a required value type does not establish presence: an omitted member would bind to 0 and a client that forgot the guard would be treated as one that supplied it. A stale value is a 409 `ExternalAppVersionConflict`. There are no idempotency keys in V1.
  - **Acceptance binds to the fingerprint, not the version number.** Install and update echo the `manifestSha256` their preview returned; a catalog that republishes v3 with a wider `capAdd` keeps its version number but produces a different sha, and the command answers 409 `ExternalAppManifestChanged` rather than installing something the operator never read. The permission diff the server refuses an update with is **per service** — a capability moved from one service to another is a widening the union cannot see — so `acceptPermissions` is a boolean the server owns rather than a list the client could get wrong.
  - **`POST …/runtime/refresh` is a POST because it can pin a daemon.** A refresh, a prefetch or a health check must not be able to approve a daemon identity change, and `acknowledgeDaemonId` is never a blind approval: the endpoint re-probes first and compares the id against the observed one, answering 400 on a mismatch, so a client echoing the last id it rendered cannot approve whatever daemon is answering now. After a preflight that comes back ready it reconciles, making "approve the daemon and recover the rows still transient after boot" one operator action rather than a restart; the reconciler skips any instance with an operation in flight, so a refresh during an install cannot disturb it. The plain `GET …/runtime` never pins and never reconciles, which is why its `foreignInstallContainers` is 0 — that count is the reconciler's observation, and reporting a cached one as fresh would tell the operator a foreign container is there when it is not.

- **Development Mode (`development/*`).** Twenty-one Operator-gated endpoints sit under `Endpoints/Development/V1/`, one `*DevelopmentEndpoint.cs` file per endpoint class, covering the capability, repository, template, project, task, artifact, event and patch route families. `development/capability` is the deliberate exception to the disabled-mode 404 sweep: it stays reachable so the SPA can resolve whether the capability exists rather than guessing from a 404. The write path is two-phase — `.../tasks/{taskId}/preview` produces a patch bound to the expected base commit and evidence hashes, `.../tasks/{taskId}/apply` revalidates those values before mutating the registered source repository. Live attempt output does not stream over HTTP; it goes over `DevelopmentAttemptHub` (§2). An attempt that ends without a verdict carries a `terminalReason`, which the React feature renders — so a failed attempt names *why* it stopped instead of presenting an empty result. Three ADRs record the decisions behind the restart-recovery, cloud-egress and container-execution behavior: [ADR 0001 — restart recovery uses replacement attempts](../adr/0001-development-mode-restart-recovery.md), [ADR 0002 — cloud authorization uses `ChatOptions.AdditionalProperties`](../adr/0002-development-cloud-egress-carrier.md), and [ADR 0004 — Development Mode container execution](../adr/0004-development-mode-container-execution-docker-stopgap.md) (whose implementation status lives on [Development Mode container implementation status](../roadmaps/development-mode-container-status.md)).
- **Development workflow graphs — four save-time capability invariants (`development-workflows/definitions/{id}`).** `PUT` parses the graph through the same `DevWorkflowGraph.Parse` the dispatcher routes with, so an invariant refusal is a **400** whose message names the rule id the operator quotes. The effect model underneath is one enum, `DevWorkflowNodeEffect` (`ReadLocal`, `WriteExecute`, `Orchestration`, `Network`) plus a derived scope (`Sandbox` for a `DevTask`, `Repository` for everything else): **declared** on an Agent node through `requiredCapabilities` — an object of effect ⇒ the author's one-line reason, bounded at 200 characters and refused on any other node type — and **derived** everywhere else, because every other node type says what it does in the node itself. The four rules:
  - **`GRAPH-C4-1`** — every path reaches an end of the run, over the edges a run can TAKE. A human-gate out-edge that fires for none of `Approve`/`Reject`/`RequestChanges` is dead (`{"path":"decision","op":"eq","value":"Approved"}` — the past participle — validates and never fires), and the message names the gate that OWNS the dead edge before it names anything the dead edge stranded. Its fourth step is about materialization: a `Tool`/`Validate` node inside a template subtree needs an out-edge, because D12's verdict row lands under that key and a template leaf is otherwise an end of the run. It stops there deliberately — no row is ever written under a `DevTask` or `Agent` template key. Two further structural rules make the shared fixpoint answerable at all: the AUGMENTED graph (authored edges plus one virtual edge per materializer to its template root) must be acyclic, which a single-materializer rule cannot see, and each template node has exactly one materializer owner, since two would both seed its verdict row.
  - **`GRAPH-C4-2`** — a node that writes outside its sandbox is reached through a human gate on *every* path, waived only by the graph's own `allowUngatedWrites`. Its runtime half is asked of the resolver's effective tool projection rather than of a re-derived `offer ∩ allowedToolNames` — once before the session is created, and then again on **every turn** the session takes, because the agent definition it judges is mutable: edit one between two steps to add a write tool, or delete one so the turn falls back to the default persona, and a one-time check would have judged neither. The node's declaration and the template's waiver ride on `WorkSessionRuntimeOverride.RefuseUndeclaredWrites`, re-supplied off the run's pinned graph on every start and resume; a refused turn fails the session, and the run's poll blocks the node run with failure class `Policy`.
  - **`GRAPH-C4-3`** — an apply node (`toolMode: "Apply"`) follows a `Tool`/`Validate` node on every path. The dispatcher re-asks it of the rows a run actually landed, before an apply records that it consumed anything.
  - **`GRAPH-C4-4`** — a node's `maxLoopIterations` bounds its own fix loop, counted as attempts minus operator `Retry` decisions and blocked with `BudgetExhausted`.
  Three rulings are worth knowing before changing any of this. **D8**: a `DevTask`'s write is sandbox-scoped — its patch reaches a real repository only through an apply node a gate already stands in front of — so it is not what C4-2 is about. **D9**: an absent `maxLoopIterations` means NO cap, never a default, or every already-stored definition would tighten at the next run start. **D12**: a decomposition that finds no work seeds one already-`Succeeded` row per `Tool`/`Validate` node of its template subtree, carrying the verdict `validation-not-applicable` — a uniform invariant rather than an exemption for the empty package — and the node-run summary carries `validationNotApplicable` so the run header does not count it as work done. Both invariant halves live in `Client.Application/Services/DevWorkflows/`; the browser mirrors the four rules in `DevWorkflowDefinitionValidation.ts`.
- **Development workflows — the endpoints' two doors onto the store (endpoint-dependency rule).** No endpoint on this family takes `IDevWorkflowStore`. `Client.Application/Services/DevWorkflows/DevWorkflowAuthoringService.cs` is a pass-through for the operator-authored rows — definitions, rule sets and work items — and `DevWorkflowRunQueryService.cs` a read-only one for the run feeds (run summaries, the run row, the event log, the artifact list and one artifact's record). Both are concrete `sealed class`es registered as themselves, `AddScoped` like the store they front; neither adds policy, so graph validation, the request-size refusal, the status-filter parse, the read-the-run-first 404, the one-over-the-limit probe and the artifact ownership and size checks all stay in the endpoints. Everything that MOVES a run — start, pause, resume, cancel, the human decision, the work-item delete — goes through `IDevWorkflowRunService` instead, and the composed run detail through `DevWorkflowRunComposer`.
- **Development workflows — what the run-detail response derives server-side (`DevWorkflowRunComposer`).** Run detail is THE repaint fetch, so the composer is written to a fixed query budget — the run and its node runs, the definition names, the agent definitions and the artifact rows — never a per-node query, which would be an N+1 on the one request a live view repeats. Each field below is computed once on the server, because re-deriving join or state-machine semantics in the browser would duplicate the dispatcher's own evaluation and drift from it.
  - **Materialization counts** are taken over the run's WHOLE node-run list and over distinct `MaterializationIndex` values, not over rows: a client counting the rows it drew is wrong by construction for a fan-out wider than its page, and a template subtree of more than one node clones every one of them per child, so counting rows would read a two-child fan-out of a two-node template as "1 of 4".
  - **`skipWaived`** is the state machine's own verdict on a skipped row: a skip a person chose is waived and a join carries on past it, one that cascaded off something dead is not. A client cannot tell them apart, because the ancestor that decides it need not be among the join's own dependencies. Only a `Skipped` row has a verdict, and a run whose pinned graph could not be parsed has none — both read as `null`, which the client renders as a skip it makes no claim about rather than as a dead one.
  - **`operatorRetries`** is the distance the node run's own `MaxAttempts` has travelled from the cap its definition declared, which each `Retry` raises by one IN PLACE; the client subtracts it to recover the declared cap. It is read off the row, never counted from `Retry` decision rows: such a row exists whether or not it was ever applied, so counting them reports a widening for the settle window between recording a `Retry` and the dispatcher spending it — which a PAUSED run holds open indefinitely — and for any node run whose `Retry` rows moved no cap at all, both rendering a cap one below the definition's. A MATERIALIZED clone is looked up by its own key and needs no template hop, because the materializer DEEP-CLONES the template node into the graph's node array, rewriting only `nodeKey` and `retryTarget`, and the expansion is written back to `run.GraphJson` under a bumped revision — so the pinned graph a run detail reads declares every clone key, carrying the template's own `maxAttempts`. Floored at zero, and zero for a node key the pinned graph does not declare (an unroutable graph, which `DevWorkflowGraphContract.DeclaredMaxAttempts` answers empty for): nothing to compare against is not evidence of a widening.
  - **`waitingOnNodeKeys`** names the upstream nodes a `Pending` node run is still waiting on. Only `Pending` carries it — `Blocked` means a human is the dependency. A source that has SETTLED is never waited on, whichever way it settled, which is the same answer the dispatcher's edge rule gives for a branch whose condition did not fire, and is why an `Any` join needs no case of its own: it too waits exactly while an inbound edge is undecided. The one edge that needs saying out loud is a materialization TEMPLATE's — it never gets a row, so it can never settle, and naming it would show every decomposing run as stuck on the one node nothing ever runs.
  - **`modelLabel`** is the node's own `modelProfile` when it authored one — that is the pin the work session is created and resumed with — and the bound agent's otherwise. It is `null` when neither pins anything, because the session then takes the node's default chat model, a live setting this pane has no business naming as if the run had chosen it. The authored pin counts only on an AGENT node run, the one lane that dispatches on it: a Tool or DevTask node carrying the field runs on neither, since Dev Mode's coder resolves its own, so naming it there would be a false label. Only the PINNED half is stable — the node comes from the run's own graph snapshot, so a definition edit cannot change it — while the fallback is the agent definition as it stands NOW, so a node that pinned nothing re-labels when its agent is repointed, the same live read every other agent field on this response makes. The label is trimmed, because the parser trims before it pins: labelling `" qwen "` for a session dispatched on `"qwen"` would make the pane disagree with the run over whitespace.
  - **Stale inputs** name the node runs that consumed an artifact since superseded. Staleness is written today by the two callers that supersede an artifact — an agent-node promotion and a Tool node's report, both through `MarkDependentsStaleAsync` — so the field answers a real question rather than a reserved one. It is still "none" for most runs and costs one artifact read to say so; the per-node read only happens once a stale row actually exists.
  - **Applied rule sets** are read from the record written at materialization, never re-resolved: re-resolving would answer "what would apply now", a different and misleading question in an audit view. The CURRENT hash of each named rule set rides alongside it, so a reader can tell an unchanged document from one edited since the node ran, and both from one deleted, which reads as a null current hash. This and the stored route are both parsed through the runtime's own tolerant reader — an unreadable column is a hand-edited row, and it costs that node its rule-set list or its route rather than costing the whole drill-down a 500.
- **Inbound model proxy (`proxy/*`) — hand-mapped, off the OpenAPI document.** `proxy/key` is an ordinary Operator-gated FastEndpoints family (`GetLocalModelProxyApiKeyEndpoint` / `GenerateLocalModelProxyApiKeyEndpoint` / `RevokeLocalModelProxyApiKeyEndpoint`); the OpenAI-compatible passthrough is not. `app.MapGet`/`MapPost` in `Program.cs` wire `proxy/v1/models`, `proxy/v1/chat/completions` and `proxy/v1/embeddings` to `LocalModelProxyForwarder` for two load-bearing reasons stated in the source: the paths sit **inside** `/api/local/v1` so `LocalApiSecurityMiddleware`'s loopback peer + Host + Origin gate still covers them (moving them out would silently drop that layer and leave the bearer key as the only control), and the request/response is arbitrary OpenAI JSON + SSE rather than a node DTO, so it must not appear in the OpenAPI document or the generated React SDK. Chat completions and embeddings are forwarded verbatim to the resolved `llama-server` child; `proxy/v1/models` is **synthesized** from the local GGUF catalog, because a child only knows the one model it loaded. Every one of the three requires `NodeAuthorizationPolicies.LocalModelProxy`, which accepts **only** the model-proxy API key scheme — never the operator's JWT and never the MCP key — and its own rate-limit policy. See [Security & Privacy](12-security-and-privacy.md).
- **External integrations (`integration-api/*`) — hand-mapped, off the OpenAPI document.** The Operator-gated `integrations/*` management family is ordinary FastEndpoints; the surface an integrator actually calls is not. `app.MapPost`/`MapGet` in `Program.cs` wire `integration-api/triggers/{triggerName}/invoke`, `integration-api/executions/{executionId}`, `integration-api/executions/{executionId}/events`, `integration-api/executions/{executionId}/cancel` and `integration-api/sessions/{sessionId}` to `IntegrationApiHandler`, for the two reasons the model proxy is mapped the same way: the paths sit **inside** `/api/local/v1`, so `LocalApiSecurityMiddleware`'s loopback peer + Host + Origin gate still covers them, and the request/response is an integration envelope a caller owns rather than a node DTO, so it must not reach the OpenAPI document or the generated React SDK. All five require `NodeAuthorizationPolicies.IntegrationApi`, which accepts **only** the `xeint_` key scheme — never the operator's JWT, the MCP key or the proxy key.
  - **A retry must resend the byte-identical body.** A request is deduplicated on `(principal, requestId)` and a SHA-256 fingerprint taken over the **raw request bytes**. Resending the same `requestId` with the same bytes returns the original execution and its 202; resending it with a body that differs by so much as whitespace, JSON property order, or a re-serialised number is a **409**, not an idempotent replay. There is no JSON canonicalisation anywhere in this feature, deliberately: canonicalising would make two requests a caller considers different look identical. A caller that builds its retry by re-serialising a parsed object should capture the bytes it sent instead.
  - **No 403 exists on this family.** A missing, malformed, unknown or **revoked** credential is the same 401 with no distinguishing body. Everything authorisation-shaped — a trigger the key may not fire, an execution owned by another integrator, an execution under a trigger the calling key is not scoped to — is a **404 byte-identical to "unknown"**, because the id is the capability and a row a caller may not see must not be confirmable. A key's trigger allowlist keeps binding after the invocation, and the key row is re-read per request, so narrowing or revoking a key takes effect on the very next call.
  - **Streaming an execution (`Accept: text/event-stream`).** Send that `Accept` on the invoke, and instead of the 202 the response is a `text/event-stream` that begins with `event: execution.accepted` at `id: 1`. Frames are `event:` / `data:` / `id:`, in that order, and a `: keepalive` comment goes out every 15 s so a silent stretch is not mistaken for a dead connection. Reattach with `GET integration-api/executions/{id}/events` and a `Last-Event-ID` header carrying the last `id:` you saw; without one the stream replays from the beginning of what the node still holds. **Every rejection happens before the stream begins**, so a 404, 409, 413, 422, 429 or 503 is always an ordinary JSON status and never a half-written stream.
    - **Not every event type appears on every run.** `execution.queued` is emitted **only** when the execution actually waits for the node's invocation lease, so a stream that goes straight from `execution.accepted` to `execution.started` is correct, not truncated. And a run that is cancelled or refused before it starts carries phase events only.
    - **A long silence is normal.** Loading a cold model produces **no event at all** — the runtime's own phase transitions map to none of the eleven types — so minutes of nothing but `: keepalive` between `execution.started` and the first `assistant.delta` is the expected shape of a first request against an unloaded model.
    - **An empty answer is an answer.** A turn the model spends entirely in reasoning streams **no** `assistant.delta` at all and ends with `assistant.completed` carrying `{"text":""}` — reasoning chunks travel their own path and map to none of the eleven types — so an empty `assistant.completed` on an execution that terminalizes `execution.completed` means the model produced no answer text, not that the stream dropped frames. Reasoning is never streamed at all, under any event type, so there is no separate frame that would explain the gap. Rely on `execution.completed` for whether the run succeeded, and — for a trigger whose agent uses the `emit_output` tool — on the `external.output` frames it produced; `assistant.completed`/`assistant.delta` are the chat transcript, not the integration's typed output channel, and an empty one is not evidence of anything going wrong.
    - **`tool.completed`'s `ok` means different things for `emit_output` than for every other tool.** The frame carries `{"name", "ok"}`. For every tool but `emit_output`, `ok` is false only when the function-invocation pipeline caught an exception. For `emit_output`, `ok` is *also* false whenever the call was refused by policy — not inside an integration execution, no running execution, unreadable arguments, a missing payload, an invalid media type, or over the per-payload or per-execution output cap — because a refusal returns a sentence rather than throwing, so the exception-only signal would otherwise report a refused call as successful. A refusal still lets the run continue; the model just reads back why. So `ok:true` on `emit_output` means, and only means, that a matching `external.output` frame was published for that call — a caller no longer has to infer a refusal from a missing frame.
    - **The concatenated `assistant.delta` text is authoritative.** `assistant.completed` is a bounded backstop for a caller that attached late; it is cut at 256 KiB, so for a long answer the two differ and a caller that reconnected past the deltas gets strictly less text than one that stayed connected. Neither assistant event is ever persisted: the final text lives on the execution's own conversation.
    - **`id:` values ascend but may skip.** A durable write that failed leaves a permanent hole, so treat `Last-Event-ID` as a **watermark** and never assert `id == previous + 1`. Frames are always delivered in ascending `id:` order; a brief pause covered only by `: keepalive` may be the node holding a frame until an earlier event's durable write resolves, which is why the ORDER is guaranteed and the timing is not. Concretely, every event type reserves its sequence, commits its row, and only then publishes; a reservation that cannot commit is **abandoned**, not retried, so a gap of exactly one — e.g. sequences 1, 2, 4 with no 3, observed on executions cancelled mid-run — means one abandoned reservation, never a lost or dropped frame. Resume must therefore be driven by the last `id:` you actually saw (send it back as `Last-Event-ID`), not by counting frames received or assuming the next id is `previous + 1`.
    - **A stream that ends without a terminal event means the node moved past your position.** Reattach with `Last-Event-ID`; that attach answers **410 Gone**, whose body names the recovery route below. A 410 on attach means the same thing: the live buffer no longer holds that position, because it was never tracked, was evicted, or has dropped past it. A **503 with `Retry-After: 5`** means too many streams are open on this node right now.
  - **Recovering after a 410 (`GET integration-api/executions/{id}/events?sinceSeq=`).** The same route, without the `text/event-stream` accept, returns the **committed** events as a JSON array in ascending `sequence`: `executionId`, `sequence`, `eventType`, `detailJson`, `occurredAtUtc`. It reads the database, so it works after a restart, after the buffer expired, and after the ring dropped the row — it never answers 410. `sinceSeq` is exclusive and is the last `sequence` you received; `limit` defaults to 200 and is clamped to 500, so a full page means "call again" and a short page means "caught up". It carries the persisted set only — the phase events, the terminal, `tool.*` and the output events — and **never** `assistant.delta` or `assistant.completed`, which are stream-only: a caller that wants the token text has to stay attached. The execution GET carries this route as `links.events` so it is discoverable without reading this page.
  - **Caller-managed sessions (`GET integration-api/sessions/{sessionId}`).** A trigger whose session policy is `CallerManaged` returns a `sessionId` on every 202; send it back on the next invoke and the run continues that session's conversation instead of starting a new one. This route reports the session: `sessionId`, `triggerName`, `status` (`active` / `closed`), `executionCount` and `lastActivityUtc`. **Its 404 is the family's masked one** — an unknown id, a session owned by a different integrator, and a session under a trigger the calling key's allowlist excludes all answer the identical body, so the route cannot be used to discover session ids. Ownership is the INTEGRATOR, not the credential: two keys minted for the same principal reach the same sessions, which is what makes a credential rotation safe, while a key narrowed to other triggers stops reaching them on its very next call. Continuing a session that is closed, that belongs to another trigger, or that already has an execution in flight answers 409 or the masked 404; the two 409 bodies carry a machine-readable `code` beside the `message` (`session-closed`, `session-busy`), while the masked 404 and the 401 stay code-free because a discriminator there would re-open the enumeration oracle; a per-invocation trigger has no addressable sessions at all, so naming one is that same 404. Any agent may host a caller-managed session (ADR 0008 R6-1): each turn's tool calls and their results are persisted as message parts and replayed to the model on the next continuation as real function call and function result content, so a continued run can tell an action it performed from prose describing one. The prior-outputs framed document remains the typed-output memory beside them. `session-policy` therefore appears only on execution rows written before that change; nothing produces it now. An operator deletes a session through `DELETE integrations/sessions/{sessionId}`, which purges its conversation and, with it, that session's executions and their events.
  - **The other answers.** 202 with an execution id on acceptance, 409 on a request-id reuse with a different body, 413 over the body cap, 422 for inputs a trigger does not accept, 429 with `Retry-After: 60` over the caller's per-principal budget, and 503 with `Retry-After: 5` when the node's admission queue is full — and a 503 writes nothing at all. Rate limiting is two layers: a coarse per-IP ceiling in the middleware, which runs before authentication and is therefore shared by every loopback caller, and the per-principal budget the handler spends after authentication, which is where fairness lives. See [Security & Privacy](12-security-and-privacy.md).
- **Training (`training/*`) — enqueue-only writes on a single-consumer queue.** `POST training/runs` and `POST training/evaluations` **enqueue**; the run starts when the node's GPU is free, so a 202-shaped create followed by hub push is the normal flow rather than a long-held request. Create-time refusals (`TrainingRunRejectedException`) are about the request itself — unconfirmed base-checkpoint licence, a missing or not-yet-ready dataset/checkpoint, a dataset with no reviewable samples — not about GPU contention (the VRAM-fit check, `TrainingCapacityGate`, runs later inside `TrainingRunExecutor` when the run is picked up): the queue consumer (`TrainingRunQueueHostedService`) is what waits for `IGpuWorkGate` exclusivity and, for training runs, for the llama.cpp runtime-mutation lease (`TryAcquireRuntimeMutationLeaseAsync`, the same eject-first `runtime-busy` vocabulary the source builds use) before it claims the next item. `training/runtime/*` manages one machine-global uv-provisioned Python venv, so none of those four routes is id-scoped. See [Training](18-training.md).
- **Busy admission → 503 + `Retry-After` (document ingestion).** The knowledge-document upload/reindex endpoints and the chat file upload each guard a bounded capacity with **non-blocking** admission: a full knowledge ingestion queue (`KnowledgeIngestionDispatcher`, bounded capacity 256) returns `QueueFull`, and the synchronous extraction gate (`DocumentExtractionAdmissionGate`, a `SemaphoreSlim`) rejects when every slot is taken — both surface as **503 Service Unavailable with `Retry-After: 5`** rather than holding the request or growing the backlog. Admission is idempotent (a document already queued/in-flight is a no-op), and a knowledge upload whose ingestion a full queue previously rejected (leaving its blob persisted-but-unindexed) is re-enqueued on a later re-upload — so a 503 is a retryable busy signal, not data loss. See [Knowledge Base](15-knowledge-base.md).

### Notable non-typed routes

**No endpoint on this surface authors SSE.** The former `models/pull` / `models/pull/stream` pair (`PullStreamLocalModelEndpoint`) is gone — model acquisition is now GGUF download under `model-fit/*` with progress pushed over `GgufDownloadHub`, and chat streaming is a SignalR streaming hub method (§2). A grep for `text/event-stream` under `XE-Local-AI-Engine.Client/` returns nothing. The one place a stream still crosses this boundary is the hand-mapped model proxy: `LocalModelProxyForwarder` reverse-proxies the caller's request verbatim to the resolved `llama-server` child and relays that child's response body (SSE included, with its upstream content type) back, bounded by an upstream-idle timeout — it neither produces nor parses the event stream.

**`/llm/v1/*` is not on this surface at all.** `/llm/v1/chat/completions`, `/llm/v1/embeddings` and `/llm/v1/models` are served only on the **container bridge listener** — the engine's one deliberately non-loopback Kestrel endpoint, mapped by `ContainerBridgePipeline.Map` before everything else in the pipeline and branched on the arrival port. They are absent from the loopback listener, absent from the OpenAPI document and absent from the generated client, because their only caller is an application container calling in with a per-instance bearer token. They reuse `LocalModelProxyForwarder`, so this is the same forwarding behaviour §`proxy/v1/*` describes, reached from a different listener under a different gate. See [ADR 0011](../adr/0011-container-bridge-listener.md) and [Security §3.5](12-security-and-privacy.md).

**The three hand-mapped inbound surfaces all sit INSIDE `/api/local/v1`, and that is load-bearing.** `MapMcp`, the OpenAI-compatible model proxy and the external integration API are mapped beside the hubs rather than as FastEndpoints endpoints, because each owns a transport or an envelope that is not a node DTO — JSON-RPC, arbitrary OpenAI JSON plus SSE, an integration envelope — so none of them may appear in the OpenAPI document or the generated React SDK; only external clients talk to them. But `LocalApiSecurityMiddleware` matches on the `/api/local/v1` prefix ALONE, so mapping any of them at a bare path (`/mcp`, say) would silently drop the loopback peer, Host and Origin gate and leave the bearer key as the only control. Do not move them out of the prefix. Each carries a policy that accepts ONLY its own key scheme, never the operator's JWT and never another surface's key, and the integration routes' route-level rate limit is the COARSE per-IP abuse ceiling — per-principal fairness is the limiter the handler consults after authentication, the only place a principal exists to partition on. The integration body cap is read from configuration at map time, because endpoint metadata is baked then and an `IOptions` instance resolved per request would be a second source that can disagree with what the route already carries.

A small set of routes is still **hand-wired on the React client rather than consumed through the generated typed SDK**, because the response is not request/response JSON or the call must run outside the SDK's auth path:

- `images/{imageId}` — fetched as a `Blob` to build an object URL (`features/images/hooks/useImageObjectUrl.ts`).
- `knowledge-base/documents` (POST) — multipart upload with progress (`features/knowledge/queries/useKnowledgeUpload.ts`).
- `auth/status|setup|login|refresh|logout` — the **one documented second axios instance** (`authClient` in `core/auth/api/NodeAuthApi.ts`). It exists precisely so the shared instance's 401-refresh interceptor cannot recurse through the refresh call itself.

Everything except `authClient` goes through the shared axios instance via `buildLocalApiUrl()`. See [React Client](10-react-client.md).

## 2. SignalR hubs (inbound, browser ↔ node)

Hub classes live in `Client/Hubs/` and every one of them is mapped by a `MapHub<>` call in `Program.cs` — that call site, not a number here, is the inventory. All are `[Authorize(AuthenticationSchemes = JwtBearer, Policy = NodeAuthorizationPolicies.Operator)]` and mapped with `.RequireAuthorization(Operator)`. Their full paths are constants (`...Hub` in `LocalApiRoutes.cs`), mapped via `MapHub` *outside* the FastEndpoints prefix.

The table below is this wiki's single enumeration of the hubs — every other page links here instead of repeating it. Every hub except one is mapped unconditionally; that one, `DevelopmentAttemptHub`, is mapped **only when Development Mode is enabled** — `isDevelopmentModeEnabled` in `Program.cs` reads `Development:Enabled` and defaults to `true` (the same default as `DevelopmentOptions.Enabled`). When it is `false` the hub is not mapped, its services are not registered, and the disabled-capability middleware in `Program.cs` answers **404** for every `/api/local/v1/development/*` path except `development/capability` — deliberately *before* local-API security or authentication can challenge the caller, so a disabled capability stays opaque.

Work sessions take the **other half** of that pattern deliberately: `WorkSessionHub` and every `work-sessions/*` route are mapped and discovered unconditionally, and only their behaviour is gated. Dropping them from discovery would drop the whole family out of the OpenAPI document and therefore out of the generated React SDK, which would make the client's surface depend on the node that produced the spec. `WorkSessions:Enabled=false` (the option default; `appsettings.json` ships `true`) instead gets the same 404 middleware ahead of authentication, and `SubscribeSession` throws a `HubException`. As with Development Mode, exactly one route is carved out of that sweep — `work-sessions/capability` — and `development-workflows/capability` is its twin on the dev-workflow gate: the 404 those blocks write has no body at all, so without a route that still answers, a client cannot tell a switched-off feature from a broken node, and both SPA pages showed a generic "could not load" on every node that had the switch off.

### Hub event-name contracts

Push hubs use **stable string constants as the SignalR client-method names**, doubling as the wire event-type discriminator so React can subscribe per event name:

- **Scheduler** (`SchedulerHubEvents` in `ISchedulerEventPublisher.cs`): `scheduler.jobDefinitionChanged`, `scheduler.runStarted`, `scheduler.runProgress`, `scheduler.runCompleted`, `scheduler.runFailed`, `scheduler.runCancelled`.
- **GGUF download** (`GgufDownloadHubEvents` in `IGgufDownloadEventPublisher.cs`): a single `ggufDownload.statusChanged` event; each push carries the sanitized `GgufDownloadStatusHubEvent` for one tracked download.
- **Source build** (`LlamaCppSourceBuildHubEvents` in `ILlamaCppSourceBuildEventPublisher.cs`): `llamaCppSourceBuild.statusChanged`. Each push carries the phase plus the appended log lines and their **sequence numbers**, so a client reconciles across ring-buffer rollover and reconnects rather than assuming a contiguous log.
- **Runtime acquisition** (`RuntimeAcquisitionHubEvents` in `IRuntimeAcquisitionEventPublisher.cs`): `runtimeAcquisition.statusChanged`, carrying a monotonic sequence and sanitized progress snapshot shared with the hydrate endpoint.
- **Knowledge base** (`KnowledgeBaseHubEvents` in `IKnowledgeIndexingNotifier.cs`): `knowledge.documentChanged`. Payload is document id + coarse status + timestamp only — deliberately no file name, chunk text, or failure detail.
- **Image jobs** (`ImageJobHubEvents` in `IImageJobEventPublisher.cs`): `imageJob.statusChanged`, carrying the coarse phase and a per-job monotonic `Seq` for replay/dedupe. **Never** carries the prompt, and there is no step/percent field (the runtime exposes none over HTTP).
- **Image runtime source build** (`StableDiffusionCppSourceBuildEvents`): `stableDiffusionCppSourceBuild.statusChanged`, carrying the phase, bounded appended log lines with their start sequence, sanitized terminal error, and build provenance.
- **Benchmark runs** (`BenchmarkRunHubEvents` in `Client/Hubs/BenchmarkRunHub.cs`): `benchmarkRun.event` plus `benchmarkRun.replayReset`, the latter carrying `(RunId, LatestSequence, RunVersion)` so a client that cannot be caught up from the buffer re-hydrates from the run endpoint instead of rendering a hole.
- **Dataset generation** (`DatasetGenerationHubEvents` in `Client/Hubs/DatasetGenerationHub.cs`): `datasetGeneration.event` / `datasetGeneration.replayReset`, same reset contract keyed on the dataset id and version.
- **Training runs** (`TrainingRunHubEvents` in `Client/Hubs/TrainingRunHub.cs`): `trainingRun.event` / `trainingRun.replayReset`, same reset contract keyed on the run id and version.
- **Training runtime** (`TrainingRuntimeHubEvents` in `Providers.Training/Contracts/ITrainingRuntimeService.cs`): `trainingRuntime.statusChanged`. Each push carries the install phase plus **only the log lines appended since the last push** and their start sequence, so a reconnecting client splices its local log at a known offset rather than re-rendering the whole ring.
- **Work sessions** (`WorkSessionHubEvents` in `Client/Hubs/WorkSessionHub.cs`): a single `workSessionChanged` carrying `(SessionId, Seq, Kind)` to the group `work-session-{sessionId:N}`. It is a **notification, never a payload**: the client re-reads the named feed from that feed's own watermark, so a dropped push degrades to a late read rather than a wrong render. `Kind` is **lowercase on the wire** (`status|step|task|finding|artifact|checkpoint`), written out as literals in `WorkSessionEventPublisher.ToWireKind` rather than derived from the enum name — the client switches on those strings. The `seq` is the EVENT row's sequence, one above the content row's, which is why the contract is "something changed at N, re-read each feed from its own watermark" rather than "row N is in feed X".
- **Development workflows** (`DevWorkflowHubEvents` in `Client/Hubs/DevWorkflowRunHub.cs`): a single `devWorkflowChanged` carrying `(RunId, Seq, Kind)` to the group `dev-workflow-run-{runId:N}` — the same notification-never-a-payload contract as work sessions, and for the same reason: the client re-reads the run or the named feed, so a dropped push is a late read rather than a wrong render. `Kind` is **lowercase on the wire** (`run|node|gate|artifact`), written as literals in `DevWorkflowEventPublisher.ToWireKind`. The publisher is a **store decorator** (`PublishingDevWorkflowStore`), so one ping is emitted per committed mutation with the sequence that commit allocated — a reflection test holds the decorator to every mutation the store interface declares.
- **Graph workflows** (`GraphWorkflowHubEvents` in `Client/Hubs/GraphWorkflowRunHub.cs`): a single `graphWorkflowChanged` carrying `(RunId, Seq, Kind)` to the group `graph-workflow-run-{runId:N}` — the same notification-never-a-payload contract as the two above, and for the same reason: the client re-reads the run or its event feed, so a dropped push is a late read rather than a wrong render. `Kind` is **lowercase on the wire** (`run|node|gate`), written as literals in `GraphWorkflowEventPublisher.ToWireKind`. The publisher is a **store decorator** (`PublishingGraphWorkflowStore`), so one ping is emitted per committed mutation with the sequence that commit allocated; a run start and the startup reconciler publish nothing, because nothing is subscribed to them.
- **Transcription** (`TranscriptionHubEvents` in `Client/Hubs/TranscriptionHub.cs`): `transcriptionSegmentCommitted` carrying `(SessionId, Seq, StartMs, EndMs, Text, Channel, Confidence)`, `transcriptionPartialUpdated` carrying `(SessionId, Channel, Text)` and `transcriptionSessionStatusChanged` carrying `(SessionId, Status)`, all to the group `transcription-session-{sessionId:N}`. These ARE payloads, not notifications, and deliberately so: a partial has no row behind it to re-read, and a committed segment reaches a persist-free dictation session that stores nothing at all. `Channel` is **PascalCase on the wire** (`Mono|You|Others`), written as literals in `TranscriptionMapper.ToWireChannel` and shared with the REST transcript rows — a resuming client merges the replay snapshot and the live pushes into one list by exact `Seq`, so the same field must be spelled the same way in both. `Status` is the end reason mapped by `TranscriptionEventPublisher.ToWireStatus` (`Completed|Cancelled|Abandoned|Overloaded|Failed`; `NeverAttached` reports as `Abandoned`).
- **External apps** (`ExternalAppHubEvents` in `Client/Hubs/ExternalAppHub.cs`): `externalAppChanged` carrying `(InstanceId, Sequence, Kind, Status)` to the group `external-app-{instanceId:N}` — notification, never payload: the client re-reads the instance or its event feed from its own watermark, so a dropped push is a late read rather than a wrong render. `Kind` is **lowerCamelCase on the wire** (`installed|started|stopped|restarted|updated|reset|uninstalled|failed|startRequested|stopRequested|updateRequested|resetRequested|uninstallRequested|restoredOnBoot|stoppedUnexpectedly|permissionAccepted`), written as literals in `ExternalAppEventPublisher.ToWireKind` rather than derived from the enum name. `externalAppPullProgress` is the one message that is a payload — `(InstanceId, Service, LayerCount, CompletedLayers, Bytes)` — because there is no row behind it to re-read.
- **Development attempts**: the one hub that does **not** use a `*HubEvents` constant class — `DevelopmentAttemptLiveEventPublisher.PublishAsync()` sends the literal method name `developmentAttemptUpdate` to the group `development-project:{projectId:N}:attempt:{attemptId:N}`.

### Hub payloads use the app's JSON policy

`AddSignalR(...).AddJsonProtocol(options => ConfigureJsonSerializerOptions(options.PayloadSerializerOptions))` in `ConfigureServices` hands the hub protocol the **same** `JsonSerializerOptions` configurer the REST surface gets (§5) — camelCase property names, the two custom converters, and `JsonStringEnumConverter`, so a CLR enum member goes out as its **declared name** (`"Indexed"`, `"Succeeded"`, `"TerminalSnapshotAvailable"`), matching the string union the OpenAPI-generated type carries for the same field. Without that call SignalR uses its own defaults, which agree on camelCase but have no enum converter, so every enum member left as a **raw integer** while the generated TS type said string: five browser handlers compared a number against a name and did nothing — silently, with no error, log line or failing test, because each one's own test fed it a string. The wire form is now identical on both transports; do not configure a second options instance for hubs.

This does **not** change the hand-written projections above. `ToWireKind`/`ToWireChannel`/`ToWireStatus` and the `Phase` members of the source-build, acquisition and image-job payloads are already `string` on the CLR side, deliberately, and the enum converter never sees them — their documented lowercase / lowerCamelCase / PascalCase spellings are unaffected. Inbound (client→server) arguments are scalars everywhere, including `TranscriptionHub.PushAudioFrame`'s `int channel`, so nothing the browser sends changes meaning either.

### Publisher pattern (default no-op + host swap)

Scheduler and Graph Workflow broadcasts go through a publisher interface whose default implementation is a **no-op** (`NoOpGraphWorkflowEventPublisher`, registered with `TryAddSingleton`); the Client host swaps in the hub-backed publisher, so a host without the hub stays resolvable. This keeps `Client.Application` services free of a SignalR dependency — they call `IGraphWorkflowEventPublisher`/`ISchedulerEventPublisher`, and the transport is injected at the host. The concrete `GraphWorkflowEventPublisher`/`SchedulerEventPublisher` (`Client/Hubs/*EventPublisher.cs`) wrap `IHubContext<T>`. Graph Workflows go one step further: the publisher is invoked from a **store decorator** (`PublishingGraphWorkflowStore`), so exactly one ping is emitted per committed mutation with the sequence that commit allocated, and a publisher failure is logged rather than failing a write that already landed.

### Per-run scoping (Graph Workflows and Development Workflows)

`GraphWorkflowHubGroups.Run(runId)` → group name `graph-workflow-run-{runId:N}`. A **single hub connection can drive several runs**, so every payload carries a mandatory `RunId` — that is the real cross-contamination guard, with the group only scoping delivery. A **disconnect cancels nothing**: a workflow run is durable and outlives both the browser tab and the engine, which is the property the module exists to prove.

> There is no privacy exception to declare here. The graph-workflow payload is content-free — `(RunId, Seq, Kind)` and nothing else — so a subscriber re-reads the named feed from its own watermark and no run output ever crosses the hub. See [Security & Privacy](12-security-and-privacy.md).

### Chat hub: attachment and refusals

`HubException` is the **only** exception type whose *message* SignalR forwards to the client without detailed errors enabled; any other type reaches the browser as the bare "An unexpected error occurred invoking 'SendMessage' on the server." SignalR still PREPENDS that generic sentence plus `HubException:` to the forwarded text, which is why the chat page's `errorMessage` helper strips the wrapper so the operator reads the real sentence first.

`LocalChatHub` throws it in two places. `EnsureMessageWithinSizeCap` is the message-size cap's only enforcement point for a local send, and it sits in the hub rather than deeper because `NodeChatStreamService.SendMessageCoreAsync` persists the user turn before anything downstream can inspect its content — a check any later leaves the oversized row in the conversation for every subsequent turn to trip over. `TranslateDomainRejections` re-throws the stream services' typed caller-triggerable rejections: a send or regenerate against an `Origin=Remote` (view-only) conversation, a deleted conversation or message, or a correlation already being generated. The conversion is deliberately narrow, matched by exception TYPE and never by inspecting a message string, because widening it to every fault would forward internal detail to the browser — which is what SignalR's generic message exists to prevent. Only the read-only rejection is PREFIXED, with the `NodeConflictProblemType.ReadOnlyConversation` name: the exact discriminator token the REST 409 carries as `ConflictProblemDetails.conflictType`, so the SPA's `isNodeChatReadOnlyConflict` recognises both shapes off one constant. It is referenced via the enum, never a literal, so a rename cannot silently desynchronise the two paths. The others carry no token — no caller discriminates on them, and an unstripped token would be the first thing the operator reads in the toast.

`TranslateDomainRejections` is composed into `TrackAttachment` rather than applied at the individual call sites, so all four stream entry points are covered by one seam; it is a no-op for the resume paths, which never run the mutation guard. The rejections are thrown LAZILY during enumeration (they live inside the services' async iterators), so the conversion has to happen around `MoveNextAsync`; C# forbids `yield return` inside a `try` that has a `catch`, hence the manual enumeration with the yield outside the try.

`TrackAttachment` marks the invocation as WATCHED for as long as its stream is being consumed, so `DetachedInvocationReaper` can end a run whose client went away and never came back. The hub is the only attach site because all four stream entry points return from that one file. The invocation id is latched off the FIRST event's `ChatStreamEvent.RequestId` rather than taken from the arguments — `SendMessage` and `ResumeMessage` know it up front, but `RegenerateMessage` and `ResumeConversation` mint it server-side, and latching uniformly means an entry point added later is covered without touching the method. The release is driven by the cancellation token SignalR cancels when the client unsubscribes or disconnects, NOT by the source enumerable completing: `NodeChatStreamService.SendMessageCoreAsync` awaits its pump and runner tasks in the `finally` after its SSE loop exits, so the enumerable does not return until the entire run is over, and releasing only from the method's own `finally` records the detach *after* the run has already terminalized — leaving the reaper nothing to reap and the grace silently dead. The `finally` stays as the normal-completion path; the handle is idempotent.

### Hub authentication: token-in-query

Browsers cannot set an `Authorization` header on a WebSocket handshake, so JWT bearer is configured in `ConfigureServices.AddNodeAuthAndConnectionExtensions()` with an `OnMessageReceived` handler that pulls the token from the `access_token` query-string parameter — but **only when the path is under `/api/local/v1` *and* ends with `/hub`**. Both conditions matter: a query-string token is never honoured on an ordinary REST route, only on a hub handshake. React clients append `?access_token=…` when opening a hub. See `NodeChatConnection.ts` for the client side ([React Client](10-react-client.md)).

## 4. Cross-cutting transport concerns

### Exception handling → RFC7807

Registered **before** `UseFastEndpoints` so it wraps endpoints (see the `UseExceptionHandler` / `UseFastEndpoints` order in `Program.cs`). A chain of `IExceptionHandler` implementations is registered in order by `ConfigureServices.AddServices()` plus `AddProblemDetails()`; the registration block itself is the inventory, and `ExceptionHandlerRegistrationOrderTests` pins the order. The shape of the chain:

1. **Shared wire contracts** — `ConflictExceptionHandler` (typed domain conflict → the one 409 `ConflictProblemDetails` envelope) and `DomainValidationExceptionHandler` (single-message validation → the FastEndpoints 400 body).
2. **Per-family handlers** — one per area that owns its own status split or response DTO: Development conflicts and not-found, the selected-folder family (404 / 409 / 400 by type), Training, Benchmark, the GGUF import and download mappers, WorkSession / DevWorkflow / GraphWorkflow not-found.
3. **Host refusals** — `RequestBodyTooLargeExceptionHandler`, which answers Kestrel's own body-cap rejection (raised inside model binding, before any endpoint runs).
4. `DefaultExceptionHandler` — catch-all 500; redacts internal detail outside development (takes `IHostEnvironment`).

This mirrors the central platform's handler-chain pattern: specific handlers first, generic catch-all last. Internal error detail is never leaked to the browser. An endpoint-local `catch` that re-states a mapping the chain already owns is the anti-pattern `EndpointExceptionMappingSourceGuardTests` guards against — a type belongs in the chain when its status is the same at every endpoint that raises it, and stays local when it is not.

### Status choices worth their reasons

A handful of handlers in the chain answer a status whose reason is not obvious from the type they catch.

- **No usable container runtime → 503, not 409.** `ContainerRuntimeUnavailableExceptionHandler` maps the routes that reach `IContainerRuntimeResolver.CreateRuntimeAsync` inside the request rather than inside a background operation; without it, reading a log tail on a node whose Docker daemon is down is a 500, which tells the operator the engine broke rather than that the machine has an obstacle to clear. It is not a state transition the operator can decline and not a conflict with anything the node holds: the request is well-formed and will succeed once the daemon is back, which is what "the service is temporarily unable" means. [ADR 0009](../adr/0009-conflict-envelope-versus-operational-block.md)'s Blocked-family carve-out does not apply, because those exist for refusals the service RETURNS as a value, whereas this one can only be thrown. The detail is the resolution's own operator message — the same prose the runtime card renders, already redacted to `DockerDaemonEndpoint.Display` — and never a daemon exception message, which can carry the environment it failed on. The lifecycle verbs are unaffected: they admit with a 202 and settle the same unavailability into the row's `RuntimeUnavailable` failure category.
- **A capped route has two refusal paths and one 413 answer.** A route carrying `IRequestSizeLimitMetadata` has two of them and only one used to be answered. The endpoint's own early exit reads `Content-Length` and sends the declared 413, but Kestrel enforces the cap as it READS, inside model binding and before any handler code runs; its refusal is a `BadHttpRequestException` carrying status 413, which nothing mapped, so `DefaultExceptionHandler` turned the refusal a real connection actually takes into a 500. `RequestBodyTooLargeExceptionHandler` answers it, and it is transport-level rather than per-family — one handler instead of one per capped route, so every route that declares a body cap reaches the same throw and the same answer. The two paths used to write two different shapes for that one status (ASP.NET `ProblemDetails` from the handler, FastEndpoints' `errors[]` from the endpoint) while both DECLARE `ProducesProblem(413)`, which made the second a contract lie the generated client encodes. Both now go through `RequestBodyTooLargeProblem.WriteAsync`, the single writer: the handler awaits it and an endpoint sends `RequestBodyTooLargeProblem.Result` through `Send.ResultAsync`. Only `Detail` differs between them, because the host knows nothing but "too large" while an endpoint can name the cap it enforces.
- **The Development family's 409s keep the FastEndpoints body.** `DevelopmentConflictExceptionHandler` writes `AddError(message) + Send.ErrorsAsync(409)`'s body through `FastEndpointsProblemWriter` — a relocation of what every endpoint used to write by hand, not a reshape. It deliberately does NOT route through `ConflictExceptionHandler`, whose `ConflictProblemDetails` envelope is a different body: the message moves from the `errors` array to `detail`, `title` becomes "Conflict", and a `conflictType` discriminator appears. Folding Development into that envelope is worth doing, but it is an OpenAPI-visible contract change needing its own `NodeConflictProblemType` members and a regenerated client. `DevelopmentWorkspaceSecurityException` is absent on purpose: the patch and next-action endpoints answer it 409 while register/create/reconnect answer it 400, so no single status is correct for it — and its derived `DevelopmentRepositoryStateConflictException` is absent for the same reason, since the reconnect endpoint still catches the base type locally and would swallow the derived one before a global handler saw it.
- **Two `type` URIs coexist, deliberately.** `ConflictExceptionHandler` sets `https://tools.ietf.org/html/rfc7231#section-6.5.8`, which is also what ASP.NET Core's own `ProblemDetailsDefaults` emits and what the API already serves unmodified wherever `Results.Problem` builds the body (`BenchmarkEndpointSupport.Problem`); `DevelopmentConflictExceptionHandler` reaches FastEndpoints' `www.rfc-editor.org/rfc/` base by setting no `Type` at all. Aligning the first line would move it AWAY from the framework's, so one canonical `type` across the API is unreachable. `DevelopmentExceptionHandlerTests` pins the divergence and [ADR 0009](../adr/0009-conflict-envelope-versus-operational-block.md) records why it stands.

### The three error bodies and their declarations

This API writes **three** distinct error shapes, and each has its own `Produces*` declaration. Declaring the wrong one is a contract lie the generated hey-api client encodes, and nothing at runtime corrects it. `Endpoints/Common/ProblemDetailsProducesExtensions.cs` holds the one custom declaration.

| Body | Written by | Declare with | Schema |
|---|---|---|---|
| FastEndpoints' own error body | `AddError` + `Send.ErrorsAsync`, and the global `DomainValidationExceptionHandler`, which mimics it | FastEndpoints' `ProducesProblemDetails(status)` | `additionalProperties: false` with an `errors[]` member |
| The `ConflictProblemDetails` envelope | `ConflictExceptionHandler` | `ProducesConflictProblemDetails()` (`ProblemDetailsProducesExtensions`) | carries a `conflictType` discriminator and cap members the FastEndpoints schema does not know |
| Plain ASP.NET `ProblemDetails` | `Results.Problem(...)`, including `ConflictProblemSenderExtensions.ConflictProblemAsync` for a service that reports a conflict as a *return value* rather than an exception, so `ConflictExceptionHandler` never sees it | ASP.NET's own `ProducesProblem(status)` | permits additional properties, so extension members such as `code` / `outcome` / `traceId` are legal |

### Health checks

Two endpoints, each mapped with an explicit `.AllowAnonymous()` so an orchestrator or probe can reach them without a token (see `MapHealthChecks` in `Program.cs`). That call is load-bearing rather than decorative, and it is the *only* thing making these anonymous: what decides whether a request is challenged is the authorization metadata attached to the selected endpoint, never where the `Map*` call sits in the file. Until the deny-by-default pass these two were reachable purely by omission, because no `FallbackPolicy` existed; under the fallback policy an endpoint with no auth metadata is challenged, and Aspire's `WithHttpHealthCheck` poll carries no token. See "Security middleware & auth ordering" below.

| Endpoint | Behavior |
|---|---|
| `/health/live` | `Predicate = _ => false` — runs no checks; returns 200 if the process can serve requests (liveness). |
| `/health/ready` | runs only checks tagged `ready`; custom JSON writer emits `{status, checks:[{name,status,duration}]}` (readiness). |

### Security middleware & auth ordering

- `LocalApiSecurityMiddleware` (`Endpoints/Common/LocalApiSecurityMiddleware.cs`) runs before routing/auth. For any path under `/api/local/v1` it returns **403** unless the transport **peer** is loopback (`context.Connection.RemoteIpAddress` — the socket peer, so a routable caller is rejected even if it forges a loopback `Host`/`Origin`; a null peer, e.g. the in-process test host or an in-process health probe, is treated as loopback-equivalent) *and* the `Host` is in `{localhost, 127.0.0.1, ::1}` *and* the `Origin` (when present) is same-scheme/same-host/same-port and loopback. This enforces loopback-only access at the edge. See [Security & Privacy](12-security-and-privacy.md) §3.1.
  - **Why the socket peer is trusted as the client.** A reverse proxy running on the *same* host would appear as a loopback peer and defeat this check, since every forwarded request would arrive from `127.0.0.1`. That is by design and acceptable because a proxied or headless deployment is **unsupported**: the app binds loopback-only (`LoopbackBindGuard` shuts the process down on a routable bind, next bullet), and no forwarded-headers middleware is registered, so `X-Forwarded-For` is never honoured and the socket peer is always the real client on every supported (same-machine, single-user) launch. Deployments that put this surface behind a proxy, or expose it beyond the local machine, are out of scope for this guard.
- **Startup bind guard.** `LoopbackBindGuard` (`Hosting/LoopbackBindGuard.cs`, wired via `LoopbackBindGuard.Guard(app)`) is defense-in-depth behind the request-time middleware: after `ApplicationStarted` — so an OS-assigned port and wildcard expansion are already resolved — it inspects the addresses Kestrel *actually* bound and, if any is non-loopback (wildcards `*`/`+`/`0.0.0.0`/`::` count), logs a **critical** line naming the offending address and shuts the app down with exit code 1. The opt-out `Security:AllowNonLoopbackBind=true` defaults to `false` and no supported launch sets it. One bind is exempt **by name rather than by flag**: the container bridge deliberately listens on a LAN-facing address, and its resolved listener URL is passed in as the expected non-loopback bind. Naming exactly that address keeps the guard failing closed on every OTHER routable bind, which the flag cannot do — the flag would also silence the guard for `/api/local/v1` going routable by operator error, which is the thing it exists to catch. An expected bind is compared by scheme, host and port rather than as raw text, because Kestrel reports back what it actually bound and that string need not be character-identical to the one it was given; a wildcard is never "expected", since it is not one address and allow-listing it would exempt every interface the app bound rather than the single one the caller named (both the Kestrel spellings `*`/`+`, which parse to an empty host, and `0.0.0.0`/`[::]`, which parse to a real one). Desktop mode always binds `127.0.0.1` and Aspire dev binds `localhost` — external exposure is handled by the DCP proxy, not the app process — so the guard is a no-op on every supported launch. The shutdown sets `Environment.ExitCode = 1` **before** `StopApplication()`, so the value is in place before the host tears down and `Program`'s final return reads it; a supervisor or CI then treats the guarded shutdown as an error rather than a clean stop. See [Security & Privacy](12-security-and-privacy.md) §3.4.
- Then `UseRouting → UseRateLimiter → UseAuthentication → UseAuthorization` in `Program.cs`. Authn is JWT bearer; the `Operator` authorization policy gates both endpoints and hubs. Tests in `XE-Local-AI-Engine.Tests/ApiFoundation/LocalApiSecurityTests.cs` assert: missing/invalid token → 401, unsafe host → 400, unsafe origin → 403, valid token + same-origin → allowed.
- **Deny by default, in two layers.** The FastEndpoints global configurator (`config.Endpoints.Configurator` in `Program.cs`) forces `Policies(NodeAuthorizationPolicies.Operator)` onto every discovered endpoint, so an endpoint whose own `Configure()` forgets the call still ships protected. An endpoint that deliberately opted out with `AllowAnonymous()` still wins, because FastEndpoints emits no conflicting authorize metadata for a verb its anonymous verbs cover; the four pre-authentication endpoints under `Endpoints/Auth/V1/` (`NodeAuthStatusEndpoint`, `NodeSetupEndpoint`, `NodeLoginEndpoint`, `NodeRefreshEndpoint`) are the whole anonymous set. Behind that, `AuthorizationOptions.FallbackPolicy` (`ConfigureServices.cs`) requires JWT bearer plus an authenticated user for every routed surface carrying no auth metadata of its own: the hand-mapped minimal APIs, the hubs, the health probes, the SPA shell. It is deliberately weaker than `Operator`, asking for a valid token rather than the Admin role, so it is the second layer and not a replacement for the first. `EndpointAuthorizationPolicyTests` is what proves the first layer stays wired; see [Testing & Validation](13-testing-and-validation.md). The Configurator is applied **unconditionally** rather than "only when `AnonymousVerbs` is empty", because the order between it and an endpoint's own `Configure()` is unspecified and the unconditional call needs no such guarantee. `ConfiguratorCanaryProbeEndpoint` exists solely to make the deletion of that line fail the test.
  - **One documented side effect.** Because the Configurator sets `PreBuiltUserPolicies` on EVERY endpoint, FastEndpoints' Swagger generator treats every endpoint as `RequiresAuthorization()` and adds an auto-403 — including to the four anonymous auth operations (login, setup, status, refresh), whose auto-401 the same generator does suppress off `AnonymousVerbs`. The asymmetry is the library's. The 403 is kept because it is TRUE: `LocalApiSecurityMiddleware` answers a real 403 on every `/api/local/v1/*` route, anonymous ones included, for a foreign Origin/Host or a non-loopback peer, so an anonymous login request can and does get one. Suppressing it would mean unsetting the very policy the canary endpoint pins, trading a truthful declaration for a deny-by-default hole; `OpenApiDocumentTests` asserts the 403 is on every operation.
- **A path the node does not serve now answers 401, not 404.** The fallback policy is also evaluated when routing selects no endpoint at all, so an anonymous request to a missing file-like asset, or to a route registered only in desktop mode, fails closed instead of reporting 404 or 405. That is intended: an unauthenticated caller learns nothing about which paths and verbs exist. A caller holding an operator token still gets the ordinary 404 or 405.
- Request logging redacts the access-token query param via `AccessTokenQueryRedactor` before anything is written (the `UseSerilogRequestLogging` request-path projection in `Program.cs`).

Full rationale: [Security & Privacy](12-security-and-privacy.md).

### Dev-only surfaces

Not mapped in Production: OpenAPI JSON at `/openapi/local/v1/{documentName}.json` and the Scalar API reference at `/scalar`.

`UseSwaggerGen`, which serves the OpenAPI JSON, runs **before** `app.UseAuthentication()`. It is raw middleware rather than an endpoint-convention builder, so it registers no endpoint for `.AllowAnonymous()` to attach to, and the fallback policy would otherwise challenge it. Scalar stays where it is: `MapScalarApiReference` is a `Map*` call already chained with `.AllowAnonymous()`, and a `Map*` call's position in the file never decides which middleware wraps it.

Development Mode's endpoints are kept out of **discovery**, not merely out of routing, when the feature is off (`config.Endpoints.Filter` in `ConfigureServices`). The routing filter in `UseFastEndpoints` is too late: FastEndpoints instantiates every discovered endpoint at startup before evaluating that filter, and `AddNodeDevelopment` registers the services those endpoints take through their constructors only when the feature is on, so a discovered-but-unrouted Development endpoint would fail the node's boot. `GetDevelopmentCapabilityEndpoint` deliberately does not carry the marker, so it stays discoverable and answers the disabled state. The 404 the other routes give while the feature is off still comes from the request-path middleware in `Program.cs`, which runs before authentication and is therefore unaffected by whether the route exists.

The diagnostics canary probe (`diagnostics/configurator-canary-probe`) is registered like any other endpoint but excluded from the OpenAPI description, so it never reaches the generated client. It exists only so the global configurator's deletion fails a named test; it answers 204 to an operator and 401 to anyone else.

### Static SPA fallback

`UseStaticFiles()` + `MapFallbackToFile("index.html")` serve the built React app from the same origin as the API (the "C0re static-files pattern"). See [Hosting & Deployment](11-hosting-and-deployment.md).

`MapFallbackToFile` carries an explicit `.AllowAnonymous()`: the login page has to load before anyone can hold a token, and the fallback policy would otherwise challenge the SPA shell. Static assets are served by the `UseStaticFiles` middleware ahead of routing and are unaffected either way. A file-like path that no asset matches is a different story. The fallback route's `{*path:nonfile}` constraint keeps dotted paths out of the SPA shell, so such a request matches nothing and an anonymous caller now sees 401 rather than 404.

The shell is also kept off the API. An extensionless path satisfies `{*path:nonfile}`, so a mistyped or removed `/api/local/v1/...` route used to be answered with a 200 `text/html` shell — success, to a JSON client, for a route that does not exist. A small middleware immediately after `UseRouting` fixes that: the SPA fallback is mapped with a marker (`SpaFallbackMarker`), and when that endpoint is selected for a path under `LocalApiRoutes.Prefix` the middleware calls `SetEndpoint(null)`. The request then takes exactly the route an unmatched *dotted* path already takes — anonymous 401 from the fallback policy, operator token a bare 404 — and only the SPA fallback is detached, so real endpoints under the prefix (the hubs and their `negotiate`, `MapMcp`, the OpenAI-compatible proxy, the integration API) are untouched.

Detaching rather than mapping a second catch-all over the prefix is deliberate. `MapFallbackToFile` registers a **GET/HEAD-only** endpoint, which is why routing's own 405 still answers a wrong-verb request on a real API route; a routed all-verb catch-all under `/api/local/v1` would join the candidate set of every route below it and replace that 405 with 404 across the whole API. `RouteCoexistenceTests` pins both halves.

## 5. OpenAPI → hey-api: the single source of truth for React REST

**Rule:** the backend's OpenAPI document is the *only* definition of REST request/response shapes used by React. React never hand-writes a REST client; it imports generated functions. Hubs are the exception (hand-wrapped — SignalR isn't in OpenAPI).

### The pipeline

```
FastEndpoints (NSwag doc)                       React build
   │  /openapi/local/v1/v1.json                    ▲
   │                                               │  src/core/api/generated/
   ▼                                               │  (axios SDK + zod + react-query)
 openapi:fetch ──► openapi/v1.json ──► openapi:generate (hey-api/openapi-ts)
```

- **Doc source:** NSwag-generated document served at `/openapi/local/v1/{documentName}.json` (the non-Production `MapOpenApi` branch in `Program.cs`). `XE-Local-AI-Engine.Tests/ApiFoundation/OpenApiDocumentTests.cs` guards the document.
- **Fetch:** `pnpm run openapi:fetch` → `scripts/FetchOpenapi.mjs` pulls `OPENAPI_SPEC_URL` (default `https://localhost:50722/openapi/local/v1/v1.json`) into `openapi/v1.json`. HTTPS uses Node's normal certificate validation. When Node does not already trust the local .NET development certificate, export its public certificate as PEM and set `NODE_EXTRA_CA_CERTS` before starting Node; never disable TLS verification. The sanctioned desktop live contract script uses an isolated random loopback HTTP endpoint instead.
- **Normalize:** the fetch does not commit the document verbatim. `normalizeOpenapiDocument` in the same script is the single place the committed file is materialized, and the live check compares through it too, so the fetch and the check cannot disagree. It (a) drops `format: int64` so the zod plugin does not emit `bigint` validators against `number` types, (b) removes the dynamic loopback `servers` entry whose port changes per run, and (c) sorts the three maps the generator emits in **discovery order** — `paths`, each path item's operations, and `components.schemas`. That order is assembly type order, hence compile order, hence the order the `.cs` files sort in, so without the sort renaming one endpoint file reshuffles thousands of lines of an unchanged contract. Only maps are sorted, never arrays: `required`, `enum`, `parameters`, `oneOf`/`anyOf`, `tags` and a schema's `properties` order all reach the generated TypeScript.
- **Generate:** `pnpm run openapi:generate` → `openapi-ts --file OpenapiTs.config.ts` writes `src/core/api/generated/`.
- **Combined:** `pnpm run openapi` runs both; `openapi:check` / `openapi:check:live` fail CI if the generated output drifts from committed code (`git diff --exit-code`). The two see different things: `openapi:check` regenerates the client from the **committed** spec and so cannot see a backend-side change at all, while `openapi:check:live` compares the committed spec against a running host. Only the first is in a gate, because the second needs a host.

### Why the FastEndpoints serializer global is seeded at registration time

The OpenAPI document is generated against a COPY of the FastEndpoints serializer global — `FastEndpoints.Swagger`'s `SwaggerDocument` registration does `new JsonSerializerOptions(Config.SerOpts.Options)` — and NSwag's `UseOpenApi` resolves that registration EAGERLY while the pipeline is being built, whenever the document path contains `{documentName}`, which this one does. `UseFastEndpoints`, which is what normally populates that global from `IOptions<JsonOptions>`, has not run at that point, so the generator would describe a camelCase API with PascalCase property and parameter names. Seeding the global in `ConfigureServices`, at registration time, makes the document correct no matter where the middleware sits in the pipeline; `UseFastEndpoints` later replaces the instance outright, so runtime serialization is unaffected. The camelCase policy is **stated rather than inherited** in the shared JSON configuration: every options instance it is applied to at runtime already carries it from `JsonSerializerDefaults.Web`, but the FastEndpoints global starts life as a bare `JsonSerializerOptions` (PascalCase) and the document generator snapshots that one.

The global is process-wide and shared with every other host in the process, so it must not be mutated once it has been used: `System.Text.Json` seals an options instance on first (de)serialization. Read-only therefore means an earlier host already ran `UseFastEndpoints` and served with it, which is exactly the case where the instance already carries the camelCase policy it took from `IOptions<JsonOptions>` — nothing to seed.

### What the generator emits (`OpenapiTs.config.ts`)

- `@hey-api/client-axios` with a custom `Generated.runtime.ts` (sets axios baseURL, remaps thrown `ZodError` → central `ApiError`).
- `@hey-api/typescript` types.
- `zod` response schemas with `dates: { offset: true }` — required so RFC3339 offset timestamps (the backend serializes `DateTimeOffset` as `…+00:00`) validate; the default bare-`Z` schema would reject every offset response.
- `@hey-api/sdk` with `validator: true` — each SDK call validates the response at the transport boundary.
- `@tanstack/react-query` with `queryOptions`, `queryKeys`, `mutationOptions`.

### Maintainer workflow when you touch an endpoint

1. Add/modify the `*Endpoint.cs` + DTOs (the **class name becomes the operationId/SDK function name** — see §1).
2. Regenerate against a host: `OPENAPI_LIVE_SCRIPT=openapi scripts/openapi-live-check.sh`. That script already starts the host the document must come from — **desktop mode**, an isolated `XDG_DATA_HOME`/`HOME`, the build lock, the assembly guard, the port read from `desktop-port.txt`, and the host killed by process group on the way out — and `OPENAPI_LIVE_SCRIPT` chooses what it runs against it (`openapi:check:live` to compare, `openapi` to regenerate, `openapi:fetch` for the document alone). Desktop mode is not optional: off it, `Program.cs`'s `config.Endpoints.Filter` drops every `IDesktopOnlyEndpoint` from the document, and the regen then silently deletes those paths and their SDK functions.
3. Commit the regenerated artifacts (they are tracked; `openapi:check` enforces this).
4. For a **hub**, or a route whose response is not request/response JSON, do *not* expect a typed SDK fn — wire it by hand on the shared axios instance / through `SharedHubConnection` (see the hand-wired list above and the chat hub).

> Hand-rolling the throwaway host instead (connection string as a CLI arg, `XE_NODE_SQLITE_KEY`, `ASPNETCORE_URLS`, and `NODE_EXTRA_CA_CERTS` pointing at the trusted PEM development certificate, which Node reads only at startup) is the older recipe and gets the document **wrong** unless it also runs in desktop mode. Prefer the script in step 2; it is the same host start CI uses.

The generated SDK is regenerated as endpoint families land; the current artifacts include Custom Tools CRUD/probe, runtime-acquisition status, automation commands, workspaces, the Benchmarks and Training families, `proxy/key`, and the other routes inventoried above. The committed `openapi/v1.json` + `src/core/api/generated/` already include them; `openapi:check` still enforces that they stay in sync. The proxy **passthrough** (`proxy/v1/*`) is deliberately absent from that document — it is hand-mapped precisely so it never reaches the generated SDK.
