# LlamaServer Supervisor Internals

> Reference page for [Local Runtime & Providers](../03-local-runtime-and-providers.md) §2 · Reviewed: 2026-10-02 · Code-grounded.

It lists the supervisor's `EnsureRunningAsync` flow and spawn internals, spawn sequencing and fallbacks, startup failure classes, health and liveness probes, eviction and reaper rules, orphan reaping and DI wiring.

## `LlamaServerProcessSupervisor` — process lifecycle

**`EnsureRunningAsync` flow** (`LlamaServerProcessSupervisor.cs`):

```
1. External-endpoint short-circuit: _externalEndpoints.Resolve(model, role)
   -> if configured, return LlamaServerEndpoint pointing at it. NO spawn, NO supervision.
2. Fast path: an already-running, live process for the key is reused
   (MarkUsed timestamp) WITHOUT taking the spawn gate.
3. Single-flight: per-key SemaphoreSlim ensures concurrent callers spawn exactly once.
   Re-check under the gate; reap any crashed/exited lingering process; then
   SpawnWithRestartAsync (linear backoff up to MaxRestartAttempts).
```

**Spawn internals.** `SpawnWithRestartAsync` → `SpawnOnceAsync` → `SpawnCoreAsync` → `BuildLaunchSpec`. `SpawnOnceAsync` (`LlamaServerProcessSupervisor.cs`) no longer builds args itself: it hands `SpawnCoreAsync` a resolver delegate `(variant, ct) => _profileResolver.ResolveAsync(model, role, variant, ct)` that returns the launch arguments for this `(model, role, backend)`. `SpawnCoreAsync` resolves the model file + variant + binary, awaits that delegate **before** taking the admission gate (so a slow profile read never stalls admission for other keys), then `AdmitAndAllocatePortAsync` takes the admission gate, prunes exited processes, enforces the loaded-cap (evict idle LRU via `TryEvictIdleLeastRecentlyUsed`, else throw `CapReached`), and allocates a port.

`BuildLaunchSpec(key, exe, modelFile, port, variant, resolved)` builds the exact ordered argv from the resolved arguments:

```
-m <modelFile> --host 127.0.0.1 --port <port>
  --parallel 1             # pinned on EVERY spawn (single-slot serving)
  --no-warmup              # pinned on EVERY spawn (skip empty-run warmup)
  <context/placement/thread args>   # from the launch policy — see below
  --jinja                  # ModelRole.Chat
  --embeddings --pooling mean  # ModelRole.Embedding
  --rerank --pooling rank      # ModelRole.Reranker
```

Two flags are pinned on **every** spawn:

- **`--parallel 1`** forces single-slot serving. Without it `llama-server` auto-selects `n_parallel=4`, which reserves 4× the KV cache and starves the auto-fit weight offload — a model that would fit on the GPU spills weights to system RAM for KV slots it never uses and runs slow on the CPU.
- **`--no-warmup`** skips the empty-run warmup (45–110 s on a large model) that would otherwise overrun the readiness budget and tree-kill the half-ready process in a respawn loop (observed as a chat inter-chunk stall and an explore "did not become ready in time").

**Context, KV/flash-attention, and CPU threads now come from a central launch policy** (`LlamaServerLaunchPolicy` + `LlamaServerLaunchPolicyOptions`, AUD4-02/05/17). `BuildLaunchSpec` takes a `LlamaServerLaunchPlan` the policy produced (a **null** plan for operator profiling = no policy interference). Precedence, highest first: **frozen inference profile replayed verbatim** (never overridden) > per-send/user config > role defaults. Emission by variant + explore/replay mode:

- **GPU explore** — `--fit on --metrics` (auto-fit chooses layer/expert placement and prints it for capture) **plus** the policy's deterministic `-c <ctx>` (auto-fit respects an explicit `-c` and fits ngl/batch around it) **plus** the KV-cache quant + flash attention optimization `-fa on -ctk q8_0 -ctv q8_0`. `-c`/`-fa`/`-ctk`/`-ctv` are not *placement* flags, so `--fit` stays active.
- **GPU replay** — the frozen/explored profile's explicit args verbatim: `-c <ctx>` plus `-ngl/-ts/-ot` and matched `-ctk/-ctv` with `--flash-attn on`. `--fit` is intentionally absent (an explicit placement flag disables it). The policy leaves context/KV to the profile.
- **CPU** — `-c <ctx>` (deterministic; previously the CPU variant emitted **no** `-c` ⇒ full-train-ctx KV in RAM) **plus** the CPU thread policy `-t`/`-tb` (physical-core estimate minus a host reserve). **No** `--fit`/`--metrics`/`-ngl`/`-ctk` — a frozen GPU profile does not transfer to a CPU spawn, and KV stays f16 / flash-attention auto.

Context allocation in the composed application is capacity-tiered: chat selects the largest stable dual-axis tier from **65536/32768/16384/8192/4096/2048**, while embedding/reranker use **2048**; each is capped and aligned to the model's GGUF train context. The `ChatContextTokens=16384` option is the provider-only fallback when the application capacity resolver is not composed, not a fixed shipping-app default. **KV-quant one-shot fallback:** if the optimized GPU spawn can't reach readiness, the supervisor retries once with the safe config (no `-ctk/-ctv`, `-fa auto`) and — only when the safe retry succeeds — records the fallback per (backend, KV type) in `llama-launch-fallback.json` (`ILlamaServerLaunchFallbackStore`) so later spawns skip the known-bad config while the same backend's other KV types keep working; legacy un-keyed entries written before that keying are ignored and dropped on the first read. The file is USER-level and shared by every node process on the host, so a write re-reads and merges under an OS lock held on a sibling `llama-launch-fallback.json.lock` (never on the state file itself, or the atomic replace over it would fail on Windows) and — while that lock is held — sibling node processes cannot lose each other's verdict. Acquisition is bounded (a few short retries); a write that could not take the lock proceeds unlocked, logs a Warning, and can still lose a concurrent sibling write. The **`--host 127.0.0.1`** localhost-only bind is unchanged. See [§2.5 Inference profiles / per-machine tuning](../03-local-runtime-and-providers.md#25-inference-profiles--per-machine-tuning) for where the frozen `resolved` args come from.

## Spawn attempt sequencing, startup capture and one-shot fallbacks

**Following the served binary.** Everything after `EnsureBinaryAsync` keys off the variant of the binary actually handed back, not the selected one: the VRAM admission gate, the placement sniffer, the launch policy and — through `LlamaServerLaunchProjection` — every GPU argument (`-ngl`, `--fit` and `-ctk` are gated on a non-CPU variant). The manager may serve a different variant than was selected, because the managed source-build record is authoritative and wins while the selector's cached signal is unseeded; selecting CPU and serving a CUDA build would otherwise spawn it with no offload at all. The admission **identity** check deliberately stays on the SELECTED variant — that is what the admission was granted against — while an admission whose variant the override moved off is dropped entirely: its arguments were resolved for another backend and its allocation was sized for one (a CPU admission carries no GPU bytes), so spending it on a GPU load would put that load outside VRAM capacity accounting and let concurrent spawns oversubscribe the device. The unadmitted path then resolves both against the variant actually being launched.

**The GPU load-admission gate.** A non-CPU spawn holds a process-wide ticket (shared with the image supervisor) across its whole spawn-through-readiness window, so two `--fit` loads never read the same free-VRAM snapshot and oversubscribe the device; CPU loads bypass it, having nothing to contend for. It is acquired after variant selection and argument resolution and immediately before the admission cap decision that may evict an idle process to free VRAM, so the freed VRAM is seen only by this load's `--fit`; the ticket releases on readiness or on any failure, and the next waiter proceeds with a fresh free-VRAM read. It deliberately spans **both** launch-plan attempts, because another load interleaving between them would re-race exactly the read the gate exists to serialize. The core runs under the detached-spawn/shutdown token rather than the first caller's, so a caller cancelling its wait never leaves the gate held.

**Operator extra launch arguments.** Per-model operator flags are resolved alongside the profile arguments and before the admission gate — a slow store read must not stall admission for other keys — and only on the normal serving path, so a benchmark or profiling spawn stays a pure measurement that the operator's experimentation flags never perturb. The resolver has already stripped the app-managed families: reachability (`-m`, `--model`, `--host`, `--port`) and the memory-fit placement family (`-c`, `-ngl`, `-ts`, `-ot`, `-ctk`, `-ctv`, `-fa`, `--parallel`, `-b`, `-ub`), whose values the allocation and the policy already decided and recorded in the ledger — so what remains is sampling and decoding tuning. Those are appended **after** the built spec, where a later scalar flag overrides the bundled tuning default (llama.cpp is last-wins), and **before** the diagnostic `--metrics` / `-lv` fill-ins, so those checks see an operator-supplied flag and do not duplicate it. Resolution never throws.

**Raised verbosity for the placement banner.** At the server default the whole startup is 11 lines and says nothing about placement, so a model whose weights spilled into system RAM is indistinguishable from one that fully fit; every GPU spawn therefore launches with `-lv` raised just enough to make llama.cpp print how many layers landed on the GPU. Every GPU spawn pays it deliberately: placement under auto-fit is decided against the free VRAM *at load time*, so the same model can be fully resident loaded alone and partly resident loaded beside two others — measuring once and reusing the answer would report a number that is no longer true, and each spawn is a fresh process that gets a fresh reading. The sink cost is paid back by demoting that child's request chatter to Debug once it is serving. The operator-profiling **explore** path is skipped because it already raises verbosity to maximum. A **benchmark** spawn is the exception among profiling spawns: it takes a fit-params capture like the others but never reaches the explore `-v` branch (its args are a replay), so without this branch it would be the one measurement that could not say where its own layers landed — exactly the spawn whose placement a later reader most needs. It pays the same demotion.

`PlacementProbeLogVerbosity` is the lowest level that emits the banner, and the levels were measured: the server default of **3** prints an 11-line startup carrying no placement information at all; level **4** adds ~213 startup lines per spawn and ~22 lines per request. The launcher forwards every line to the child's output tail, but logs only marker lines at Information (errors, warnings, CUDA, backend, tensor-load and offload summaries, listening and readiness; `LlamaServerProcessLauncher.IsMarkerLine`) and one rate-limited `slot` progress line, and everything else at Debug, so the rolling file absorbs little while the support bundle's `processes/*.txt` tail still holds the full start-up; the next level up is the per-tensor debug firehose at ~1250 startup lines and ~1650 lines **per request**, which no sink policy makes affordable.

**Startup capture.** The sink is wired for the process's lifetime, but the two automatic buffers behind it are startup-only: the placement banner is read at readiness, and the failure-classifier window is only ever read from an attempt's catch block, which readiness has ruled out. Detaching them at readiness turns every serving-time forwarded line from a lock plus string copy into one volatile read. The operator profiling sink is **not** detached — that output was explicitly requested. The placement sniffer is deliberately not read off the bounded automatic buffer: at the verbosity the banner requires it is printed around line 155, outside any small window.

**Ordering around readiness.** The load observation is assembled at readiness but published only just before the successful return: post-readiness bookkeeping can still throw and tree-kill the child, and a `Ready` observation raised before that point would tell the host — and its last-load VRAM cache — that a process which never served had loaded. The publish latches, so the catch paths record the failed outcome exactly once. The serving latch is flipped only after the placement banner has been read, and never on a spawn that failed to become ready, because both startup buffers must stay live for the whole load window. `llama-fit-params` output is published only for the candidate that actually reached readiness, so output from a failed optimized candidate is never frozen.

**The safe-retry verdict.** When the safe plan reaches readiness where the optimized (KV-quant + flash-attention) plan could not, the optimized config is the culprit for that backend — a broken model would have failed the safe plan too — and `ILlamaServerLaunchPolicy.RecordOptimizedConfigFailedAsync` records it so later spawns skip it. `WithoutKvCacheQuantization()` leaves the plan's `KvCacheType` intact, so the verdict is keyed on the node's CURRENT selection; on the replay branch that coincides with the profile's frozen type only because the selected KV-cache type is part of a profile's launch-policy fingerprint, so a profile frozen under another type is already stale and re-explores rather than replaying — a mismatching pair never reaches the line. The record is written after the process is registered, which is safe because the policy absorbs a verdict it cannot persist: the endpoint is already reachable by a concurrent `EnsureRunningAsync`, so an exception there would tree-kill a process another caller holds, to save a cache entry the next spawn re-records. An **expert-offload** (`CpuMoe`) plan is the exception: it is the most VRAM-marginal launch on the host, so a one-shot safe success proves nothing about KV — the primary may have failed on placement or transient pressure — and recording it would disable the optimized config for every model on that backend from one model's failure, so it is logged as inconclusive instead.

**The benchmark launch receipt** is read back out of the FINAL argv rather than recomputed from `(variant, resolved, plan, role, tuning)`: the capability gate can drop an optional flag the intended projection still claims, and the operator's extra arguments were appended after it. An unparseable vector falls back to the intended shape — a describable launch is worth more than no receipt at all. Assembly is non-throwing by construction, so a receipt can never turn a healthy measurement into a failed run.

### Startup failure classification

Two precedence rules, both deliberate. WITHIN a line an unambiguous out-of-memory phrase wins, then a KV or flash-attention compatibility marker, then generic allocation-failure wording — so a line reporting an unsupported cache type stays a compatibility verdict even though it also says it failed to allocate. ACROSS lines, out-of-memory outranks compatibility: an allocation failure is hardware evidence that stands on its own, while another line merely naming the KV cache is not evidence against it. The compatibility markers name a cache TYPE or flash attention, never the KV cache as a component — the distinction the joined buffer erased, since failing to allocate the KV cache is an allocation failure and only a rejected cache type or a flash-attention requirement is a compatibility problem.

## Health probe — readiness vs liveness

`LlamaServerHealthProbe` (impl of `ILlamaServerHealthProbe`) polls the `llama-server` **`/health`** endpoint over HTTP (`/health` is a sibling of the `/v1` base). `WaitForReadyAsync` polls every 250 ms until a 200 or the readiness deadline — connection-refused during warm-up is normal and retried. `CheckResponsiveAsync` is a single probe used by health aggregation. The readiness deadline is **size-aware** (`LlamaServerSupervisorOptions.ResolveReadinessTimeout(bytes)` — base + per-GiB extension above a threshold, capped), not a fixed constant, so a large model gets proportionally longer to load. The probe runs on a **dedicated, resilience-free `HttpClient`** with a ~1 s per-attempt bound: routing it through the app's `IHttpClientFactory` inherited the standard resilience handler's exponential retries, which fired one logical probe at +0.2 / 2.4 / 5.1 / 10.2 s and detected readiness up to ~5 s late. The probe issues exactly one bounded request per poll, so the 250 ms cadence — not a retry ladder — controls timing. The client is localhost-only, so factory handler rotation buys nothing, and it is a process-lifetime singleton that is intentionally never disposed; the modest backstop `Timeout` on it sits above the probe's own per-attempt and reuse bounds.

`TryReadEffectiveContextTokensAsync` (AUD4-02) reads the server's **`/props`** `default_generation_settings.n_ctx` once after readiness — the effective per-slot context window the server actually loaded (the launched `-c` as clamped). The supervisor stores it on the running process; `GetRuntimeInfo(model, role)` / `ILocalModelProvider.GetRuntimeInfoAsync` expose it so the invocation runner can size **both** context budgeters (outer `TurnPolicy.ContextCapacityTokens` and inner `num_ctx`) against the real window, and the chat context-usage meter can show it (`LocalModelDetailsResponse.EffectiveContextTokens`). The same running process carries `ExpertsOffloaded`, set when its final argv pins MoE experts to the CPU (`--cpu-moe`, or a replayed `-ot …exps=CPU`); it reaches `model-fit/running`, model details and the hardware profile's `gpuExpertsOffloaded`, because llama.cpp's own banner still says "offloaded 41/41 layers to GPU" for such a launch and the layer counts alone read as fully on the GPU. Best-effort — a `/props` failure just leaves the effective context unknown (the app falls back to its default window).

The provider owns every other native route the application reads, too: `ILlamaServerNativeClient` (`Contracts/`)
serves `/metrics` (the benchmark harness's Prometheus scrape, parsed by `LlamaServerMetrics`), `/props` (the training
smoke gate's chat-template check), `/tokenize` and `/v1/messages/count_tokens` (token-estimator calibration: the chars-per-token divisor and the chat
template's tool preamble, over their own redirect-free, proxy-free client) and the pooled `embeddings`/`rerank` benchmark POSTs. `/props` has ONE parser, `LlamaServerProps.ReadAsync`,
shared by this probe and that client. The callers keep their decisions, timeouts and error mapping; the client only
speaks the protocol. `ILlamaPerplexityRunner` runs `llama-perplexity` for benchmark fidelity the same way.

## Reuse-path liveness, retry classes and the two HTTP network floors

**Reuse-path liveness.** A reuse is handed out immediately, with no HTTP call, unless `ReuseLivenessProbeInterval` (5 s) has passed since that process was last probed — at most one `/health` probe per process per interval, never one per request. A single probe is bounded by `ReuseLivenessProbeTimeout` (2 s) so a server that accepts the connection but never answers cannot stall the hot path for the whole `HttpClient` timeout; exceeding it counts as a failed probe. Only `MaxReuseLivenessFailures` (3) **consecutive** failures tear a wedged process down and respawn it, and one success resets the count, so a single transient failure never evicts a busy server.

**Three failure classes, not one counter.** A readiness TIMEOUT — the process is alive but slow — is a deterministic property of a large model on a cold cache, so retrying it many times only multiplies kill/reload thrash: `MaxReadinessTimeoutRetries` defaults to **1**. A transient start failure still gets `MaxRestartAttempts`. A process exit during load is a deterministic crash and stays non-retryable regardless of either value.

**Two HTTP network floors.** Both are set EXPLICITLY on the built OpenAI client so neither inherits System.ClientModel's 100 s `NetworkTimeout` default, which would abort a legitimately long local generation. `HttpNetworkTimeout` (chat) is **3600 s**, deliberately generous: streaming inter-token stalls are already bounded by the invocation's stream-idle watchdog and a non-streaming sub-agent completion by the per-request invocation deadline, so this is only the outermost floor against a wedged socket and must not pre-empt a slow-but-progressing model. That value is also the CEILING of the node-level "Maximum message request timeout" (`StoredNodeSettings.MaxMaxMessageRequestTimeoutSeconds`); `Providers.LlamaServer` references only `Providers.Abstractions` and cannot reference that constant, so the two are kept in step by hand — a shorter default silently pre-empted an operator who had raised the message timeout, handing them a socket abort from the inner HTTP timeout first. `EmbeddingHttpNetworkTimeout` is **600 s**, shorter on purpose: an embedding call (knowledge ingestion, memory extraction) carries no per-request invocation deadline, so its HTTP timeout IS its only bound and a wedged request must fail in minutes, not an hour. The SDK retry layer is pinned OFF independently of both, because a local chat completion is non-idempotent and must never be re-issued.

## Eviction & reaper

- `LlamaServerSupervisorOptions`: `MaxLoadedProcesses`, `IdleTimeToLive` (default **15 min**), `TransientIdleTimeToLive` (default **2 min**, clamped to at most `IdleTimeToLive` by `EffectiveTransientIdleTimeToLive`), `PortRangeStart`/`PortRangeEnd`, `MaxRestartAttempts`, plus the Audit-4 readiness/eject knobs — `ReadinessBaseTimeout` (default 120 s), `ReadinessTimeoutModelSizeThresholdGiB`/`ReadinessTimeoutSecondsPerGiB`/`ReadinessTimeoutCap` (size-aware deadline), `MaxReadinessTimeoutRetries` (default 1 — a readiness timeout is retried at most this many times, NOT `MaxRestartAttempts`), and `EjectDrainTimeout` (bounded graceful-eject drain). `Validate()` fails fast on structurally invalid values. The host overrides cap/TTL/launch-flag knobs from node config (`AddNodeModelRuntimeExtensions.BuildSeededLlamaServerSupervisorOptions`).
- `ReapIdleLoopAsync` runs on a background loop (interval = the shorter, transient TTL / 4, min 1 s) and evicts processes already exited or idle beyond their own TTL: `IdleTimeToLive`, or the transient TTL for a transient process (below). Idle time runs from the end of the last use: `LastUsedUtc` is stamped when a request starts (ensure, reuse, lease) and again when its inference lease is released, and the release stamp never changes the transient mark. A leased process is still skipped, since a request can outrun the idle window while it runs.
- `TryEvictIdleLeastRecentlyUsed` runs synchronously under the admission gate to free a slot for a new admission. It prefers exited or past-TTL entries, may let an unleased in-window embedding/reranker or transient process yield to a new load, and never selects an in-window interactive chat process or a live leased/profiling-pinned process.
- `TryEvictIdleChatForMemoryAsync` frees MEMORY, not a slot: the chat load admission below calls it when a cold chat model does not fit beside the residents. Its victim is the least-recently-used live CHAT process with no active lease — including an interactive one still inside its idle window (operator decision, 2026-10-05: a chat load may unload any chat model no request is using). It never takes the requesting key, a process still awaiting its first lease for a short grace period after readiness (`RunningProcess.AwaitingFirstLease`, `FirstLeaseGracePeriod` = 30 s: registered at readiness, before the request that spawned it leases it, so two concurrent cold loads cannot evict each other; bounded because a warm-only load never leases), a profiling-owned or pinned process, an embedder or reranker, or a protected model (the keep-warm model while keep-warm is on). Image (`sd-server`) and whisper residents are never evicted: they count only through the global free figure. It reuses the cap path's `TryBeginEvict` claim, detach and out-of-gate kill, and logs each eviction at Warning.
- A child that dies or is killed from outside the node (a crash, or another checkout's stale-process reaper sharing the binary path) logs one Warning naming the model, role, pid and exit code, so a model that vanishes from the loaded list leaves a trace in the node log. The line comes from the shared `DetachProcess` step, whichever path notices the exit first: the admission prune, the same-key respawn, the idle reaper or an eject. It fires only for a child already dead at detach, because every deliberate removal detaches before it kills. The idle reaper's own eviction logs at Information and cap eviction at Warning.

**Transient residency.** A caller states a `ModelResidencyIntent` on `LocalModelSelection` (default `Interactive`); `DefaultConfigDraftService`, the AI Assist drafts for agents, skills and image prompts, passes `Transient`, and `DeferredLlamaServerChatClient` hands it to `EnsureRunningAsync` and `TryAcquireInferenceLease`. `RunningProcess.IsTransient` is set only when a Transient request SPAWNED the process, and is carried by the in-flight spawn record, so a draft cancelled during a cold load still leaves a registered, transient process: the spawn outlives its callers. Any Interactive touch clears the mark for good: an ensure, a reuse, joining the in-flight spawn, a lease, keep-warm, and every caller that passes no intent. A process that already existed is never marked, so a model the operator was chatting with keeps its normal lifetime when a draft borrows it. The mark shows as `isTransient` on `GET model-fit/running`, next to `isBusy` and `lastUsedUtc`. Why: a model loaded only for a short helper call should not hold multi-GB of memory for a full interactive window. Housekeeping that leases a model on its own, such as `LlamaTokenEstimatorCalibrationService`, passes `Transient` too: it runs right after every chat request, so an interactive lease there would clear the mark of every draft-loaded model.

**The cap is measured by the reserved-PORT count, not the registered-process count.** A port is allocated under the admission gate and held until the process registers, fails or is evicted, so the count already includes in-flight spawns; counting registered processes instead would let two concurrent distinct `(model, role)` spawns, which take distinct ensure-gates, both pass the check at count *N* before either registers and overrun the cap.

**Victim ranking** inside `TryEvictIdleLeastRecentlyUsed`, best first: rank **0** is exited or idle past its TTL in any role, which the reaper would take anyway; rank **1** is an in-window but unleased POOLED role (embedding or reranker) or TRANSIENT process. Pooled roles earn that demotion because background indexing and search touch them continuously, so on the default cap — 3, the number of roles — they otherwise pin every slot and a foreground chat model switch hard-fails for up to a full TTL window with "maximum number of local models are already loaded", the most likely user-visible runtime failure on consumer hardware; a pooled reload costs about a second against a chat reload's tens of seconds, so the pooled process yields. A transient process yields for the reason it is transient: nobody chose to keep it, it was loaded for one helper call that has already ended (it is unleased), and holding a slot for it would fail the operator's next real load. An in-window INTERACTIVE CHAT process is never a cap victim (the memory eviction of a chat load is the one path that may take it): keep-warm recency protection is deliberate there, the cheap error beating the silent eviction of a multi-GB model the user is about to reuse, and admission rejects when no rank qualifies. A better rank always wins, and within a rank the least-recently-used one does. The scan itself is a best-effort heuristic read; the atomic claim is `TryBeginEvict` on the chosen victim, and if a request took a lease in between, no victim is admitted that round and the caller surfaces the cap error rather than tree-killing a process under an active lease. A lost removal race — a concurrent eject or reap already detached the victim — frees no slot of this call's doing, so it reports no admission rather than letting the cap be overrun on someone else's teardown.

**Chat load admission.** A cold chat spawn passes the capacity gate inside the supervisor, exactly once: `DecideEnsureAsync` calls the `ILlamaServerPooledLaunchAdmission` hook after the reuse and join arms, so a turn on a resident model and a caller joining an in-flight load are never admitted again. Every chat spawn path reaches it, since `EnsureRunningAsync` is the only serving spawn path (exclusive profiling spawns on its own). The hook is skipped when a caller already published an admission for the key — a sub-agent dispatch decides on its own, and a second decision would reject on that admission. `PooledRoleLaunchAdmission.AdmitChatAsync` then loops, with every eviction OUTSIDE the capacity decision gate:

1. Decide at the full tier (`CapacityRequest.AllowAdmissionDownTier = false`). The supervisor's own loaded cap and its cap eviction still own the process count (`SupervisorEnforcesProcessCap`), so an idle embedder or reranker keeps yielding a slot to a chat switch as before.
2. On a memory shortfall (`CapacityDecision.IsMemoryShortfall`), unload one idle chat process as above, re-probe global free VRAM with forced refreshes until it rises or about 3 s pass (a killed process releases its VRAM asynchronously), and decide again.
3. When no process is idle but one was skipped ONLY for its active lease, the eviction callback reports it busy (`IdleChatEvictionResult.BusyModel`) and the hook polls the eviction once a second until it unloads that process or `BusyResidentWaitCap` (60 s per admission) has passed, logging one Information line when the wait starts. Why: chat turns are serialized node-wide, so a turn on another model starts right after the previous turn, while that model's post-turn background request (memory extraction) still holds a lease for a few seconds; refusing then would refuse the ordinary model switch. A protected, profiling or grace-period process is not a candidate at all and never causes a wait. The wait holds neither the reaper's admission gate nor the capacity decision gate, only the requesting key's ensure gate, so it delays only other ensures of the same model, which would wait for that load anyway.
4. With nothing left to unload, or a resident still busy at the bound, decide with the smaller windows allowed: the walk goes down every chat tier to the smallest. If no tier fits, the load is refused with the capacity reason that names the loaded models ("Eject one of them or pick a loaded model"), thrown as a non-retryable `LlamaRuntimeException`, as for a refused pooled role. The smaller window rarely rescues a large model: the estimate is weights plus KV with a 12 % margin plus a fixed runtime overhead, so for a model whose weights dominate (a hybrid-attention MoE) every tier stays within about 1.5 GB of the full one.

**Only a load a user is waiting on may unload.** Steps 2 and 3 run only for a user load. A caller doing work no user waits on passes `ModelResidencyIntent.Background`, which keeps the `Interactive` idle lifetime (it clears a transient mark like any non-transient touch) and is read in one more place: the supervisor passes `mayUnloadIdleModels: false` to `AdmitChatAsync`, so the load decides at the full tier, then at the smaller windows, and is otherwise refused; it never unloads or waits for a resident. The spawn carries the intent on to the loaded-process cap: there `TryEvictIdleLeastRecentlyUsed` skips every live chat-role process for a background spawn, whether idle past its TTL or in-window transient, so the spawn may still reclaim an exited handle or take an embedding or reranker process exactly as a user load would, and with no such victim it is refused with the ordinary cap error ("maximum number of local models are already loaded"), a non-retryable `LlamaRuntimeException` like the capacity refusal. The capacity reservation taken just before is released when the spawn settles, refused or not. The background callers are memory extraction (`DefaultMemoryExtractionAgent`), automatic compaction and distillation (`ConversationMaintenanceWorker`, threaded through `IConversationCompactionService` and `IConversationStateDistillationService` to the summarizer and distiller inputs) and keep-warm (`ILocalModelProvider.WarmModelAsync` with an intent). Why: those jobs run on a configured or node-default model right after a turn; a load that unloaded the user's idle model between turns would make the user's next turn unload the job's model again, two full loads per turn. Each job already treats a failed load as its own failure: it logs a warning (keep-warm: debug, retried at its cadence) and the chat is unaffected. The admission is decided once per spawn, by the caller that starts it: a joiner never re-admits. A refused background load registers no in-flight spawn, so a user turn for the same model that queued behind it on the ensure gate runs its own admission with unloading; a background load admitted at a smaller window stays at that window when a user turn later reuses it, until the model reloads.

One Information line records the final decision: model, user or background load, verdict, global free MiB at the decision, footprint GPU MiB, window, placement and evicted models. A memory-shortfall reject carries the last candidate it tried (`CapacityDecision.Admission`, report-only), so a refusal logs the figures that did not fit rather than nulls. A node with no global free-VRAM reading — CPU-only, a silent CPU fallback, a non-NVIDIA GPU — skips the hook entirely: no eviction, no refusal, today's launch. **The two VRAM figures stay unmerged:** admission compares the footprint against the GLOBAL free reading (`HardwareProfile.AvailableVramBytes`, §3), while the tier and placement that footprint describes were sized by `ProcessContextAllocationResolver` against the PROCESS budget (`--list-devices`, §2.5). Under WSL2 the process budget does not shrink when other processes hold VRAM, which is why a chat load used to pick its full window beside a resident model that held most of the card; the process budget is still not clamped to the global figure, the global figure only decides whether that allocation may launch now.

**`DetachProcess` is the ONLY place a process leaves the table**, so it is also the only place the measured layer placement is retired: cap-admission eviction, the idle reaper, exited-process pruning, operator eject (drained and forced), wedged-process respawn, the pre-respawn reap of a dead entry, the profiling teardown and shutdown all funnel through it. Retiring the placement matters because the reading described THAT process and the report ranks any partial reading above every full one, so leaving it behind would keep telling an operator that a model they unloaded is running partly from system RAM, for the rest of the app's lifetime and even while the model actually loaded is fully GPU-resident. **Invariant:** the port reservation is dropped there, before the child is killed, so the reservation set that bounds the cap never counts a process on its way out. That does not hand the next spawn a port the dying child still holds, because `LlamaServerPortAllocator.Allocate` bind-probes every candidate and skips one that is still bound — the bind probe was always the real guard, since `TreeKill` (`kill(-pgid)`, or closing the Windows job) returns before the OS reclaims the socket, so releasing the port after the kill never proved availability either.

**Tree-kills always happen OUTSIDE the admission gate**, because killing a multi-GB model is slow enough to serialize every unrelated model's admission behind it; the gate serializes exactly three things — the cap decision plus port allocation, the release of a reservation for a spawn that never registered, and the detach half of a removal. An admitting spawn still awaits its own victim's death before it launches, so the VRAM the victim held is genuinely released first, and `RemoveProcessAsync` likewise awaits the kill because callers (notably the profiling path's ambient-VRAM baseline) rely on the child being gone when it returns.

The supervisor's present lifecycle boundaries and remaining concurrency risks are mapped in the read-only
[Llama server process supervisor decomposition report](../../audits/2026-08-22-llama-server-process-supervisor-decomposition.md).
That report authorizes no production refactor; the existing launch composer, idle reaper, port allocator, and runtime
mutation gate remain the implemented seams.

## Startup orphan reap and spawn receipts

A hard kill of the node skips that teardown. On Windows the Job Object still takes the child down with the host; on Linux a `setsid` child survives, reparented to init, still holding its port and VRAM. A startup `StaleProcessReaper` (`Providers.ProcessSupervision`), one per runtime (`llama-server`, `sd-server`, `whisper-server`, each registered in its provider's service-collection extension), reaps such orphans two independent ways, and nothing else:

- **Managed-root path match** (every OS, unchanged): a server whose executable is under the app's own binaries root for that runtime. It covers orphans from builds that predate receipts, and it is also why two hosts must not share a managed binary path.
- **Spawn-receipt match** (Linux): right after `_launcher.Launch` returns, every spawn hands the handle to `ProcessSpawnReceiptStore.TrackAsync`, which writes `runtime/<server>/<pid>.json` under `INodeDataDirectory.Root` (atomic, `0600`): the pid, its `/proc/[pid]/stat` start time, the realpath of the binary launched (from the spec, since a `setsid` child may not have exec'd yet) and a model/role/port label. The returned handle removes the receipt when disposed, after the child is torn down, and every exit path disposes it. The writers: `LlamaServerProcessSupervisor.SpawnCoreAsync` (eviction, idle reap, exited-process prune, eject, same-key respawn, profiling teardown and `DisposeAsync` through `KillDetachedProcess`, plus the cancelled and failed spawn catches); `ImageServerProcessSupervisor.SpawnOnceAsync` and `WhisperServerProcessSupervisor.SpawnOnceAsync` (every detach ends in `KillDetachedProcess` / `KillDetached`, plus the spawn catch; a whisper in-place model switch keeps the same process and so the same receipt); and both `TransientLlamaServerLauncher` spawns (`RunAsync`, `RunEvaluationAsync`), whose `finally` disposes the handle whether the body returned or threw. Each runtime registers ONE store as a keyed singleton under its server name, so the llama-server supervisor, the transient launcher and the llama-server reaper share one instance. A receipt on disk therefore means the host died with the child alive. At startup a receipt is resolved by its pid, not through the name-filtered process scan, so a bring-your-own binary with any file name still matches: it is acted on only when the pid is live, is not this host's own child, its `/proc/[pid]/exe` realpath equals the recorded one and its start time equals the recorded one; the start time is re-read immediately before the single `SIGKILL` (to the group when the child leads it). Any partial match, an unreadable `/proc` entry or an unparseable file signals nothing and deletes the receipt. Because receipts live in one node's data directory, this covers a bring-your-own binary outside the managed root without claiming another host's process of the same binary.

Receipts are best-effort (a write failure logs and leaves the untracked handle; the spawn proceeds), Linux-only (macOS has no cheap `/proc` start time, so it keeps the path match alone) and off in a provider-only host that registers no `INodeDataDirectory`. The residual read-then-signal window is microseconds; `pidfd_send_signal` is the upgrade that closes it.

## DI wiring

`LlamaServerServiceCollectionExtensions.AddLlamaServerLocalModelProvider` registers the whole stack as singletons via `TryAdd*`: vendor probe, variant selector, the live catalog + installed-runtime store + update state, the binary manager (built by factory with `cacheRoot/activeTag = null` so it self-defaults), default supervisor + external-endpoint options, the launcher and health probe, the **`DefaultInferenceProfileResolver`** (TryAdd, see §2.5), the source-build stack (§2.6: the prerequisite probe, the `LlamaCppSourceBuildService`, the no-op event publisher, `ILlamaCppSourceBuildActivity`, `ICudaManagedBuildSignal`, and the `CudaBuildStartupService` hosted service), and the supervisor itself (explicit factory because its ctor is internal). The host must register an `HttpClient` (`AddHttpClient`) for binary downloads and supply an `IGgufModelStore` (the HuggingFace GGUF store).

**Which HTTP client each seam gets is a correctness decision, not a style one.** Under Aspire, `AddServiceDefaults` installs the standard resilience handler on *every* client through `ConfigureHttpClientDefaults`, so a registration that says nothing inherits blanket retries and a pipeline-owned deadline.

- The **release catalog and the binary manager** stay on the host's shared default factory client, and that is a deliberate KEEP: everything they issue is an idempotent catalog or download GET against GitHub, exactly the shape the standard pipeline helps, where a retried GET costs a second read and never a second side effect.
- The **reranker client** gets its own named client with `RemoveAllResilienceHandlers` (a no-op outside Aspire), because sharing the default client was wrong twice over: `/v1/rerank` is a non-idempotent POST, so a retry makes a cross-encoder score the whole pool a second time on the operator's own GPU, and a pool that legitimately outruns the pipeline's per-attempt timeout is severed by that timeout rather than by the client's own budget. The explicit `HttpClient.Timeout` set alongside it is NOT redundant and must not be dropped: `AddStandardResilienceHandler` sets `Timeout` to `Timeout.InfiniteTimeSpan` — its pipeline owns the deadline instead — and `RemoveAllResilienceHandlers` removes the HANDLER, never that mutation, so a client that only strips ends up under Aspire with no pipeline AND no client deadline. It is FINITE rather than infinite, unlike the proxy and the whisper runtime client, because the per-call timeout override the reranker's constructor accepts is unbounded, so "the caller's own deadline always applies" is not a property this registration can guarantee. It sits above the client's own ceiling (`LlamaServerRerankerClient.ResolveRequestTimeout` caps the linked-token budget), so in production that budget still fires first and the degrade-to-fusion-order path stays reachable; `LlamaServerRerankerResilienceTests` pins that ordering.
- The **readiness/liveness probe** bypasses `IHttpClientFactory` altogether — see [Health probe — readiness vs liveness](#health-probe--readiness-vs-liveness).
