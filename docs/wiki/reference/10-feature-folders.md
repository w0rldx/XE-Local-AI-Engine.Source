# React Feature Folders

> Reference page for [React Client](../10-react-client.md) "The feature folders" · Code-grounded.

It lists every first-level directory under `src/features/`: what it owns and which wiki page explains the behavior behind it. The shared shape of a feature folder and the route and capability wiring stay in the parent page.

## The feature folders

Source: the first-level directories under `XE-Local-AI-Engine.Client.React/src/features` — `ls -d src/features/*/` is the inventory; the table below names all of them.

Read-only: deleting a run, deep-linking to its conversation and reading its logs are later slices. Like `/invocations` and `/usage` it carries no extra route guard and no capability flag: the authenticated `_layout` *is* the operator gate, and a node with AgentHome switched off simply has an empty history | [Agent Mode](../04-agent-mode.md) |

| `chat` | Streaming chat UI, SignalR adapter, reasoning/tool-call rendering, sampling options, file-upload attachments + pane drag-and-drop (`usePaneFileDrop`, `ChatAttachmentChips`), manual compaction (`CompactButton`) and the read-only distilled-state drawer (`ContextStatePanel`) | [Chat](../05-chat.md) |
| `cloud-providers` | **Cloud Providers** at `/cloud-providers`, the one Settings entry for every cloud or remote provider; `/cloud-settings` and `/external-providers` only redirect here. The page lists the configured providers from their three stores, composed on the client with no summary endpoint: each `ext:` connection, the Azure AI Foundry slot when one is stored, and the Codex session when signed in. "Add provider" offers templates gated by capability: two OpenAI-compatible ones (generic, Azure OpenAI v1 with a key; `externalProviders`) that open the same empty connection form and differ only in the editor's hints, and Azure AI Foundry and ChatGPT (Codex) (`cloudSettings`), each disabled while its single slot is taken. The connection editor (`external/`): display name, base URL, the declared Local/Cloud trust (with the warning shown when Local is declared for a host that is neither loopback nor private), a write-only API key with an explicit "Remove key" action, and the timeout, the per-model registration rows (backing model id, display name, context length, declared tools/vision/reasoning capabilities and a reasoning-effort default), and the connect-time probe with pick-to-add. Its writes are optimistic-concurrency guarded: a 409 carries the whole stored configuration, which the page renders in place of a refetch. The Azure editor with its Entra sign-in cards (`azure/`, `entra/`) and the Codex sign-in card (`codex/`) keep their own credentials node-local. Stores and model ids are unchanged: the page merges the UI, not the stores | [Local Runtime & Providers](../03-local-runtime-and-providers.md), [Security & Privacy](../12-security-and-privacy.md) |
| `commands` | Automation-command catalog backed by `automation/commands`; list/detail queries use the generated SDK | [API & Hubs](../09-api-and-hubs.md) |
| `command` | **Command page** at `/command`: a text box, a mic button and Enter. Enter posts the sentence to `graph-workflows/intents/invoke`; a started run is followed over `graph-workflows/hub` with a link to the run view, and an unmatched sentence goes to the default agent as a new conversation over the chat hub's `SendMessage` stream, its reply shown inline with an "Open in chat" link (through `PendingChatConversationStore`). The mic starts an ephemeral dictation session (`transcription/dictation-sessions`), pushes microphone frames over `transcription/hub` and appends committed segments to the box; partials only show. The route sits **outside** `/_layout` (no sidebar or header) because the desktop overlay window loads it at 520×220; it runs the same sign-in chain (`guardFirstRun` in `core/auth/utils/FirstRunGuard`, without the external-access step) and has a home button for a browser tab. Results are memory only | [Graph Workflows §11](../21-graph-workflows.md#11-intent-routing) |
| `customTools` | Operator-authored HTTP-fetch and host-program tools: list, create/edit form, danger acknowledgement, enabled state, secret header/env masking, and desktop executable probe | [Security & Privacy](../12-security-and-privacy.md#custom-tools-operator-authored-execution-boundary) |
| `development` | **Development Mode** operator surface at `/development`, surfaced under the "Preview" nav group (alongside Image Generation) because it is an experimental surface: project creation bound to a registered Git repository (`DevelopmentProjectForm`), the task/attempt workflow, and `DevelopmentLivePanel` streaming live attempt output over `DevelopmentAttemptHub` (`hooks/useDevelopmentAttemptHub.ts`). The page resolves the authenticated server capability (`development/capability`) before exposing projects or actions, so a backend kill switch fails closed without a separate frontend build | [Architecture Overview](../01-architecture-overview.md#development-mode-registered-source-managed-worktree) |
| `externalApps` | **External Apps** at `/external-apps/catalog`, `/external-apps/installed` and `/external-apps/instances/{instanceId}` (`/external-apps` redirects to the catalog). The catalog page owns `RuntimeStatusCard` — the one place the container runtime is named, gated on the server's `requiresOperatorConfirmation` and posting the **observed daemon id** it displayed — and `InstallDialog`, a four-step disclosure (permissions → settings → resources → installing) whose acceptance is bound to the `(manifestVersion, manifestSha256)` pair the operator was shown: any later preview carrying a different pair clears it and returns to step 1. `PermissionsPanel` states network access as fact rather than denial (V1 enforces no outbound restriction) and renders the server's four application-level aggregates plus one block per part, never a union computed here. The installed list reads addresses and row actions straight off the widened `ExternalAppInstanceView[]`; the detail page is driven by `instance.manifest` alone, so **no catalog query is mounted on it**. Every lifecycle call echoes the row's `version` as `expectedVersion` (uninstall as a query parameter, it has no body) and Cancel is the only action offered while an instance is busy. `useExternalAppHub` subscribes one instance over `external-apps/hub`, reads only the ping's `sequence` — never its lowerCamelCase `kind` — and keeps pull progress in local state, because a query per layer would turn a multi-gigabyte pull into a request storm | [External Apps](../23-external-apps.md) |
| `directInference` | **Direct inference** at `/direct-inference` (Models nav group, Advanced only): one optional system prompt plus one prompt to a chosen local, external or cloud model, with the shared sampling fields, no agent, tools, history, persona, memory or knowledge base, and nothing saved. It streams over the chat hub's `StreamDirectInference` (contract types hand-written in `core/directInference/DirectInferenceModels.ts`; the stream, the output view and the sampling fields live in `core/directInference/` because Model Lab shares them) and shows the answer, the reasoning, the token usage and, for a llama-server model only, its prompt/generation timings. For a llama.cpp model the Max output tokens field states the server's default cap and that thinking counts toward it (other models have no default), Stop goes idle at once even while the hub is still connecting, and a `length` finish reason shows that the answer was cut off. A llama.cpp model can also return token probabilities (1 to 20 alternatives per entry): `DirectInferenceLogprobs` lists what arrived, labelled as pre-sampling model output, keeps the first 500 entries of each kind, reasoning and answer, and states what it left out, and never treats an entry as a token. For a reasoning-capable llama.cpp model (`reasoningLlamaCppModels` from `useDirectInferenceModels`) a Thinking off switch (`DirectInferenceThinkingSwitch`) sends `disableThinking: true`; it starts off, so the model's default applies, resets when the model changes and is hidden for any other model. A Thinking budget field (`reasoningBudgetTokens` in the sampling options, 128 to 131072) shows for a model in `budgetLlamaCppModels` while Thinking off is not set, and resets with the model. Probabilities are labelled as percentages in the app language | [API & Hubs](../09-api-and-hubs.md) |
| `modelLab` | **Model Lab** at `/model-lab` (Models nav group, Advanced only): the Architecture, Next token, Inspect, Same-prompt A/B, Trace and Training stepper tabs; what each tab shows and reads: [Model Lab reference](25-model-lab.md#the-modellab-feature-folder) | [Model Lab](../25-model-lab.md) |
| `diagnostics` | **Local-only** frontend error diagnostics at `/diagnostics`. Snapshots never leave the browser on their own; the feature calls two backend endpoints only when the user exports or opens an issue (`diagnostics/support-bundle`, `diagnostics/node-info`). `SnapshotStore.ts` is an **IndexedDB** store (`idb`, DB `xe-diagnostics`) holding at most 25 snapshots / 25 MB, with retention enforced *inside* the same readwrite transaction as the write so eviction is atomic. `DiagnosticsPanel` lists/inspects snapshots; `BreadcrumbTimeline`, `NetworkLog` and `RrwebReplay` render one; **Export is one merged zip**: `SupportBundle.ts` (lazy-loaded) downloads the server's scrubbed bundle as a blob, adds `snapshot.json` next to the server entries (`manifest.json`, `node-info.json`, `logs/*`, `processes/*`) and saves `xe-support-<snapshot id>.zip`; if the server half fails for any reason it falls back to the browser-only zip (`ExportSnapshot`) and shows a toast. Import still reads `snapshot.json` from either shape. An **Open GitHub issue** button (`IssueUrl.ts`, fed by `useNodeInfo`) opens a new tab on the repository's `bug_report.yml` form prefilled with version, OS, browser and hardware; nothing is sent, and the user attaches the zip by hand. `AppErrorFallback` offers the same two actions (export the newest stored snapshot, open the issue). Reached from the header/mobile nav bug button (`ReportProblemButton`), which captures a snapshot and opens the page; the page header also has **Report a problem**, **Import** and **Open GitHub issue**, and each snapshot row has **Export**. The page also carries a **Verbose logging until restart** switch (strings `diagnostics.verboseLogging*`) that reads and sets `diagnostics/log-level`; the intended flow is switch on, reproduce, then export, and the node turns it off by itself at the next restart. Collectors and redaction live in `core/diagnostics/`. **The app never transmits anything**: export writes to disk, the issue link only opens a tab | `diagnostics/node-info`, `diagnostics/support-bundle`, `diagnostics/log-level` |
| `graphWorkflows` | **Graph Workflows** at `/graph-workflows` (one route; the definition, run, node and tab selections live in **search params**, so a view is linkable). A React Flow editor for the twelve node kinds (`Start`, `Agent`, `LlmCall`, `Tool`, `Condition`, `Parallel`, `Join`, `Pause`, `End`, `ChatInput`, `DecisionModel`, `DevTask`; [21 §4](../21-graph-workflows.md)) with an **Assistant** tab beside the Inspector (editing, generating and reviewing states; a proposed graph is accepted into the canvas with one Undo, [21 §12](../21-graph-workflows.md)), plus a read-only run view over the pinned graph — node runs, the Pause decision panel, node input/output documents and the event trail — and `useGraphWorkflowRunHub`, whose content-free `graphWorkflowChanged` ping invalidates the run's queries. Ships **on** (`nodeCapabilities.graphWorkflows`) as a **top-level** navigation entry. `useUnsavedChangesGuard` is set with `allowSameRoute`, so writing a search param does not trigger the leave prompt while a real route change still does | [Graph Workflows](../21-graph-workflows.md) |
| `home` | **Home** at `/`, the landing page and the first nav entry (`matchesNavRoute` matches `/` only exactly). A fixed `SimpleGrid` of plain cards, each handling its own loading, empty and error state: the welcome card (local-clock greeting, "New chat" and "Continue last chat", and while `hasAnyChatModel` finds nothing, the install hint plus the first-run download from `useActiveGgufDownloads`), the Activity card over `core/operations` (running and failed operations, Simple and Advanced, absent when idle), recent chats (`GET chat/conversations` re-sorted by last activity, because the server lists pinned threads first) and, in Advanced mode, a 30-day usage card over `agents/usage-summary` sharing `core/usage/UsageDateRange.ts` and `core/formatting/NumberFormatting.ts` with `/usage`, plus an Upcoming card over `scheduler/upcoming` (next five fires; absent when the `scheduler` capability is off or the route answers 404 because the node's switch is off; refreshed by the scheduler's job mutations invalidating its key and a 60 s poll, since Home holds no scheduler hub). The What's New card (Simple and Advanced) reads the shared `app-update/status` entry and, only when `isDesktop`, `app-update/release-notes`; it renders the first item (the running version when the feed has its notes) through `core/ui/components/MarkdownView` with images as links, clamped by a Mantine `Spoiler`, names the newest `isNewerThanRunning` item, and is absent while `items` is empty. Opening a conversation or a new chat hands the intent to `/chat` through `core/ui/stores/PendingChatConversationStore.ts`; Home imports no other feature | — |
| `images` | Local text-to-image at `/images`, surfaced under the "Preview" nav group (alongside Development Mode) because the runtime is not yet confidently verified end-to-end: generation form, job list/cards, result view, installed-model manager, plus `useImageJobHub` (subscribe-then-replay, dedupe on `seq`) and `useImageObjectUrl` (fetches the encrypted PNG as a `Blob`) | [Image Generation](../14-image-generation.md) |
| `integrations` | **External Integrations** operator surface: `/integrations/triggers` (the named external entry points that run a saved agent unattended over the loopback integration API — list plus an editor dialog whose `name` slug is validated live because it is the integrator's URL) and `/integrations/keys` (the `xeint_` credentials, with a show-once reveal held in component state and never in a store or the query cache, a `principalId` identity column and an identity picker for rotating a credential without stranding an integrator's sessions). The trigger editor derives its approval warning and its `CallerManaged` preflight CLIENT-side from `listAgentDefinitions` ∩ `getToolCatalog`, tighten-only and **fail-closed**: a tool name absent from the live catalog counts as approval-requiring and as side-effecting. The allowlist switch is the only thing that produces the all-triggers wildcard — an empty multiselect is a validation error, never a grant. The group's index route only redirects. `/integrations/executions` lists active and historical runs with one status chip per state, a cancel action on active rows and a detail dialog whose timeline reads the persisted events whole; `/integrations/sessions` lists the caller-managed conversations with both filters server-side and a delete that refuses while an execution is still active. Both lists are a single bounded server window with no page navigator, because neither response carries a total count | [API & Hubs](../09-api-and-hubs.md) |

| `transcription` | **Audio Transcription** at `/transcription` and `/transcription/{sessionId}`, under the "Preview" nav group: the session list and create/upload dialog, and a detail page rendering the committed transcript with a channel badge for any non-`Mono` segment. The audio upload is the one hand-written multipart call in the feature — `axiosInstance.post` with `Content-Type: multipart/form-data` and an upload-progress callback, following `features/knowledge/…/useKnowledgeUpload.ts`, because the generated client expresses no upload progress. "Send to chat" hands the transcript to the composer through `core/ui/stores/PendingComposerTextStore.ts`, a Zustand store whose `setPendingText`/`consume` pair exists to carry text **across a navigation**; dictation (a later slice) appends in place and deliberately does not use it. **Live capture** lives under `capture/`: `CaptureSource.ts` is the seam (`CaptureSource`, `CaptureFrame`, `CaptureError`/`CaptureErrorCode`, `listAudioInputDevices`), implemented by `MicrophoneCaptureSource` (`getUserMedia`) and `SystemAudioCaptureSource` (`getDisplayMedia`, whose video tracks are stopped immediately — the picture is never read). Both share `PcmCapture.ts`: one `AudioContext` per stream, `Pcm16DownsamplerWorklet.js` on it, and `source → worklet → zero-gain → destination`. The worklet is a plain `.js` file imported for its URL alone with Vite's `?url`, which puts it outside `tsconfig.json`'s `include` and knip's project set and means it must stay free of imports. `hooks/useTranscriptionHub.ts` owns the hub connection — `useTranscriptionHub` for the handle, `useLiveTranscript` for the push-fed query read — and `capture/useLiveCapture.ts` orchestrates the two, calling the hub hook itself so a page mounts exactly one. `components/LiveTranscriptPanel.tsx` and `components/CaptureControls.tsx` render the live half; `stores/TranscriptionCaptureStore.ts` is UI-only and persisted (last source kind, last device id, whether provisional text is shown) and never holds transcript data | [Audio Transcription](../24-audio-transcription.md) |

Like `/invocations` it carries no extra route guard: the authenticated `_layout` *is* the operator gate and the endpoint 401s otherwise | [Agent Mode](../04-agent-mode.md) |
| `voice` | Web Speech text-to-speech: node-settings feature gate, platform-voice catalog, preferences store, composer controls, per-message play button, and voice preview. Browser/OS voice behavior is outside repository control. | [Chat](../05-chat.md) |
| `workSessions` | Long-running agent work sessions at `/work-sessions` and `/work-sessions/{id}`: the list + create dialog, and a 3-pane detail page whose centre pane **is** `features/chat`'s `Chat` component. Owns `useWorkSessionHub` and the query hooks over the generated work-session operations. The list page and the detail page both read `work-sessions/capability` first and render `WorkSessionsDisabledAlert` — "disabled by this node's runtime configuration" — when an operator has turned the feature off, gating every query and the hub on it — the same page-level pattern `DevelopmentPage` uses. The one feature that deliberately composes another feature's page — see [Work Sessions: the chat-embed seam](../10-react-client.md#work-sessions-the-chat-embed-seam) | [Agent Mode](../04-agent-mode.md) |
