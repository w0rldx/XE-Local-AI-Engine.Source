# SignalR Hub Inventory and Event Names

> Reference page for [API & Hubs](../09-api-and-hubs.md) §2 · Code-grounded.

It lists every hub the `MapHub<>` block maps, with its path, direction and purpose, then each hub's event-name constants and payloads. Authorization, the JSON policy, the publisher pattern, chat-hub refusals and the bearer subprotocol stay in the parent page.

## Hub event-name contracts

A provider or Application service never names a hub method or shapes a frame: it publishes a neutral domain type (`RuntimeAcquisitionStatusEvent`, `LlamaCppSourceBuildStatusEvent`, `StableDiffusionCppSourceBuildStatusEvent`, `TrainingRuntimeStatusEvent`, `GgufAcquisitionStatus`, `ImageJobStatusEvent`, `SchedulerRunEvent` / `SchedulerRunProgressEvent` / `SchedulerDefinitionEvent`) and the `Client/Hubs` publisher owns the method name and projects the event 1:1 into a host wire type (`*HubMessage` in `Client/Hubs/*HubContracts.cs`), pinned frame for frame by `ProviderStatusHubWireTests` and `ApplicationHubWireTests`. Every event-name constant below lives in `Client/Hubs`.

Push hubs use **stable string constants as the SignalR client-method names**, doubling as the wire event-type discriminator so React can subscribe per event name:

- **Scheduler** (`SchedulerHubEvents` in `Client/Hubs/SchedulerHubContracts.cs`): `scheduler.jobDefinitionChanged`, `scheduler.runStarted`, `scheduler.runProgress`, `scheduler.runCompleted`, `scheduler.runFailed`, `scheduler.runCancelled`. The run payload (`SchedulerRunHubMessage`) carries an optional `manualFireId`: the id a manual trigger stamped on that fire, which `model-fit/recommendations/refresh` returns as `fireId`; null for a cron fire (added 2026-10-09, additive).
- **GGUF download** (`GgufDownloadHubEvents` in `Client/Hubs/GgufDownloadHubContracts.cs`): a single `ggufDownload.statusChanged` event; each push carries the sanitized `GgufDownloadStatusHubMessage` for one tracked download or import.
- **Source build** (`LlamaCppSourceBuildHubEvents` in `Client/Hubs/LlamaCppSourceBuildHubContracts.cs`): `llamaCppSourceBuild.statusChanged`. Each push carries the phase plus the appended log lines and their **sequence numbers**, so a client reconciles across ring-buffer rollover and reconnects rather than assuming a contiguous log.
- **Runtime acquisition** (`RuntimeAcquisitionHubEvents` in `Client/Hubs/RuntimeAcquisitionHubContracts.cs`): `runtimeAcquisition.statusChanged`, carrying a monotonic sequence and sanitized progress snapshot shared with the hydrate endpoint.
- **Runtime residency** (`RuntimeResidencyHubEvents` in `Client/Hubs/RuntimeResidencyHubContracts.cs`): `runtimeResidency.changed`, carrying only a monotonic `sequence`. It says "re-read the running and residents lists", trailing-edge coalesced (500 ms after the first change) with at least 4 s between pushes, so request churn (each inference ensures, leases and releases) costs no more than the 4 s poll it replaced.
- **Knowledge base** (`KnowledgeBaseHubEvents` in `Client/Hubs/KnowledgeBaseHubContracts.cs`): `knowledge.documentChanged`. Payload is document id + coarse status + timestamp only — deliberately no file name, chunk text, or failure detail. The ingestion service pushes each transition of a run (`Extracting` onward), and `Pending` when a run parks for an ejected embedder; the operations feed counts a batch from these pushes and keeps it open until every queued document is `Indexed` or `Failed`. Queueing a document never pushes a status: `knowledge.documentsChanged` (timestamp only) is the status-free refresh sent by every admission (`KnowledgeIngestionDispatcher.EnqueueAsync`: upload, repository import, a duplicate retried from `Pending` or `Failed`, reindex, scheduled model reindex) and by every stranded row that startup recovery or the drain sweep re-admits (`EnqueueStrandedAsync`). Even a row the caller just wrote or reset can be indexed by a drain sweep, or deleted by a purge, before the push lands, so a `Pending` push there could arrive after that row's `Indexed` or its removal and stick. A row the admission reads back as already gone, or written and already `Indexed` or `Failed`, gets the refresh and no admission (`KnowledgeIngestionAdmissionService`). The knowledge page refetches on the refresh without writing any status, and the operations feed ignores it, so every queued document joins a batch at its first real transition (`Extracting`). A repository import of N files sends N extra small pushes; they are not coalesced. `knowledge.documentRemoved` (id + timestamp) is pushed when `KnowledgeDocumentPurgeService` deletes a document, so the feed drops a member that will never reach a terminal status; the ingestion run's skip of a missing row needs no push, since only a purge deletes a queued row.
- **Job created** (`JobCreatedHubEvents` in `Client/Hubs/JobCreatedHubContracts.cs`): `job.created`, broadcast by `JobCreatedPublisher` to every connection of `training/runs/hub`, `training/datasets/hub` or `images/hub` when `TrainingRunService`, `DatasetGenerationService` or `ImageJobCoordinator` creates a job of that kind, when `StartModelLabExperimentEndpoint` starts a Model Lab experiment, or when `BaseArtifactDownloadCoordinator` starts a base checkpoint download (both on `training/runs/hub`). `job.ended` is the same broadcast when a base checkpoint download ends, whatever its outcome: that download has no group, while an experiment ends with its own `trainingRun.event` State event. Payload is the id and kind name only (`TrainingRun`, `DatasetBuild`, `ImageJob`, `ModelLabExperiment`, `BaseArtifactDownload`), so the three kinds sharing the training-run hub tell each other apart. A job's other events go to its group, so this is how an operations feed with no running work learns of a job another tab or an API caller started.
- **Image jobs** (`ImageJobHubEvents` in `Client/Hubs/ImageJobHubContracts.cs`): `imageJob.statusChanged`, carrying the coarse phase and a per-job monotonic `Seq` for replay/dedupe. The coordinator buffers domain `ImageJobStatusEvent`s, and the hub replay goes through the publisher's projection, so a replayed frame is byte-identical to the live one. **Never** carries the prompt, and there is no step/percent field (the runtime exposes none over HTTP). `imageModelDownload.statusChanged` is broadcast to every connection and carries one weight download's `ImageModelDownloadHubMessage` (`modelName`, `phase` as the `ImageModelDownloadPhase` name, byte counts, part framing, sanitized error), the fields of the REST download row, plus `sequence`. `ImageModelDownloadCoordinator` pushes the start and every terminal phase and at most one `Running` progress push per model per second. The pushes are fire-and-forget and can land out of order, so every status write takes one coordinator gate and stamps the next `sequence` (a new start always outranks the terminal state before it); the client drops a push whose `sequence` is not above the one it applied for that model.
- **Image runtime source build** (`StableDiffusionCppSourceBuildHubEvents` in `Client/Hubs/StableDiffusionCppSourceBuildHubContracts.cs`): `stableDiffusionCppSourceBuild.statusChanged`, carrying the phase, bounded appended log lines with their start sequence, sanitized terminal error, and build provenance.
- **Benchmark runs** (`BenchmarkRunHubEvents` in `Client/Hubs/BenchmarkRunHubContracts.cs`): `benchmarkRun.event` plus `benchmarkRun.replayReset`, the latter carrying `(RunId, LatestSequence, RunVersion)` so a client that cannot be caught up from the buffer re-hydrates from the run endpoint instead of rendering a hole.
- **Dataset generation** (`DatasetGenerationHubEvents` in `Client/Hubs/DatasetGenerationHubContracts.cs`): `datasetGeneration.event` / `datasetGeneration.replayReset`, same reset contract keyed on the dataset id and version.
- **Training runs** (`TrainingRunHubEvents` in `Client/Hubs/TrainingRunHubContracts.cs`): `trainingRun.event` / `trainingRun.replayReset`, same reset contract keyed on the run id and version.
- **Training runtime** (`TrainingRuntimeHubEvents` in `Client/Hubs/TrainingRuntimeHubContracts.cs`): `trainingRuntime.statusChanged`. Each push carries the install phase plus **only the log lines appended since the last push** and their start sequence, so a reconnecting client splices its local log at a known offset rather than re-rendering the whole ring.
- **Work sessions** (`WorkSessionHubEvents` in `Client/Hubs/WorkSessionHubContracts.cs`): a single `workSessionChanged` carrying `(SessionId, Seq, Kind)` to the group `work-session-{sessionId:N}`. It is a **notification, never a payload**: the client re-reads the named feed from that feed's own watermark, so a dropped push degrades to a late read rather than a wrong render. `Kind` is **lowercase on the wire** (`status|step|task|finding|artifact|checkpoint`), written out as literals in `WorkSessionEventPublisher.ToWireKind` rather than derived from the enum name — the client switches on those strings. The `seq` is the EVENT row's sequence, one above the content row's, which is why the contract is "something changed at N, re-read each feed from its own watermark" rather than "row N is in feed X". Beside each `status` push, `workSessionStatusChanged` carrying `(SessionId)` goes to every connection, for the app-wide operations feed, which watches no session and re-reads the session list; a stop of a session no running loop owns publishes its own `status` push, since nothing else announces that end.
- **Graph workflows** (`GraphWorkflowHubEvents` in `Client/Hubs/GraphWorkflowRunHubContracts.cs`): a single `graphWorkflowChanged` carrying `(RunId, Seq, Kind)` to the group `graph-workflow-run-{runId:N}` — the same notification-never-a-payload contract as the two above, and for the same reason: the client re-reads the run or its event feed, so a dropped push is a late read rather than a wrong render. `Kind` is **lowercase on the wire** (`run|node|gate`), written as literals in `GraphWorkflowEventPublisher.ToWireKind`. The publisher is a **store decorator** (`PublishingGraphWorkflowStore`), so one ping is emitted per committed mutation with the sequence that commit allocated; a run start and the startup reconciler publish nothing, because nothing is subscribed to them. The decorator's `TransitionRunAsync`, the one writer of a run's status, also broadcasts `graphWorkflowRunStatusChanged` carrying `(RunId, Status)` (the `GraphWorkflowRunStatus` name) to every connection, for the app-wide operations feed's list of runs waiting for a decision.
- **Transcription** (`TranscriptionHubEvents` in `Client/Hubs/TranscriptionHubContracts.cs`): `transcriptionSegmentCommitted` carrying `(SessionId, Seq, StartMs, EndMs, Text, Channel, Confidence)`, `transcriptionPartialUpdated` carrying `(SessionId, Channel, Text)` and `transcriptionSessionStatusChanged` carrying `(SessionId, Status)` `transcriptionCatchUpProgress` carrying `(SessionId, BufferedMs)`, `transcriptionAdmissionClosed` carrying `(SessionId)` and `transcriptionSourceQuiet` carrying `(SessionId, Channel, QuietMs)`, all to the group `transcription-session-{sessionId:N}`. These ARE payloads, not notifications, and deliberately so: a partial has no row behind it to re-read, and a committed segment reaches a persist-free dictation session that stores nothing at all. `Channel` is **PascalCase on the wire** (`Mono|You|Others`), written as literals in `TranscriptionMapper.ToWireChannel` and shared with the REST transcript rows — a resuming client merges the replay snapshot and the live pushes into one list by exact `Seq`, so the same field must be spelled the same way in both. `Status` is the end reason mapped by `TranscriptionEventPublisher.ToWireStatus` (`Completed|Cancelled|Abandoned|Failed`; `NeverAttached` reports as `Abandoned`). `BufferedMs` is the session's queued, untranscribed audio; it is advisory, is sent at most once per second of audio consumed while a lane is behind, once with `0` when caught up and once at the start of a graceful end, and never follows the status push. `QuietMs` is how long an in-host capture lane has had no audio, sent each second past a 10 s threshold and `0` when audio returns; it is non-terminal and never follows the status push. One event is not per session: `transcriptionModelDownloadChanged` (`TranscriptionModelDownloadChangedPush`: `modelId`, `phase` in the REST download row's lower-case spelling, byte counts, part framing, sanitized error, `sequence`) is broadcast to every connection for the app-wide operations feed; `WhisperModelDownloadCoordinator` pushes the start, every terminal phase and at most one `running` progress push per model per second, sequenced like the image downloads above.
- **External apps** (`ExternalAppHubEvents` in `Client/Hubs/ExternalAppHubContracts.cs`): `externalAppChanged` carrying `(InstanceId, Sequence, Kind, Status)` to the group `external-app-{instanceId:N}` — notification, never payload: the client re-reads the instance or its event feed from its own watermark, so a dropped push is a late read rather than a wrong render. `Kind` is **lowerCamelCase on the wire** (`installed|started|stopped|restarted|updated|reset|uninstalled|failed|startRequested|stopRequested|updateRequested|resetRequested|uninstallRequested|restoredOnBoot|stoppedUnexpectedly|permissionAccepted`), written as literals in `ExternalAppEventPublisher.ToWireKind` rather than derived from the enum name. `externalAppPullProgress` is the one message that is a payload — `(InstanceId, Service, LayerCount, CompletedLayers, Bytes)` — because there is no row behind it to re-read.
- **Development attempts**: the one hub that does **not** use a `*HubEvents` constant class — `DevelopmentAttemptLiveEventPublisher.PublishAsync()` sends the literal method name `developmentAttemptUpdate` to the group `development-project:{projectId:N}:attempt:{attemptId:N}`. The lossy `CommandOutput` kind (`DevelopmentAttemptLiveUpdateKind.CommandOutput`) carries one batch of a running catalog command's redacted lines in `outputDelta`, tagged with `currentCommandId` and `currentCommandExecutionId`; command started and completed updates carry the execution id too (the stop route's `{executionId}`) and `commandOutputSkippedLines`, the command's lines not shown live so far. `DevelopmentAttemptLiveBroker` lets command output fill at most half an attempt's channel, so a flood never makes one lifecycle update evict another. Validation has no attempt of its own: `DevelopmentAttemptExecutionSupervisor` streams its commands under the judged coder attempt (the task's latest, when it `Succeeded`) and ends that stream with a `Terminal` update whose activity reads "Validation passed.", "Validation failed.", "Validation was cancelled." or "Validation could not finish." before completing it.
