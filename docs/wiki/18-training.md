# Training (QLoRA fine-tuning)

> Reviewed: 2026-10-02 · Code-grounded.

**What this page covers.** QLoRA fine-tuning on the node: a teacher model generates a dataset, a run trains an adapter
on a Hugging Face base checkpoint, and the result is exported to GGUF, smoke-loaded, evaluated and promoted. Two
decisions shape it (ADR 0005): all training semantics live in Python under `tools/training/` in a uv-managed venv, and
a run holds the node exclusively through `IGpuWorkGate`. The C# side lives in `Providers.Training` and
`Client.Application/Services/Training/`.

**Read this if you are** changing the training pipeline, the Python runtime or its pins, or debugging a run that will
not start or finish. **Skip to** [§1](#1-the-python-runtime-uv-pinned-machine-global) for the runtime and
[§4](#4-training-runs) for runs; **reference tables** are in [Where the code lives](#where-the-code-lives) and
[§7](#7-endpoints-hubs-and-background-services); **related pages:** [Benchmarks](20-benchmarks.md), [Compute
Tools](19-compute-tools.md), [Model Fit](07-model-fit.md).

**Tier: experimental.** Training and Model Lab carry no 1.0 stability or API promise and may change or be cut
([feature tiers](../user-guide/docs/for-experienced-users.md#feature-tiers)).

The Training group lets an operator turn the node's own tool-calling behaviour into a **fine-tuned local model**, entirely on the host: a teacher model generates a supervised dataset, a QLoRA run trains an adapter against a downloaded Hugging Face base checkpoint, and the result is exported to GGUF, smoke-loaded, evaluated from staging, compared against its installed base, quality-decided, and only then explicitly promoted into the local model registry. Nothing leaves the node except the two explicit downloads (the Python wheel closure and the base checkpoint).

Two decisions shape everything on this page, both recorded in [ADR 0005](../adr/0005-training-runtime-python-exclusivity-and-project-placement.md):

1. **All training semantics live in Python**, inside a `uv`-managed, lockfile-pinned venv. C# owns process lifetime, phase/progress, artifact identity, persistence and policy — never optimizer math, tokenization, chat-template rendering or quantization arithmetic. The whole interface is a line-delimited JSON stdio protocol.
2. **A run holds the node exclusively.** While a training run, evaluation run or export is admitted, the node does no chat, no embeddings, no image generation and no benchmarks. That exclusivity is one lock — `IGpuWorkGate` — and taking it *is* the check.

## 1. The Python runtime (uv, pinned, machine-global)

`ITrainingRuntimeService` (`TrainingRuntimeService`) provisions the venv single-flight. It is **Linux-x64-only by gate** (`TrainingRuntimePrerequisiteKeys.Platform`), and the committed lockfile narrows resolution to the same platform via `tool.uv.environments`. The shared uv layer underneath is Windows-capable (ADR 0016 §5); Training stays Linux-only by profile and reports `Unsupported` on Windows.

- `UvBinaryAcquirer` (`Providers.Python`) downloads the pinned `uv` release and verifies its SHA-256. Both live in `ManagedPythonPins` (`UvVersion` plus one `ManagedPythonUvAsset` per RID, `linux-x64` and `win-x64`; `Current` resolves this host's) — uv publishes a `.sha256` per asset, unlike llama.cpp, so a version bump re-fetches it rather than reading the Releases API.
- Install phases are `TrainingRuntimePhase`: `Idle → AcquiringUv → ProvisioningPython → InstallingPackages → Verifying → Ready` (plus `Failed`, `Removing`). A refusal to start is a `TrainingRuntimeInstallOutcome` (`AlreadyRunning`, `InsufficientDisk`, `MissingPrerequisites`), not an exception.
- `Verifying` runs `probe.py` inside the fresh venv and reads its one-line JSON handshake (`TrainingRuntimeProbeReport`). A probe whose `contractVersion` differs from `TrainingRuntimePins.ProbeContractVersion` is **rejected rather than adopted** — the scripts and the managed side are versioned together.
- Adoption is **one rollback boundary** spanning both the directory swap and the `InstalledTrainingRuntimeStore` write (`TrainingRuntimeLayout` names `active` / `.staging` / `.backup` under `{LocalApplicationData}/XE-Local-AI-Engine/training-runtime`). The backup is consumed only after both steps succeed.
- A failed reprovision that left the previous runtime intact terminalizes **`Ready`** carrying the reason in `SanitizedError`; only a failure with no surviving runtime ends `Failed`. `TrainingRunExecutor` and `TrainingExportService` gate on `Phase == Ready`.

**The shipped manifest is `tools/training/pyproject.toml` + `uv.lock` and nothing else.** The app copies exactly those two files into staging and runs `uv sync --locked` (no `--no-dev`), so a dev dependency group added there would install linters into every user's training venv. Repo-wide Python tooling lives in the **root** `pyproject.toml` instead (see §7).

### The scrubbed environments, and the uv pipeline the compute tool shares

`TrainingRuntimeEnvironment` builds the environments every training subprocess runs under, on top of the shared
**allow-list** in `ManagedPythonEnvironment` (`Providers.Python`):
only `PATH`, `LANG`, `LC_ALL`, `CUDA_HOME` and `CUDA_PATH` pass through. Everything else — `LD_PRELOAD`,
`LD_LIBRARY_PATH`, proxy and credential variables, every node secret — is dropped by construction, and
the runner clears the inherited environment before applying the result. On Windows the list adds `SystemRoot`,
`SystemDrive`, `windir` and `PATHEXT`, and the uv environment maps its isolated home and temp onto `USERPROFILE`,
`TEMP` and `TMP` (ADR 0016 §5).

- **The uv environment** (`ManagedPythonEnvironment.BuildUvEnvironment`) points uv at an isolated `HOME`/`TMPDIR` under
  the training work directory and at the shared toolchain store's cache and interpreter directories, so an install
  neither reads the operator's `~/.config/uv` — which could redirect an index — nor scatters gigabytes into the
  user's home.
- **The train environment** redirects every default cache this stack writes to (`~/.cache/huggingface`,
  `/tmp/torchinductor_<user>`, a CWD-relative `unsloth_compiled_cache`), none of which is writable or wanted
  under a scrubbed environment. The split is deliberate: run-scoped state — `HOME`, `TMPDIR`, the HF cache —
  lives under the run's work directory and dies with its `work/` sweep, while compiled Triton and Inductor
  kernels live under the machine-global cache root so the second run on a box does not pay the compile cost
  again. `CUDA_CACHE_PATH` puts the CUDA driver's kernel cache there too, at its documented 4 GiB maximum
  (`CUDA_CACHE_MAXSIZE`): under the per-run `HOME` it starts empty, and every first kernel use costs seconds.
  The three **offline flags are what actually guarantee no network call**, because several
  `huggingface_hub` paths inside unsloth never thread `local_files_only` through.
- **The export environment** is the train environment plus the vendored `gguf-py` on `PYTHONPATH`, because the
  conversion scripts resolve that package relative to the llama.cpp repository they normally live in, which
  the provisioned script tree deliberately is not.

The uv pipeline is **not training-specific**, so it lives in `Providers.Python`
([ADR 0016](../adr/0016-managed-python-shared-uv-layer.md)) rather than here. `UvBinaryAcquirer` is the shared
uv acquisition for every uv-managed venv the engine provisions — the sandboxed compute tool provisions its
numpy/scipy/sympy closure through the same pipeline — so a second digest-pinned downloader would duplicate this
one rather than add a capability. Its pipeline is download → SHA-256 verify → atomic extract into a version-keyed
directory, mirroring `LlamaCppBinaryManager`, including the extract-to-sibling-then-move step that stops a partial
extract masquerading as a warm cache. The digest is checked **before** anything is unpacked, never after, and a
cache hit short-circuits the whole thing so a re-install performs no network I/O. Every uv-managed venv runs its
`uv sync` through the one scrubbed, tree-killed spawn, `IPythonToolRunner`, under
`ManagedPythonEnvironment.BuildUvEnvironment`.

### The shared toolchain store, and the migration off the per-feature one

`ManagedPythonToolchain` names one machine-global store under `RuntimeCacheDirectory.Resolve()` that Training and
the compute tool both provision against; only the **environments** stay in their feature roots:

| Path under the runtime cache | Holds | Owner |
|---|---|---|
| `python/uv/<version>/…` | the pinned uv | shared |
| `python/pythons/` | managed CPython installs (`UV_PYTHON_INSTALL_DIR`) | shared |
| `python/cache/` | the uv cache (`UV_CACHE_DIR`) | shared |
| `training-runtime/venv/{active,.staging,.backup}`, `.work/`, `installed-training-runtime.json` | the training venv and its state | Training |

- **Nothing deletes under `python/`.** Several hosts and checkouts share the store and a venv's `pyvenv.cfg` `home`
  points into it; removal is uv's own business (`uv python uninstall`, `uv cache clean`), never a directory delete.
- **Concurrency.** uv locks its cache and its install directory (`python/pythons/.lock`). `UvBinaryAcquirer` runs
  its check, download, rename-aside and move under an exclusive file lock (`python/uv/.acquire.lock`) and re-checks
  inside it, so a second acquirer adopts the first one's tree; outside the lock (an older build on the same store) a
  complete `uv/<version>` is still adopted, never replaced, and only a tree without the executable is renamed aside
  and deleted. Replacing a complete tree was the root cause of the compute live suite's cold-start failures (ADR 0016).
- **Legacy toolchain.** Before the store, `training-runtime/` held its own `uv/`, `pythons/` and `uv-cache/`. An
  installed runtime built then keeps running against them; the next **install** provisions against the store. Nothing
  deletes those three directories any more (the sweep was removed before rc.3): after a reinstall they are dead weight
  an operator may delete by hand. **Remove** deletes `VenvRoot` and `.work`; it provisions nothing and never touches
  the store.
- **The Managed Python status row.** `GET python/status` ([API](09-api-and-hubs.md), ADR 0016 §4) reports Training as
  the `training` environment, derived from `GetStatus()` without any format change to `installed-training-runtime.json`:
  a running install or remove is `Provisioning`, phase `Failed` is `Failed` with the sanitized error, nothing installed
  is `NotProvisioned`, a missing interpreter (`ResolveInterpreterPath()` null) is `RepairRequired`, and an installed
  record whose lockfile digest (against `TrainingRuntimeStatus.ShippedLockfileSha256`, hashed once per process),
  Python minor or probe contract version (against `TrainingRuntimePins.ProbeContractVersion`) differs is
  `UpdateRequired`; otherwise `Ready`, carrying the sanitized error when a reinstall failed and the old runtime stayed.
  The uv version is informational, off Linux the row is `Unsupported`, and the status offers no Training action — the
  install flow stays on the Training page.

`TrainingRuntimeException` — and `ManagedPythonException` from the shared layer, which Training's catch sites
accept alongside it — carries a message that is user-safe **by contract**: every construction site
phrases it for an operator and names no path, URL, token or environment value. The phase machine surfaces
these verbatim as the sanitized error and collapses every other exception to a generic reason, so widening
that guarantee silently widens what leaks to the UI.

## 2. Dataset generation

A **dataset definition** (`TrainingDatasetDefinition`) describes what to generate; `POST training/definitions/{definitionId}/generate` creates a `TrainingDataset` and enqueues its single `DatasetGenerationWorkItem`. `DatasetGenerationHostedService` is a single-consumer durable FIFO; `DatasetGenerationExecutor` runs one dataset to a terminal state and owns durable terminalization. Every terminal outcome, an operator cancel included (stored as dataset `Failed`, work status `Cancelled`; its event's `state` is `Cancelled`, never `Failed`), is committed and then published as a `State` event on `training/datasets/hub` (a failure whose commit throws still publishes its `Failed` event, so its reason is not lost): the cancel route returns once the cancel is signalled, so a client that re-reads right away can still see `Running`, and the push is what tells it, and the app-wide operations feed, that the build ended.

- `StructuredAgentRunner` drives a local teacher model with a **JSON-schema-constrained** turn and per-turn deadline (`StructuredAgentRunner.TurnTimeout`); `HeadlessToolExecutor` + `ToolMockService` supply the mocked tool surface (`ToolMockDefinition`, verify verb at `training/mocks/{mockId}/verify`). `HeadlessToolExecutor` composes the **teacher's offer** and the mock envelope itself — those are what dataset generation adds on top of a plain in-process call — but delegates the **real-execution** leg whole to `IToolInvocationService.InvokeAsync`: executable resolution across both registries, the structural approval floor, argument validation, the call and its classification. A refusal from that seam (approval required, or the wrong risk class) maps back onto a mocked outcome rather than being unwrapped.
- `SampleValidationPipeline` validates each record against the **original** schema. v1 samples demonstrate **exactly one** tool call (`TeacherSampleRecordV1`), so a trajectory with more than one tool part is rejected.
- Samples are staged inert: `TrainingSampleReviewState` is `Pending` until an operator approves or rejects (`training/datasets/{datasetId}/samples/{sampleId}`), and provenance is `Generated` or `Manual`.
- **A dataset pins its definition body.** `training_datasets.definition_json` carries the body copied in the same transaction that read `DefinitionVersion`; the executors read that pin (`DatasetDefinitionService.ReadPinnedBody`), never the live definition row, which an operator can edit in between. The column is nullable on purpose, and a null pin is refused (`DatasetDefinitionService.UnpinnedDatasetReason`) rather than falling back.
- `DatasetExportService` writes canonical, **template-agnostic** JSONL (or a Hermes-style form) — the base model's chat template is applied inside the trainer, never at export. Rejected samples are excluded.

Generation takes a **shared** `IGpuWorkGate` admission. `DatasetGenerationService.StartAsync` refuses with a `TrainingBusy` conflict while something holds the gate exclusively, but that refusal is UX only: the queue's claim is what actually enforces exclusivity.

## 3. Base checkpoints and the license gate

GGUF files are **not trainable** — a run needs a Hugging Face checkpoint. `BaseArtifactService` resolves the operator-selected repository to the commit the Hub reports (`IBaseCheckpointStore.ResolveAsync` refuses when it reports none, so a branch name never becomes an artifact's identity), preflights free disk with a fixed `DiskHeadroomBytes` margin on top of the manifest size (the frozen dataset copy, the run workspace and the export all land on the same volume immediately afterwards), records a `TrainingBaseArtifact` and hands the transfer to `BaseArtifactDownloadCoordinator` (`training/base-artifacts`, `.../cancel`).

`LicenseGateService` surfaces the checkpoint's licensing for the run wizard and hashes the canonical English text of what the operator confirmed, so a later reword cannot be mistaken for consent to the same terms. Model Lab's form shows that confirmation in the page's language, built from the same facts (`ModelLabCheckpointPreflightResponse.MetadataPresent` beside the repository, license and gated flag), and keeps the English text one tap away; the English text is what `ModelLabExperimentService.CreateRowAsync` records. **A repository that declares no license is not a pass** — the confirmation still happens and records that no license metadata was found.

`IInstalledBaseModelLinker` resolves the run's `LinkedInstalledModelName` from the wizard's explicit choice, else the official `<base>-GGUF` repo or the same repo id — never a display-name guess. Without that link an adapter export has no base to be smoke-tested against with `--lora`, cannot be promoted, and a comparison has no base side.

## 4. Training runs

`POST training/runs` only **enqueues** — `TrainingRunQueueHostedService` is a single-consumer durable FIFO whose work items pin `attempt = 1` (a CHECK constraint on `training_work_items`), so there is no retry to fall back on.

- **Everything exclusive is acquired before the claim.** Two gates, in order: an exclusive `IGpuWorkGate` hold, then the llama.cpp runtime-mutation lease (`AcquireRuntimeMutationLeaseOrNullAsync`), which refuses while any model is loaded. A refusal simply leaves the item `Queued`; nothing signals when the gate frees or the model unloads, so the queue retries a refused head every second while the idle poll behind the enqueue signal is 30 s (the dataset generation and benchmark queues retry a refused shared admission the same way). The queue **peeks the head's kind** before acquiring (`PeekNextKindAsync`) because an attempt-pinned claim can never be handed back.
- **An evaluation run takes the first gate and does not directly take the second.** Both installed-base and staged-tuned evaluations use `ITransientLlamaServerEvaluationHarness`, which owns the runtime-mutation lease and model-load admission in the correct order. Installed models additionally hold a coordinated read snapshot through teardown, binding the composite registry identity and verified weight SHA-256/size while the harness loads the path.
- **Model Lab traces on the training runtime.** `ModelLabExperimentService` runs trace and steering jobs in a `tools/training/modellab.py --serve` worker spawned through `ITrainingProcessSpawner`, one job at a time and refused when busy, under the exclusive GPU gate, the runtime-mutation lease and a ledger reservation. A cold start takes all three; the worker's session keeps them, and the model, between jobs (next bullet). A loaded model refuses a cold start; nothing is ejected. A chat that needs a local model waits behind the lease with the `QueuedBehindGpuWork` notice until the job ends or is cancelled. A trace generates `ModelLabTraceSpec.MaxNewTokens` (128) tokens unless its request names another count (`maxNewTokens`, 1 to `MaxRequestedNewTokens` = 256, refused with `steering`); a steering job's arms always generate 128. The script speaks its own contract version. A request may name the blocks to trace (`layers`: 1 to `MaxTraceLayers` distinct blocks, refused with `steering`); left out, the trace takes the three quarter points (`LayersFor`). A block at or past the checkpoint's block count is refused with `InvalidTraceLayers` before the gate. The service always sorts the layers ascending, because the script counts a token step when the first listed layer's hook fires, and `modellablib.validate_job` refuses an unsorted list. The byte cap scales with the layer and token counts (`TraceByteCapFor`: four times the measured 162 bytes per token per layer, plus the footer reserve, never under the three-layer 256 KiB), as the lens and attention caps scale with the job's tokens, and the blob store's bound is the cap at `MaxTraceLayers` and 256 tokens; a steering vector keeps its own smaller bound. Tracing every block costs much more generation time than three: the workbench spike measured +59 to +63 % on the 0.8B and the 9B. The prompt and the result sit in encrypted columns of `model_lab_experiments` and the trace in one encrypted blob store; the plaintext work directory goes on every path and, unconditionally, at startup through `ModelLabStartupReaper`, which first reaps the warm workers' receipt files, then the rows' receipts, through the same `TrainingProcessReaper` as a training run. The newest 20 unpinned rows are kept; a pinned row (`IsPinned`, at most `MaxPinnedExperiments` = 20, a 21st pin is the 409 `PinLimitReached`) is never trimmed and a manual delete still removes it. A row records the node version (`AppVersion`), a trace result its `layers`, `seed`, `maxNewTokens` and `cuda`, and a steering result the arms' `seed`, so a comparison can list what differs; older rows read back without them. A failed trim neither fails the start nor strands the row, and a row still holding a launch receipt is neither trimmed nor deletable, because the next startup needs it to find an orphan. The script's heartbeat stops at the first progress event: its thread outlives a wedged main thread, so between tokens only real progress keeps the inactivity watchdog quiet, while a first forward compiling kernels stays covered. Preflight refuses a model type the script has not traced (`UnsupportedModelType`; Qwen3.5 and OLMoE are traced), and a checkpoint whose family writes another GGUF architecture than the paired GGUF (`ArchitectureMismatch`: `qwen35` for Qwen3.5, `olmoe` for OLMoE), before any weight is fetched; a config with `output_router_logits` set gets a `traceRefusalMessage` (the script would install persistent capture hooks, and refuses it too, but only once the weights are loaded) and can still be steered. A first trace on a machine with an empty Triton cache compiles a helper and needs a C compiler; this is not checked beforehand, because a filled cache needs none, so without one the row fails and says there is no gcc or clang on the node's PATH. Removing or reinstalling the runtime is refused (`GpuJobRunning`) while a training run, an export or a trace holds the gate and the lease, and while a gate-free CPU job (the PyTorch source index or the training stepper) runs from the venv. The install is detached, so the check runs inside the provider's start transaction: `TrainingRuntimeService.InstallAsync` and `RemoveAsync` publish the non-ready phase first and then await the admission delegate `TrainingRuntimeOrchestrationService` passes in, which raises demand, waits up to `GpuWorkAdmission.IdleHolderReleaseBound` for an idle warm worker to go and then admits unless `IsGpuJobRunning`, a Model Lab worker not seen to exit may still run from the runtime (`IModelLabActiveJob.HasUnconfirmedWorkerAsync`, which retries the reap first), or a CPU job is registered in `TrainingRuntimeUsers` (see "The runtime-users guard" below); a refusal, and an admission that throws or is cancelled, restores and republishes the prior phase. The routes' cheaper pre-check (`RefusesForRunningGpuJobAsync`) joins a worker eviction already under way, as Direct Inference does (see Demand and preemption), and raises demand before its 409, so a trace running at the time evicts its worker when it ends instead of going idle. A route that meets an eviction can therefore wait twice, in the pre-check and in the admission. A Model Lab cold start and an export read the phase again after taking their lease, and an export resolves its interpreter again there, so of the two exactly one proceeds. An evaluation runs on llama-server, and the queue's brief hold behind a loaded model has no lease. Deleting a checkpoint a live job uses is refused with `in-use-by-experiment`, and one a worker not seen to exit may still hold (its own, or one the startup sweep kept) with `worker-not-confirmed`; the live job decides, not the row, so a row stranded in `Running` blocks nothing. A checkpoint delete holds `IModelLabActiveJob.ClaimForDelete` from just after its `Downloading` check, before the idle worker's eviction, through the directory delete; meanwhile a start on that checkpoint is refused as `CheckpointNotFound` at either point where it would publish its job: a warm start before it claims the idle session, which it leaves as it was, and a cold one after the gate, which it gives back with its session. A start therefore either publishes its job before the claim, and the delete's guard sees it, or sees the claim. A delete that then refuses has still answered those starts "not found".
- **Model Lab warm worker.** `ModelLabServeWorker` drives one `modellab.py --serve` process (contract 8) that keeps a checkpoint loaded across trace and steering jobs; a source job still runs `--config` once. The host writes one JSON command per stdin line: `{"op": "run", "jobId", "config"}` (only while idle), `{"op": "cancel", "jobId"}` and `{"op": "evict"}`, EOF counting as evict. Every frame carries the spawn's run token and a job's frames its `jobId`; a line without this spawn's token only feeds the diagnostic tail. The legal order is `handshake` (with `serve: true`), then per job any `phase`, `progress` and `heartbeat`, exactly one `done` or `error`, then `ready` (`vramBytes`, `reservedBytes`, never a `jobId`) once the job's hooks are gone and its memory released. A frame out of that order, a contract mismatch, a handshake without `serve: true`, a `ready` that carries a `jobId` or lacks a `vramBytes` of zero or more, a missed handshake (`HandshakeTimeout`) or `ready` (`ReadyTimeout`), or a process-level `error` without a `jobId` breaks the worker: its group is killed and it never takes another job. A job is finished only at its `ready`: a break or an exit between its `done` and its `ready` fails the job (so a steering job runs no arms), while a break or exit after its `ready` is the idle worker's and leaves the job as it ended. A job names its model (`modelKey`: checkpoint id, revision, bf16 and contract), and a worker holding another refuses it. The script exits 0 after evict, 3 on SIGTERM in any state and 1 after a protocol error or `worker-poisoned`. A result records `warm` and `loadSeconds`. A cancel before the handshake kills the worker. A cancel during the first, cold model load cannot interrupt the load: the job ends Cancelled once the load finishes, and the worker stays warm if that happens within the 10 s cancel-acknowledgement bound (`CancelAcknowledgementTimeout`), otherwise its group is killed. Each spawn runs in its own owner-only `worker-<runToken>` directory under the work root, the base of its `HOME`, `TMPDIR` and `HF_HOME`, so nothing one worker leaves there reaches the next. It goes once the worker's exit is seen; after an unseen exit it stays until the startup sweep clears the work root. A spawn that throws deletes its directory at once, since no process started. The kernel caches (`CUDA_CACHE_PATH` and the compile caches) stay shared across workers.
  - **The session owns the holds.** `ModelLabGpuSession` (`Admitting`, `Active`, `Idle`, `Evicting`, `Ended`) owns the gate, the lease, the reservation, the process and its receipt file. A job borrows the session and hands it on when it ends: to `Idle`, to eviction, or for a steering job's arms to the job. The holds are never released and taken again, because the lease gate is not reentrant and a queued ensure would win the gap. A cold start registers the session with the broker before it takes the gate, so demand racing the admission is latched, and takes its lease with `raisesDemand: false`, so it never preempts itself. A warm start (`TryEnterActive`: `Idle`, the same model key, and nothing has asked the session to go) runs before the gate and takes nothing, so it can be neither refused nor left waiting on itself; a start on another checkpoint evicts the idle worker first. A start claims a session (warm) or publishes a new one (cold) together with its job, under the lock a host stop sets its stopping flag under: the stop either sees the job, cancels it and waits for the eviction, or the start is refused as stopping. The idle time is the stored node setting `ModelLabWarmIdleSeconds` (0 to 3600, default 300), read at every idle transition; 0 gives one process per job, as before. A steering job never leaves its worker warm, nor does a job whose worker broke or did not end with `done` and `ready`.
  - **Demand and preemption.** `GpuIdleHolderBroker` (`IGpuIdleHolderPreemption`, implementing holders `IGpuIdleHolder`) forwards GPU demand to the registered holders. Demand is every refused `IGpuWorkGate.TryBeginExclusive` or `TryBeginShared`, every public entry of the llama runtime-mutation gate (so every model ensure) and `AcquireLeaseOrNullAsync` unless `raisesDemand` is false, a whisper GPU load (whisper takes neither the gate nor the lease, so `WhisperServerProcessSupervisor` waits up to 30 s for the release and then loads anyway), the runtime install and remove admission and their routes' busy refusal, Direct Inference's `GpuWorkExclusive` refusal, a delete of the warm checkpoint (`EvictIdleWorkerAsync`), `POST model-lab/warm/eject` and host stop. Only an `Idle` session is preempted: demand while `Admitting` or `Active` is latched and served when the job ends, so a running job is never preempted. An eject or a checkpoint delete refused because a job holds the session (409) is latched the same way: the job runs on and its end evicts the worker instead of idling. Callers that refuse at once retry once through `GpuWorkAdmission.BeginExclusiveOrNullAsync` or `BeginSharedOrNullAsync` after waiting up to `IdleHolderReleaseBound` (30 s): image jobs and exports; `DatasetGenerationService.StartAsync` waits the same way before its UX refusal. The benchmark and dataset-generation queues peek (`HasQueuedWorkAsync`) before touching the gate, so an empty poll raises no demand. Reads that show an exclusive holder as busy (`GpuWorkHolderNotice.ForModelLoad`, `AppUpdateBusyProbe`, `TrainingRuntimeOrchestrationService.IsGpuJobRunning`) count an idle worker as not busy (`IsIdlePreemptible`). A Direct Inference request and the runtime routes' pre-check that meet a session already `Evicting` join that eviction instead of refusing: they wait up to `IdleHolderReleaseBound` (the wait answers at once for an `Admitting` or `Active` session), then read their check again, because steering arms or a new start may own the gate by then; still busy, they latch demand on the holder now registered and refuse. The residents read shows the session as a `modelLab` row ([Model Fit](07-model-fit.md)) with `vramBytes`, the allocated count of the worker's last `ready` (`torch.cuda.memory_allocated`, below what the driver reports; `reservedBytes` is not read); the host logs it at Information on each `ready` that ends a job cleanly.
  - **Eviction and the verified exit.** An eviction runs once, on a task of its own that no requester's token can cancel: `evict` on stdin, `EvictGrace` (2 s), a group kill, then up to `ExitVerifyTimeout` (10 s) to see the exit. The exit is seen once the worker process has exited and, when its receipt proves it leads its own process group, that group is empty (`kill(-pgid, 0)` fails with `ESRCH`); otherwise, with no group to probe, the exit counts only once the output pipe has closed as well (`ITrainingProcessHandle.WaitForGroupExitAsync`). With a proven group it never waits for the output pipe, so a descendant that left the group (`setsid`) may still hold the pipe, and possibly VRAM, once the reservation is back: the training script never does that. A child left in the group that outlives the worker keeps the exit unseen (fail closed): the group kill reaches the group only while the worker itself lives. The reaper still proves a receipt gone by its leader pid alone, so the next reap or a restart releases the kept receipt and reservation while such a child may still live, a known gap. The output pump is retired before the stop returns, so no late line reaches a worker being torn down. Only a seen exit gives everything back, in order: the receipt file, the reservation, the lease, then the gate. An exit not seen gives back the lease and the gate but keeps the reservation on the ledger and the receipt file on disk, and every later start first retries the reap, before the gate and again once it holds the gate, and is refused with `OrphanWorker`, naming the pid (or the receipt file, when it names no readable pid), until the process is proven gone. An eject that ends this way answers the 409 `OrphanWorker`, not 204. The receipt lives in `model-lab/receipts/warm-<runToken>.json` (`ModelLabWarmReceipts`), beside the work root rather than in it, written owner-only before the first output line is read; the row holds a copy only while its job runs. A file is deleted only on `TrainingReapOutcome.Verified`: `TrainingProcessPresence.Unknown` (a stat entry that could not be read) never counts as gone, and an empty, unparsable or incomplete receipt (pid 0 or 1, no start time, no run token) is `NotVerified` without a probe. A live pid proves the process gone only when its start time or a readable run token differs from the receipt; a changed executable path (a replaced interpreter, or one read with a ` (deleted)` suffix) or process group alone leaves it `NotVerified` and unsignalled. A row's receipt is still cleared either way. The session also holds each spawn's receipt in memory, and a start reaps that instead of the file, so a receipt whose write failed still refuses starts until its process is proven gone. A held receipt too incomplete to probe can never be proven gone, so its refusal says to confirm the process is gone, remove any stale receipt file, and restart the node to drop the held copy. A receipts directory that cannot be listed at startup (only a missing one lists as empty; an unreadable one, or one under a parent that cannot be traversed, fails the scan) refuses every start with `OrphanWorker`, naming the directory, until a start lists it; the row sweep and the recovery of interrupted rows run either way. A kill opens a pidfd on the pid and signals through it only once the stat read after the open carries the recorded start time (and, for a live pid, the run token), so an unreadable entry or a recycled pid is never signalled; a pidfd call that fails operationally sends nothing and keeps the receipt (`TrainingProcessPresence.Deferred`). Where the kernel offers no pidfd, the stat is read just before a numeric signal. A steering job ends its worker after the derive (`DetachForArmsAsync`): the process stops and the reservation goes, and the gate and the lease pass to the job for its arms; an exit not seen fails the job and keeps the reservation as above.
  - **Cleanup is asserted, not assumed.** Each hook constructor pushes its handle onto the job's `ExitStack` as it registers it, and `_AttentionRows` puts the `sdpa` restore on the stack before the swap, so a constructor failing halfway leaves nothing behind. After the terminal frame the worker collects garbage, empties the CUDA cache and checks that no forward hook remains on the model and that `sdpa` is the original (`_left_behind`); otherwise it exits 1 with `worker-poisoned` rather than serve a changed model.
  - **Measured.** A warm 9B trace took about 5 s against about 19 s cold. Warm and cold runs produced bitwise identical tokens on the pinned runtime. After an eviction VRAM was back at its baseline at the first reading after the exit, so an eviction waits for the exit and not for VRAM.
- **Model Lab next-token candidates.** A trace records each step's candidates while it runs: a forward hook on the model reads the raw logits (the model's output, any final softcapping included, exactly what transformers 5.17 `_sample` copies into `next_token_logits`), and a logits processor passed to `generate`, which transformers appends after the checkpoint's generation-config processors, sees the processed scores the greedy argmax reads (`_Candidates` in `modellab.py`). Per step it takes a float32 log-softmax over the whole vocabulary of each on the GPU and keeps only the top 20 (`TOP_CANDIDATES`) and the chosen token's value; no full-vocabulary tensor outlives its step, so the reported peak VRAM no longer includes recording the candidates. The processor returns the scores unchanged, and `modellablib.check_aligned` fails the trace unless the steps it saw chose exactly the generated tokens, so a processor merged after it (a watermark) cannot shift the alignment silently. Every token in `result.json` carries `logprob` and `candidates`, `processedLogprob` and `processedCandidates`, `{id, text, logprob}` with each text decoded alone (`modellablib.scored_token`). Texts are written whole; only a result over `TRACE_RESULT_BUDGET_BYTES` (0.9 MiB, a tenth below `MaxResultBytes`) has its candidate texts, then its prompt pieces' texts, then its token texts, cut to 64 bytes of escaped JSON with a trailing ellipsis (`fitted_trace_result`, `cut_text`; the id stays exact, and the view matches the chosen candidate by id). Still over, it drops the candidates of whole steps from the end (contract 7): `candidateSteps` counts the leading steps that kept theirs, as many as fit, and every token keeps its id, text and logprobs. A result over the budget even then fails the trace. `generate` gets `num_beams=1` explicitly: a checkpoint configured for beam search would break the step alignment. Logprobs are rounded down to four decimals, so the shown probabilities never sum past 1; a candidate a processor masked (-inf) is left out, and a non-finite chosen value is null. The fields are optional on `ModelLabResultToken`, so an older row reads with them null and needs no contract bump; 128 steps of ordinary text take about 250 KB, the costliest 128-step result fits once its texts are cut, and a 256-step one of the costliest texts keeps candidates for its first steps only (`test_modellablib.py` pins both). The views show a step past `candidateSteps` as not kept, under a yellow alert naming how many steps kept theirs; a row saved before contract 7 has no `candidateSteps`, so a step there without candidates reads as made before this version. A step the trace byte cap dropped still gets its row in the view, with empty norm cells, so its candidates stay selectable.
- **Model Lab attention capture.** A trace started with `recordAttention` also records, for every predicted token, the query row of each captured full-attention block (`ModelLabTraceSpec.AttentionLayersFor`: every `full_attention` block, thinned evenly to `MaxAttentionLayers` = 8; block kinds come from the family's rule: a Qwen3.5 checkpoint's `layer_types`, or `full_attention_interval` when that list is absent; every OLMoE block is full attention, whatever the config states). Capture is implemented for the families in `modellablib.ATTENTION_FAMILIES` = the host's `AttentionModelTypes` (Qwen3.5 and OLMoE), each admitted only after its attention source was read and its recomputed rows were checked against an eager pass, because the recompute rebuilds only plain causal softmax(q·kᵀ·scaling): no window, chunking, softcap or sink. A checkpoint of another family, an OLMoE config that states anything but full attention at every block (`layer_types`, a non-null `sliding_window`, `attention_chunk_size` or `num_kv_shared_layers`), no full-attention block, unknown head counts or more than `MaxAttentionHeads` query heads is refused with `AttentionUnavailable` (the script refuses the same before any hook), and `steering` refuses the flag. The script does not switch the model to eager attention, which changes the generated tokens: `_AttentionRows` in `modellab.py` wraps `ALL_ATTENTION_FUNCTIONS["sdpa"]`, returns the kernel's own output unchanged and recomputes the last query row's softmax in float32 from the same post-RoPE query and key tensors, grouped per KV head. Only the chosen blocks' own `self_attn` modules are captured, bound by identity with the block index taken from that map, so a vision tower's attention never is; Gated DeltaNet blocks have no attention matrix. The recorded `headDim` is read from the first captured block's `self_attn` (an OLMoE config has no `head_dim`). Capture pins a `DynamicCache` and passes `cache_implementation=None` and `prefill_chunk_size=None`, and every call asserts that the key length equals prompt length plus step, so a checkpoint generation config cannot shift positions silently. The prefill's last row predicts token 0; the call reading token s-1 predicts token s. Per row and head the top `min(32, keys)` positions are kept as weights floored to 1/10,000 plus the remaining mass, in a second JSONL file under its own cap (`AttentionByteCapFor`: layers x heads x tokens x 32 x 10 bytes x 2 plus the footer reserve; about 3.9 MB for Qwen3.5-0.8B at 128 tokens, at most `MaxAttentionByteCap`, about 40 MiB at 256), stored as a second encrypted blob of the row (`AttentionBlobId`); a failed second write or completion save deletes the row's blobs through `DeleteScope`. `model-lab/experiments/{id}/attention/{layer}` returns one layer's rows. Capture is opt-in because 40 retained and pinned runs can hold up to about 1.6 GiB of attention. A spike on Qwen3.5-0.8B showed the output unchanged bit for bit with capture on, the recomputed rows rebuilding the kernel's output within 1 % (a shuffled-keys control fails), +13 KB peak VRAM and a transient key copy of about 17 MiB at 8,192 prompt tokens. Every v4 result also carries `promptPieces`, `layerKinds` and `attnImplementation`; contract 3 rows read them as null and show attention as not recorded.
- **Model Lab steering jobs.** A start carrying `steering` runs `modellab.py` with `kind: steering`: forward hooks on one block read each contrast prompt's mean block output, and the script writes the normalised difference at 0.5 times the reference norm as `steer.gguf`, plus `random.gguf` from a CPU-seeded generator at the same norm, with its own small GGUF writer (no `gguf` package; the file is the one `TransientLlamaServerControlVectorCheck` reads back against the model). The reference norm (`referenceNorm` in the result, `modellablib.reference_norm_of`) is the median of every position's residual length at that block over both contrast sets, for every family: OLMoE's first position carries a residual many times longer than the rest, which inflated a mean so far that scale 1 collapsed the output into one repeated token on both the vector and the random arm; on Qwen3.5 the median sits close to the old mean, so the same scale steers slightly differently there than before. The layer defaults to the full-attention block nearest 0.6 depth from the checkpoint's `layer_types` (`ModelLabTraceSpec.DefaultSteeringLayer`: 15 of 24, 19 of 32), a caller may name another, and a layer outside 1 to the GGUF's trunk minus 1 is refused with `InvalidLayer` before the gate. `ModelLabArmRunner` then runs baseline, vector and random under the job's own lease, through the `RunArmsAsync` overload that takes it: the gate and the lease span both phases, so a chat cannot load in the gap, and only the ledger reservation is given back after the derive, because each arm has its own load ticket. The `arm-baseline` phase is sent before the first server starts, because that start can download the runtime. A start whose first arm could only be refused for want of a runtime (`GetImplicitAcquisitionRefusalAsync`) is refused with `RuntimeUnavailable` before the gate, so it costs no derive. The vector takes the row's blob slot and `Kind` tells the row's blob apart, so the trace route answers 404 for it. `SetProgressAsync` saves the result after the derive and after each arm, so a cancel, a failed arm or a killed host still shows what finished. The vector files stay in the work directory, deleted on every path and at startup; the arm servers fall to `StaleProcessReaper` and their spawn receipts. Arms are greedy on one seed with no prompt cache. Their request client drops the service defaults' resilience pipeline, which would time a generation out and retry it. Accepted ceiling: pairing checks the family (`ArchitectureMismatch`) and the shape, so a different model of the same family and shape takes the vector silently.
- **Model Lab logit lens.** Every contract-5 trace of a checkpoint with at most 64 blocks also reads each block through the model's own output head at every generated step (`_Lens` in `modellab.py`): forward hooks copy blocks 0 to B-2's last-position state, and a logits processor placed after `_Candidates` runs them through `final_norm_of(model)` and the output embeddings in one batched call per step. The last block is not recomputed: its row is the model's own raw logits, because a batched recomputation is close but never bitwise equal (up to 0.019 nats on the 9B in the spike). One float32 log-softmax then gives each block's top `LensTopTokens` = 5 tokens, the chosen token's lens logprob and competition rank (ties share the better rank), and the readout's entropy in nats. Everything stays on the GPU until saving. Every trace now passes `watermarking_config=None`, because a watermark processor runs after the custom ones and would change scores after the lens read them; `check_aligned` also checks the lens' chosen ids. The lens lines are a separate section of `trace.jsonl` with their own cap (`LensByteCapFor`) and a `lensFooter`, so a lens overflow never marks the trace records truncated; the trace parser skips lens lines, so the trace and attention views read exactly what they did before. Texts are cut in the writer's own escaped encoding. `model-lab/experiments/{id}/lens` returns the lens, checked for contiguous steps and consistent sizes (422 otherwise). A spike on Qwen3.5-0.8B and 9B showed every block's copied state bitwise equal to the model's own hidden states, the output bitwise unchanged with the lens on, rank and entropy within 1e-5 of a float64 reference, about 0.45 MB per 128-token run, +81 / +101 MiB peak VRAM and +5.7 / +6.4 % generation time (0.16 / 0.26 s per run), accepted as always on. A checkpoint with more blocks traces as before, without a lens. A lens readout is derived: it applies the final readout early and is not what the model computed at that block.
- **Model Lab expert routing.** A contract-8 trace of a checkpoint whose blocks have a mixture-of-experts router (`routers_of`: each block's `mlp.gate` with integer `top_k` and `num_experts` and a boolean `norm_topk_prob`; OLMoE, never a dense Qwen3.5) records, for every generated step and routed block, the expert ids the router chose and the weights the experts received (`_Routing` in `modellab.py`). A forward hook on each router checks its output (three tensors: `[T, E]` logits, `[T, k]` integer ids, `[T, k]` bf16 weights; anything else fails the job), stashes copies of the last position's ids and the weights' 16 bits and returns nothing, so the output is untouched; a logits processor commits one row per step and fails unless every router was stashed, and saving fails unless there is one row per generated token. Routing jobs pin `prefill_chunk_size: None`, so the routers' last call before step 0 is the prompt's last token: row `s` is the routing at the position whose logits chose token `s`, as for the lens and attention. A spike on OLMoE showed the stash bitwise equal to what the experts' forward received and, float32 ties aside, to a softmax/top-k recomputed from the router logits, and the tokens and logits bitwise unchanged with routing on. The rows are a third section of `trace.jsonl` after the lens, `{"routing":{"s","x","w"}}` with the weights as bf16 bit patterns (`weightEncoding: "bfloat16-bits"`, lossless), under their own cap (`RoutingByteCapFor`, from the widest line at 16 experts per token) and `routingFooter`; the trace and lens parsers skip them. `MaxTraceByteCap` adds the routing bound at 64 blocks and 256 tokens and stays below the blob store's bound. The host's size check allows trace plus lens plus routing caps for every trace, dense ones included, because the script decides whether a model is routed. `ModelLabTraceSpec.ParseRouting` refuses another encoding, layers that repeat or fall outside the blocks, a k outside 1 to `MaxRoutedExpertsPerToken` (16) or above the expert count (at most 1,024), a row without exactly k distinct in-range ids and k weights in [0, 1] per block, steps that are not contiguous from 0, a missing or repeated footer, and a footer or summary that disagrees with the token count. A router past those caps, or routers that differ between blocks, records no routing; a config with `output_router_logits` set is refused. `model-lab/experiments/{id}/routing` returns the rows with each weight as the exact float. Rows saved at contract 6 or 7 open with no routing. OLMoE traces also carry the lens, whose final norm multiplies by its weight `w` where Qwen3.5 multiplies by `1 + w`.
- **Model Lab's PyTorch source index.** `ModelLabPyTorchSourceService` runs `modellab.py` with `kind: source` on a directory holding only a `config.json`, taken from a Ready checkpoint or fetched alone through `IBaseCheckpointStore.FetchConfigAsync` (commit-pinned, 1 MiB cap, no safetensors needed, kept under `model-lab/pytorch-index/configs/`). The job loads no weights and touches no GPU, so it takes no GPU gate, no runtime-mutation lease and no reservation; it needs the runtime Ready, is a registered runtime user while its script runs (next sub-bullet), runs inside the request, one at a time (`Busy` otherwise), under a two-minute watchdog, in a work directory under the Model Lab work root that goes on every path and at startup. A config with `auto_map` is refused as `RemoteCode` before any script runs, and the script refuses it again. The result is cached as `<sha256(config.json)>-<transformers>-<torch>-<contract>.json`, the versions read from the venv's `dist-info` names, so a runtime change misses the cache and hides the last index; a pointer per model names the last one. `ModelLabPyTorchJoiner` links block N to layer N only when the trunk counts match (an MTP block has no layer), a tensor through its Hugging Face name's path inside the block, and other groups by block child names; anything unmatched stays unlinked. The graph follows the PyTorch reference path on the meta device: a GPU run may use fused kernels it does not show. `modellab.py --config` runs only this kind: a trace or steering job there is refused as a contract error, since only `--serve` checks what a job leaves behind. `ModelLabScriptRunner` counts a frame only when it carries the spawn's run token, as the serving worker does: any other line, a foreign frame included, neither marks the watchdog's liveness nor changes the job and only feeds the diagnostic tail. `ModelLabTraceSpec.ContractVersion` is 8; a bump changes the cache key, so every index is rebuilt once.
  - **The runtime-users guard.** The two gate-free CPU jobs, this index and the training stepper (next bullet), hold no GPU admission, so `IsGpuJobRunning` cannot see them; `TrainingRuntimeUsers`, a singleton counted under one lock, does. A job enters through `ModelLabRuntimeJob.TryEnter`: it registers first, then rechecks the runtime (phase `Ready`, `ResolveInterpreterPath`, the script on disk) and spawns the interpreter that recheck found. An install or remove publishes its non-ready phase under the provider's state lock and then reads `InUse` in its admission; both sides cross a lock, so either the job sees the phase or the mutation sees the job. A job that meets a mutation in progress (`GetStatus().Terminal` false) is refused as `RuntimeUnavailable` with "The training runtime is being changed. Try again in a moment."; a runtime at rest that is not usable gets the not-installed text. Registrations are counted, a repeated dispose is a no-op, and each is released in a `finally` as soon as `ModelLabScriptRunner.RunAsync` returns, however it ended: what follows reads only the job's own files. **Invariant: no saved result comes from a swapped venv.** A job saves only after a registered run returned `done` with exit 0, a killed run is a failure, and only the host saves. `TrainingRuntimeService.Recover`, which an install calls before its admission, never moves the active venv under a registered user: it moves `.backup` into place only when the active venv is missing, the registered job's recheck found its interpreter there, and only an admitted mutation removes it. The source job keeps its early package pre-check, resolves the packages again once registered and names the index by those versions, so a runtime changed in between files the index under the key of the venv that built it. The install and remove 409 says "A job that runs from the training runtime is running"; the wire reason stays `GpuJobRunning`. The routes' pre-check (`RefusesForRunningGpuJobAsync`) does not read the guard: the refusal comes from the admission, which restores the prior phase. **Accepted ceiling: host death mid-run.** Neither job writes a launch receipt, so a restarted host may install or remove beside the orphaned script, which runs to its end or dies on its closed pipe; it saves nothing, because only the host saves and `ModelLabStartupReaper` deletes the work root at startup.
- **Model Lab training stepper.** `ModelLabPlaygroundService` trains one engine-authored tiny network, template `tiny-mlp-v1` in `tools/training/nnplayground.py` (`ModelLabPlaygroundSpec.TemplateId`), and saves the run so the Training stepper tab can step through it. **CPU only, no GPU gate.** The script sets `CUDA_VISIBLE_DEVICES` to empty before torch loads, then uses one thread, deterministic algorithms and float64; the service takes no `IGpuWorkGate`, lease, ledger reservation or `GpuIdleHolderBroker` registration, so a run never raises GPU demand, evicts a warm worker, waits on or is refused for a loaded model, or queues a chat. It runs inside the POST request, one at a time (`Busy` otherwise), as a registered runtime user (previous sub-bullet), under the source job's two-minute watchdog with the inactivity bound capped to it, in `playground-<id>` under the Model Lab work root, deleted on every path and at startup. It reaches what the training runtime reaches: Linux only (`UnsupportedPlatform` elsewhere) and a Ready runtime (`RuntimeUnavailable`). The script speaks its own contract (`ModelLabPlaygroundSpec.ContractVersion` 1, separate from the tracer's `ModelLabTraceSpec.ContractVersion`): `--config` only, frames `handshake`, `phase` (`loading`, `training`, `saving`), one `done` or `error` (`contract`, `result_too_large`, `internal`), no progress or heartbeat. `ModelLabScriptRunner.ScriptCommand.PublishPhases` is false for it, so its frames mark the watchdog but nothing reaches the event buffer or a hub. **Bounds**, enforced by the request validator and again by `nnplayground.validate_job`, which refuses a missing, extra or mistyped key at any level: dataset `xor` or `spirals`, learning rate 0.0001 to 10, residual and shared block on or off, depth 1 to 4, hidden width 2 to 16, steps 1 to 2000, seed 0 to 2^31−1; at most 16 recorded steps (all of a run up to 16, else 16 spread evenly, `recorded_steps`), at most 8 probe rows, `trace.json` at most 4 MiB, `result.json` at most 16 KiB; numbers are float64 in their shortest round-trip form and a non-finite value is null. A step is a full-batch forward, mean BCE-with-logits, `zero_grad(set_to_none=True)`, backward and plain SGD (no momentum, weight decay, clipping or accumulation), written into the trace as `stepDefinition`. **Outcome versus failure.** A run that diverges is a saved finding, not a failure: `outcome` is `diverged` at step t with t updates applied, either because the loss was not finite (that step has no backward and no update) or because a gradient was not finite (it has a backward with null cells and no update); otherwise `finished` with every update applied. A failure saves nothing and answers the 409 `RunFailed`: a cancel, the SIGTERM exit, a watchdog stop, an `error` frame, a missing handshake or `done`, a nonzero exit, or outputs that are missing, over their cap, not JSON, of another `formatVersion` or template, or missing a structural field (`ModelLabPlaygroundChecks`). C# checks the shape and never interprets a loss or gradient. Every activation is a tanh, which bounds it, so no in-bounds configuration was measured to diverge; a learning rate of 10 oscillates instead. `diverged` is reached only through the test seam (`train`'s `after_backward`) and a non-finite input in the tests. **Recorded playback.** Stepping replays what the run recorded on the CPU and never runs the network again. **Identity: module, parameter, occurrence.** The trace lists `modules` (`embed`, `block` or `blocks.i`, `head`), `parameters` (id = the `named_parameters()` name, module = the id without its last segment) and `occurrences` (one per visit in execution order, `{module, visit}`); a recorded step's forward and output gradients are indexed by occurrence, parameter gradients and updates by parameter. With a shared block, each of its k visits consumes fresh `view_as` aliases of the one weight and bias, whose retained gradients are that visit's `visitGrads`; autograd sums them into the parameter, and the SGD update applies once to the sum. This per-visit attribution is limited to this template, which records its own occurrences without hooks; it is not offered for arbitrary modules. Model Lab traces of a checkpoint keep their layer-index identity (`modellablib.trace_record`, `block_index_of`), and map onto this triple as layer l = module `{blockPath}.{l}`, visit 0. **Persistence and retention.** A clean run writes its trace into its own `ManagedEncryptedBlobStore` scope (`model-lab`/`playground`) and then its `model_lab_playground_runs` row, the summary in an encrypted column ([Data & Persistence](08-data-and-persistence.md)); the newest 20 (`MaxRetainedRuns`) are kept. **Accepted ceilings:** host death mid-run (previous sub-bullet), and up to one 4 MiB blob orphaned when the host dies between the blob write and the row; there is no orphan sweep.
- **Model Lab prompt tokens.** After a Next token run the page asks `model-lab/prompt-tokens` for that run's prompt as the model read it: the llama-server already running the GGUF applies its chat template to the same system prompt, prompt and Thinking switch, then tokenizes the result with pieces and marks a token special only when llama.cpp parses it as a control token, so a thinking tag that is a user-defined token stays ordinary (`IModelLabPromptTokensService`). It takes no GPU gate, no invocation slot and no load: a model that is no longer running, or whose server goes away mid-call, answers `ModelNotLoaded`, and the page asks for another run. These are the GGUF's tokens; a trace tokenizes with the Hugging Face checkpoint's tokenizer and template, so the Trace tab's Try in Next token link says the two can differ.
- **Model Lab shares the harness.** `RunArmsAsync` runs several requests in order under one lease, with a load ticket per arm and each GGUF hashed once, and a later load checks the file's length and write time instead of hashing again. `RunAsync` keeps its two hashes. `GpuWorkKind.ModelLabExperiment` is the exclusive hold such a run takes; every exclusive kind needs a row in `GpuWorkHolderNotice.ForModelLoad` and `AppUpdateBusyProbe.CollectAsync`, whose `_ => null` arms would otherwise compile silently, and `GpuWorkKindCoverageTests` fails when one is missing.
- `TrainingRunExecutor` drives one claimed run from `Preparing` to terminal: reserve capacity (`TrainingCapacityGate`), verify the runtime, decrypt the frozen dataset into owner-only scratch (`TrainingRunWorkspace`), spawn `train.py`, and follow its stdio protocol. `TrainingRunStatus` is `Queued → Preparing → Training → Exporting → Smoke →` (`Succeeded` | `Failed` | `Cancelled`).
- The **launch receipt is persisted immediately after spawn, before any output is read** — that is the only window in which a host crash could otherwise strand a trainer holding the whole GPU with nothing on disk to identify it by. Only `TrainingRunStartupReaper` clears a receipt, and only after a successful kill or a proven non-match; a receipt whose inspect or kill threw is left in place and retried next startup. The store refuses to delete a run that still holds a receipt (`ProcessNotConfirmedStopped`); no route deletes a run today. A receipt also records the boot it was written in (`LinuxBootId`; still schema 1). A receipt of another boot is cleared as gone with no probe and no signal, since no process outlives its boot. One that records no boot (written before the field existed, or when the id could not be read at spawn) keeps the checks above. One that records a boot while this boot's id cannot be read is kept and nothing is signalled, so the next startup retries it. Model Lab rows and warm receipt files reap through the same `TrainingProcessReaper`, so the same holds for them.
- Two independent bounds sit over the stream: an **inactivity watchdog** driven by the protocol's `heartbeat` event (a trainer wedged on a CUDA call prints nothing at all), and a max-duration backstop.
- **Cancellation is cooperative.** The operator's cancel signals the process *group* with SIGTERM, `train.py` latches `should_training_stop`, finishes its step and exits with a distinct status, and the run records `Cancelled`. Only the watchdog escalates to SIGKILL.
- `TrainingFootprintEstimator` sizes one QLoRA run against the host (4-bit frozen base ≈0.6 bytes/param, bf16 LoRA weights + two 8-bit Adam moment buffers ≈4 bytes per *trainable* param, activations as a headroom term), with `TrainingOptionDefaultsCalculator` computing the wizard's hyper-parameters. `GET training/runs/defaults` returns both plus the licensing text.

### The stdio protocol (contract version 1)

`train.py` emits one JSON object per line on stdout; **every other line is ignored**, because importing unsloth and torch prints banner text the script does not control.

`handshake` · `phase` (`loading` | `tokenizing` | `training` | `saving`) · `progress` (step/totalSteps/epoch/loss/lr/vramBytes) · `heartbeat` · `artifact` · `done` · `error`. Exit status is `0` success, `3` cooperative SIGTERM stop (recorded `Cancelled`, not `Failed`), `1` any error. `export.py` uses the same protocol with phases `loading` | `merging`.

## 5. Export, smoke and promotion

An export takes the **same hold a run does** — exclusive `IGpuWorkGate` plus the mutation lease — acquired before anything is written, so a refusal is an immediate, harmless 409.

- `TrainingArtifactKind` is `AdapterGguf`, `MergedGguf` or `HfAdapterDir`; all are staged under the run's own directory until promotion.
- The **adapter** path has no Python step: the host runs llama.cpp's `convert_lora_to_gguf.py` straight against the trainer's adapter directory. The **merged** path runs `export.py` to produce a 16-bit HF checkpoint, then the host runs `convert_hf_to_gguf.py` and `llama-quantize` **at the pinned llama.cpp commit**, so the file a model is served from comes from the same source tree as the server that loads it (`save_pretrained_gguf` is deliberately never called).
- **The run's status is never moved by an export.** Training already terminalized the run; the export's outcome lives entirely on the artifact row (digest, smoke state, reason), with live progress on the run hub. A run that succeeded stays succeeded.
- `TrainedModelSmokeGate` is the loadability/tool-syntax gate. It answers two questions a digest cannot — does `llama-server` actually load this file, and does the model still emit a syntactically valid tool call — because fine-tuning can destroy tool-calling while leaving a file that loads perfectly. `TrainingArtifactSmokeState` is `Pending`/`Passed`/`Failed`/`Skipped`, and `Skipped` is a deliberate operator choice, not a silent pass. Smoke and evaluation each take model-load admission through their owning transient-runtime component; callers do not hold a second admission ticket.
- Promotion additionally requires a versioned quality decision over a complete base+tuned comparison with identical frozen membership and exact model/artifact identities. Aggregate and per-kind accuracy may not regress; benchmark deltas are advisory. Revalidation first replaces the promotable decision with `Pending`, then requires a fresh comparison and fresh base+tuned evaluation ids before a new decision can replace it. An Operator can override only a complete regression failure and must record an audited reason. `ArtifactPromotionService` rechecks the installed base, staged digest, and the importer's prepared SHA-256/size before committing through the same acquisition path every local GGUF import uses. Partial commits and failed persistence commits are compensated with the importer's rollback receipt.
- Ordinary deletion still goes through `ITrainingExportService.DeleteArtifactAsync`, never the store's row-only delete. Once quality evidence references an artifact/comparison, the explicit quality-discard route atomically releases the live comparison reference while retaining the encrypted decision and discard reason/time on the artifact row as an immutable audit tombstone. Staged-byte removal is idempotent: a failed cleanup leaves `DiscardCleanupPending` set so the same route can retry without rewriting the audit decision, and stale-artifact cleanup and comparison suggestions ignore tombstones.

## 6. Evaluation and comparison

An evaluation run (`training/evaluations`) scores a model against the **hold-out membership frozen by a training run**, one question per sample.

- **Both sides of a comparison take the hold-out sample ids from the same training run's freeze**, so the base and tuned models answer exactly the same questions. Deriving a fresh split per side would make the two accuracies incomparable while looking like they compared something.
- `EvaluationScorer` is deterministic — no model is consulted, so every verdict is reproducible from the persisted sample and the persisted response. Whether a sample is a no-tool sample is decided **structurally** (the frozen trajectory carries no tool part), not from its kind label. `ScoredBy` is `deterministic` in v1; `judge` is reserved.
- **Evaluation replays the run-owned immutable corpus, never live sample rows.** The encrypted frozen JSONL records its schema version and stable sample id on every row; the freeze binds its SHA-256 digest and hold-out ids. `EvaluationRunExecutor.LoadAsync` validates the freeze id, dataset-version fingerprint, digest and complete hold-out membership before constructing a model client. A later approve/reject/relabel operation can therefore change the live dataset without changing or preventing evaluation of the already-frozen run. Legacy v1 corpora remain readable through the freeze's sequence-to-id mapping.
- `TrainingEvaluationStatus` is flatter than a run's: `Queued → Running →` (`Succeeded` | `Failed` | `Cancelled`). Evaluations ride the same single-consumer queue. The transient harness binds encrypted execution provenance after validating its launch receipt and before the first verdict is persisted; `training/evaluations/{evaluationId}/resume` may continue a partial run only when the new attempt presents byte-identical provenance, so results from different runtime identities can never be merged.
- `ComparisonReportService.CreateAsync` **refuses unless both evaluation records and both `TrainingEvaluationMembershipV1` documents belong to the same training run**, and the memberships agree on `DatasetId`, `DatasetContentFingerprint` and the hold-out id set (order-insensitive); an unreadable membership is refused too. The report's run id is derived from that validated lineage rather than caller input. `training/comparisons/suggest` pre-fills a create dialog from one training run's lineage, and optional benchmark-run ids can be bound alongside the two evaluations.

## Constraints and traps a maintainer must respect

1. **A GGUF is not trainable.** Training needs an HF checkpoint; that is what `training/base-artifacts` exists for.
2. **The gate is one lock, and taking it IS the check.** Never read `IGpuWorkGate.ExclusiveKind` and then act on the answer — that property is for UX refusals only. Queued-but-unclaimed work does not block a run; only work that *holds* the gate does.
3. **Training is unavailable without a successful uv provision, and there is no fallback** — no degraded CPU path, no system interpreter. A failed install must name the failing step.
4. **Never add a dev dependency group to `tools/training/pyproject.toml`.** That file plus `uv.lock` is the shipped runtime manifest; repo tooling belongs in the root `pyproject.toml`.
5. **A run must be linked to its installed base GGUF**, or adapters are dead ends (no smoke, no promotion, no base side for a comparison).
6. **Merged export on a prebuilt runtime stops at the quantizer, by design.** Upstream ships no `llama-quantize` in release archives; only an in-app source build has one. The refusal says "build the runtime from source, or export at F16" — F16 merged export needs no quantizer.
7. **Any llama.cpp pin bump must re-check the convert scripts' top-level imports.** At the current pin `convert_hf_to_gguf.py`/`convert_lora_to_gguf.py` import a `conversion/` package, so provisioning only the two scripts plus `gguf-py` fails with `ModuleNotFoundError`.
8. **A route-bound id in a body DTO can never be `required`.** FastEndpoints deserializes the body before binding route values, so a `required` route id turns every generated-client delete into a 400.
9. **"placed all N layers on the GPU" is the fit-plan, not the audit.** For any live GPU gate use the CUDA `llama-server` override; `IRuntimeDeviceAudit` is the authority on what actually ran on the GPU.
10. **A queued run behind a warm model waits on the eject-first rule.** Dataset generation leaves its teacher resident; `POST model-fit/running/eject` starts the queued run immediately, and the queue logs the waiting→admitted transition once.
11. **An idle Model Lab worker holds the gate exclusively, and every refusal is demand.** A read that shows the exclusive holder as busy must also check `IGpuIdleHolderPreemption.IsIdlePreemptible`, and a poller must peek for work before it touches the gate, or each empty poll evicts the worker.

### Queued runs and live progress

`TrainingRunList` polls while any run is queued or executing, but subscribes to the executing run rather than a newer
queued row. Only that run receives its streamed counters; an export on a finished run can keep its subscription while
other runs wait. `useTrainingRunHub` binds its returned progress to the subscription id, including the render before
a changed subscription's effect runs. Queued rows show guidance linking to Loaded models: training waits for other
work and resident models to release the runtime. This is guidance, not a claim that a particular model is the current
blocker; ejection remains an explicit operator action.
